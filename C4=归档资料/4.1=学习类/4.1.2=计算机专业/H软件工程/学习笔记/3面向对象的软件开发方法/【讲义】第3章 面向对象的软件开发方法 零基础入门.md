## 开篇：这一章到底在讲什么？

第 2 章讲的是「结构化方法」：把系统拆成一个个**功能模块**，像流水线一样加工数据。这套方法在需求稳定、流程清晰的系统上很好用，但遇到需求天天变、业务对象错综复杂的系统就吃力了。

第 3 章换一套思路：**不再围绕"功能"拆分，而是围绕"事物"来组织**——先找出系统里有哪些「东西」（对象、类），再看这些东西之间怎么打交道。这就是**面向对象**。

整章的四步走：

1. **先建立词汇表** —— 面向对象的基本概念（第 1 节）：对象、类、封装、继承、多态、重载。
2. **再学画图的语法** —— 统一建模语言 UML（第 2 节）：用例图、时序图、协作图、类图、状态图、组件图、部署图。
3. **然后搞清要做什么** —— 面向对象的需求分析（第 3 节）：活动图 → 用例图 → 类图 → 时序图 → 状态图。
4. **最后设计怎么做** —— 面向对象的设计（第 4 节）：包图、构件图、部署图、设计类图 + 构件级设计 + 界面设计。

和第 2 章的关系：**它们是两套并列的方法论，不是前后替代关系。** 结构化方法是「面向过程」的思路，面向对象方法是「面向对象」的思路。考试经常把两章的图混在一起出题，所以一定要分清哪张图属于哪个阶段。

## 第 1 节　面向对象的基本概念

> 本节对应考核要求：识记 6 个词条（对象、类、封装、继承、多态、重载）。**这一节是唯一"全靠背"的一节，但也是最容易拿分的一节。**

### 一句话定义

**面向对象 = 用「东西」来思考软件，而不是用「步骤」来思考软件。**

传统思路（面向过程）：「第一步输入，第二步计算，第三步输出」。
面向对象思路：「先看看有哪些角色，每个角色自己会做什么，需要时互相喊一声」。

### 用「乐高积木」来理解

- **对象** = 一块具体的积木。这块红色的 2×4 积木本身有形状（数据），也有「能拼到另一块上」这个本领（操作）。
- **类** = 积木的**模具/图纸**。图纸上写着「2×4 红色」这个规格和「凸点朝上」这个特性。用这个模具可以压出成千上万块一模一样的积木。
- **封装** = 积木的外壳把内部的塑料结构包住了。你只看到凸点和凹槽（对外接口），看不到里面的注塑纹路（内部实现）。
- **继承** = 「2×4 红色积木」这个模具是从「2×4 积木」这个通用模具派生的，继承了「2×4」的尺寸和凸点规格，只额外规定了颜色。
- **多态** = 你喊一声「拼上去！」，2×4 积木和 1×2 积木都听懂了，但各自拼出来的位置不一样。**同一句话，不同的东西有不同的反应。**
- **重载** = 「按一下」这个动作，在铅笔上是「按出笔芯」，在门铃上是「按响铃」。**同一个名字，不同的操作数，干不同的事。**

### 关键概念逐个讲透

#### 【识记】对象

> 教材原文：「**对象**是面向对象开发模式的**基本成分**，是由**描述该对象属性的数据**以及**可以对这些数据施加的所有操作**封装在一起构成的**统一体**。属性一般只能通过执行对象的操作来改变，**操作又称为方法**，在 C++ 中称为**成员函数**，它描述了对象执行的功能。」

拆开看三个要点：
1. 对象 = **数据（属性） + 操作（方法）** 打包成的统一体；
2. **属性不能随便改，只能通过操作来改**（这就是封装的体现）；
3. 操作有多个名字：**操作 = 方法 = C++ 中的成员函数**。

**配套概念：消息（教材同段给出，常作为干扰项的来源）**

> 「**消息**是要求另一对象**执行类中定义的某个操作**的规格说明。发送给一个对象的消息定义了**一个操作名和一个参数表（可能是空的）**，并**指定某一个对象**。当一个对象接收到发给自己的消息时，**调用消息中指定的操作**，并将**形式参数与参数表中相应的值结合起来**。接收对象对消息的处理可能会**改变对象的状态**（即改变接收对象的属性），并**发送一个消息给自己或另一个对象**。可以认为，这种**消息的传递大致等价于传统过程性方法中的函数调用**。」

一句话：**消息 = 「给谁 + 干什么 + 带什么参数」。**

#### 【识记】类

> 教材原文：「**类**是一组具有**相同数据结构和相同操作**的对象的**集合**，类的定义包括一组**数据属性**和对这组数据的一组**合法操作**。」
> 「**类定义可以视为一个具有类似特性与共同行为的对象的模板**，可用来产生对象。**每个对象都是类的实例**，它们都可使用类中提供的函数，一个对象的状态则包含在它的**实例变量**中。」

**类与对象的关系（教辅原题考过）**：
- 对象是类的**实例**；
- 类是对象的**模板**（"模具"这个比喻就是从这句话来的）；
- 对象的状态包含在它的**实例变量**中。

#### 【识记】封装

> 教材原文：「**封装**是面向对象方法的一个重要原则，它把对象的**属性和服务结合成一个独立的系统单元**，是一种**信息隐藏技术**，将对象的**外部特征（可用的方法）**与**内部实现细节（属性和方法如何实现）**分开，对象的**外部特征对其他对象来说是可访问的**，而它的**内部细节对其他对象是隐蔽的**。」

用表格记住"分开了什么"：

| 分界 | 内容 | 对其他对象 |
| --- | --- | --- |
| 外部特征 | 可用的方法（对外接口） | **可访问** |
| 内部细节 | 属性、方法如何实现 | **隐蔽** |

> ⚠ 关键联动：**面向对象中，信息隐藏是通过对象的封装来实现的**（第 4 节会再考一次）。第 2 章的信息隐蔽是「模块级」的，第 3 章的封装是「对象级」的——本质一样，层次不同。

#### 【识记】继承

> 教材原文：「**继承**是面向对象方法学中的**核心概念**，它是指**一个类的定义中可以派生出另一个类的定义**，派生出的类被称作**子类**，可以**自动拥有父类的全部属性和服务**。」
> 「继承**简化了人们对现实世界的认知和描述**，在定义子类时**不必重复定义已在父类中定义的属性和服务**，只要说明它是某个父类的子类，并定义自己特有的属性和服务即可。」

**继承的好处（一句话）**：**不重复造轮子**——公共部分在父类写一次，子类只写自己特有的。

#### 【识记】多态

> 教材原文：「在面向对象的软件技术中，**多态性**是指**子类对象可以像父类对象那样使用**，**同样的消息既可以发送给父类对象也可以发送给子类对象**。」

**用「同一个指令，不同反应」来理解**：系统里有个「图形」父类，下面有「圆」「矩形」两个子类，它们都有「计算面积」这个操作。你对一批图形统一发出「计算面积」这个消息——圆按 πr² 算，矩形按长×宽算。**发送方不需要知道对方到底是圆还是矩形**，这就是多态带来的灵活性。

#### 【识记】重载

> 教材原文：「有**两种**重载，即**函数重载**和**运算符重载**。
> **函数重载**是指在同一作用域内的**若干个参数特征不同的函数可以使用相同的函数名字**。
> **运算符重载**是指**同一个运算符可以对不同类型的操作数施加操作**。
> 当**参数特征不同**或**操作数的类型不同**时，实现函数的算法或运算符的**语义是不相同的**。」

| 类型 | 定义 | 例子（帮助理解） |
| --- | --- | --- |
| **函数重载** | 同一作用域内，**参数特征不同**的函数可以**用相同的函数名** | `add(int, int)` 与 `add(double, double)` 都叫 `add` |
| **运算符重载** | 同一个运算符可以**对不同类型的操作数**施加操作 | `+` 既能算整数相加，也能算字符串拼接 |

> ⚠ 区分多态和重载的常见考法：**多态看的是"子类对象可以像父类对象那样使用"**（涉及父类与子类）；**重载看的是"同名不同参 / 同运算符不同类型"**（不涉及继承关系）。

### 考试这样考

- **选择题**：对象与类的关系（正确项：「对象是类的一种实例」；干扰项：「对象是类中的操作」「对象是类的封装」「对象是类中的属性」）；消息的定义；多态的定义；重载分哪两种。
- **简答题**：什么是对象？什么是类？封装的含义是什么？继承有什么好处？
- **数字题**：重载有 **2 种**；继承中派生类叫**子类**，自动拥有**父类的全部属性和服务**。

### 易错点

| 坑 | 正确做法 |
| --- | --- |
| 说「类是对象的实例」 | 正好说反：**对象是类的实例，类是对象的模板** |
| 把「操作」和「消息」混为一谈 | **操作（方法）是对象自己拥有的功能**；**消息是别的对象发过来要求它执行某个操作的规格说明** |
| 认为多态和重载是一回事 | 多态讲**父类/子类**（同样的消息发给父类对象或子类对象）；重载讲**同名不同参/同运算符不同类型** |
| 把封装只说成"把数据藏起来" | 封装 = 把**属性和服务结合成一个独立的系统单元**（合起来）+ 分开**外部特征与内部实现细节**（藏起来），两个动作都有 |
| 只记住重载有函数重载 | 还有**运算符重载**，共 **2 种** |

## 第 2 节　统一建模语言

> 本节对应考核要求：识记「UML 的定义和用途」；领会 7 种图的作用及画法（用例图、时序图、协作图、类图、状态图、组件图、部署图）。

### 一句话定义

> 「**统一建模语言 UML** 是一个**通用的可视化建模语言**，用于对软件进行**描述、可视化处理、构造和建立软件系统制品的文档**。它可用于对系统的**需求分析、设计、浏览、配置、维护和信息控制**。」

**用「建筑行业的制图标准」来理解**：盖楼之前，结构工程师、水电工程师、暖通工程师要互相看图，如果每人一套画法就全乱了。于是行业统一了制图规范：粗实线是墙、细虚线是看不见的梁……UML 就是软件行业的这套「制图规范」。它**不是编程语言，也不是开发方法**，它是**画图说话的通用语言**。

### 关键概念逐个讲透

#### 【识记】UML 的用途

**用途（6 项，背下来）**：可用于对系统的 **需求分析、设计、浏览、配置、维护和信息控制**。

> 记法：「**需设浏配维信**」——需求、设计、浏览、配置、维护、信息控制。

#### 【识记】UML 的适用范围（这是最容易出"不属于/不适合"题的地方）

> 教材原文：「UML 是一种**通用建模语言**，对于一些**专门领域**，如**用户图形界面设计、超大规模集成电路设计、基于规则的人工智能领域**，使用**专门的语言和工具可能会更适合**。UML 是一种**离散的建模语言**，**不适合对诸如工程和物理学领域中的连续系统建模**。它是一个综合的通用建模语言，**适合对诸如由计算机软件、固件或数字逻辑构成的离散系统建模**。」

| 判断 | 内容 |
| --- | --- |
| **适合** | 由**计算机软件、固件或数字逻辑**构成的**离散系统** |
| **可能不太适合（专门领域）** | 用户图形界面设计、超大规模集成电路设计、基于规则的人工智能 |
| **不适合** | 工程和物理学领域中的**连续系统** |

> ⚠ 高频陷阱：题目问「下列哪项**不是** UML 的适用场合」，正确答案往往是「**连续系统**（如物理仿真、工程结构分析）」或上述三个专门领域之一。

#### 【领会】7 种 UML 图逐个讲透

##### （1）用例图（Use Case Diagram）

> 教材原文：「**用例图**表示**使用案例（即系统功能）与角色**（表示提供或接收系统信息的人或系统）**间的交互**。用例图显示使用案例与角色间的交互。使用案例表示**从用户角度对系统的要求**，因此**表示系统功能**。**角色是系统的主体**，显示哪个角色**启动**使用案例，并显示角色**何时**从使用案例收到信息。」
> 「用例图显示系统的**总体功能**，用户、项目管理员、分析人员、开发人员、质量保证工程师和任何对系统感兴趣的人都可以通过浏览这个图**了解系统的功能**。」

**一句话**：**用例图 = 谁（角色）能干什么（功能）。**

```

                    │        购书系统            │
    ┌──────┐        │   ╭─────────────╮         │
    │ 学生 │────────┼──►│   购买教材   │         │
    └──────┘        │   ╰─────────────╯         │
                    │   ╭─────────────╮         │
    ┌──────┐        │   │   查询库存   │         │
    │ 教师 │────────┼──►│              │         │
    └──────┘        │   ╰─────────────╯         │
                    │                           │
    ┌──────────┐    │   ╭─────────────╮         │
    │ 教材管理员│────┼──►│   录入教材   │         │
    └──────────┘    │   ╰─────────────╯         │
                    └───────────────────────────┘
      角色（棒状小人）        用例（椭圆）
```
（角色画在系统边界**外面**，用例画在**里面**，两者用**关联线**连起来。）

> ⚠ 教辅原题：「下列关于用例图的叙述中，正确的是」，答案 **C. 用例图用于描述系统的功能**。干扰项「用于描述系统的业务」（那是活动图）、「用于表示系统中类的构成」（那是类图）、「用于表示系统的状态变化」（那是状态图）。这四个干扰项就是 UML 各类图的用途互换，务必记牢。

##### （2）时序图（Sequence Diagram，又称顺序图）

> 教材原文：「**时序图**顶部显示了**涉及的角色**，系统完成取钱使用案例所需的**对象**也在时序图顶部显示。**每个箭头表示角色与对象或对象与对象之间为完成所需功能进行消息传递**。时序图**只显示对象而不显示类**，**类表示对象的类型**。**对象是特定的**，时序图不只显示客户，而且显示客户类的对象，如 Joe。」
> 「用户可以从这个图看到**业务过程的细节**，分析人员从时序图可以看到**处理流程**，开发人员看到**需要开发的对象和这些对象的操作**，质量保证工程师可以看到**过程的细节**，并根据这个过程**开发测试案例**，时序图对项目的各方面人员都有用。」

**一句话**：**时序图 = 按时间先后，把「谁给谁发了什么消息」一条条排出来。**

```
   学生        借阅界面       借阅控制器      图书
    │             │              │            │
    │ 1:提交借书请求│              │            │
    │────────────►│              │            │
    │             │ 2:校验读者资格 │            │
    │             │─────────────►│            │
    │             │              │ 3:查询库存  │
    │             │              │───────────►│
    │             │              │◄───────────│
    │             │◄─────────────│            │
    │◄────────────│ 4:返回借阅结果 │            │
    │             │              │            │
   （对象）      （对象）       （对象）      （对象）
    生命线：每个对象下方那条竖直虚线
    活动棒：生命线上那段狭长的矩形
```

##### （3）协作图（Collaboration Diagram，又称通信图）

> 教材原文：「**协作图**显示的信息**与时序图相同**，但协作图用**另一种不同的方式**显示这个信息，具有**不同作用**。」
> 「质量保证工程师和**系统架构师**利用协作图显示**对象间处理过程的分布**。若协作图是**星形的**，即几个对象与一个**中央对象**通信，则系统架构师可能认为系统对中央对象**依赖太强**，可能会**重新设计对象，更均匀地分配处理工作**。这种交互是**很难在时序图中看到**的。」

**一句话**：**协作图和时序图说的是同一件事（对象之间怎么发消息），只是摆法不同。**时序图强调**时间顺序**，协作图强调**对象之间的连接关系和处理分布**。

**教辅原题（必背）**：「下列选项中，用于显示**对象间处理过程分布**的图是」，答案 **A. 协作图**（干扰项：部署图、时序图、状态图）。

##### （4）类图（Class Diagram）

> 教材原文：「**类图**显示系统中**类与类之间的相互关系**。」「类图中每个类用**方框**表示，分成**三部分**：第一部分是**类名**；第二部分是**类包含的属性**；第三部分是**类的操作**。」
> 「**开发人员**用类图**开发类**。UML 的工具可以**产生类的框架代码**，然后开发人员用所选语言填充代码细节。**分析人员**用类图显示**系统细节**，**架构师**也用类图显示**系统设计**。」

**类图的三格画法（必会）：**

```
        ┌─────────────────────┐
        │        账目          │  ← 第一格：类名
        ├─────────────────────┤
        │  - 账号 : String     │  ← 第二格：属性
        │  - PIN  : int        │
        │  - 结余 : double     │
        ├─────────────────────┤
        │  + 打开()            │  ← 第三格：操作
        │  + 取钱()            │
        │  + 扣钱()            │
        │  + 验钱数()          │
        └─────────────────────┘
```

> 教辅原例：账目类包含**三个属性**——账号、PIN 和结余；包含**4 个操作**——打开、取钱、扣钱和验钱数。

##### （5）状态图（State Diagram）

> 教材原文：「**状态图**为**对象的各种状态提供了建模方式**。**类图提供了类及其相互关系的静态图形，而状态图则可以对系统的动态功能进行建模**。」「状态图显示对象的功能。例如，银行账目可能有几种不同状态，可以打开、关闭或透支通知客户，账目在不同状态下的功能是不同的，状态图可以显示这个信息。」

**一句话**：**状态图 = 一个东西在一生中会经历哪几种状态，什么事件让它从一种状态跳到另一种。**

```
        ● ──────► ┌──────────┐   取款超额    ┌──────────┐
     起始状态     │  正常打开 │ ───────────► │  透支状态 │
     （实心圆）   └──────────┘              └──────────┘
                     │  销户                     │ 还款
                     ▼                           ▼
                  ┌──────────┐              ┌──────────┐
                  │  已关闭   │              │  正常打开 │
                  └──────────┘              └──────────┘
                     │
                     ▼
                  ◉ 结束状态（牛眼形）
```

##### （6）组件图（Component Diagram）

> 教材原文：「**组件图**显示模型的**物理视图**。组件图显示系统中的**软件组件及其相互关系**，组件图中有**两种组件：执行组件和代码库**。**模型中的每个类映射到源代码组件**。一旦生成组件，就加进组件图中，然后画出组件间的**相关性**。组件间的相关性包括**编译相关性和运行相关性**。」

**一句话**：**组件图 = 软件被切成了哪几个可替换的物理零件（.dll、.jar、可执行文件），谁依赖谁。**注意：**每个类映射到源代码组件**。

##### （7）部署图（Deployment Diagram）

> 教材原文：「**部署图**显示**网络的物理布局和各种组件的位置**。」
> 「**项目管理员、用户、架构师和部署人员**通过部署图了解网络的物理布局和各种组件的位置，**项目管理员通过部署图与用户沟通系统的布局**，**部署人员用部署图进行部署和规划**。」

**一句话**：**部署图 = 软件装在哪几台机器上、这些机器怎么连。**（组件图管"软件零件"，部署图管"硬件落点"。）

#### 7 种图对比总表（最高频的考点，建议背下来）

| 图名 | 回答的问题 | 一句话关键词 | 静态/动态 |
| --- | --- | --- | --- |
| **用例图** | 谁用系统做什么？ | 角色 + 功能 | 需求视角 |
| **时序图** | 消息按什么顺序传？ | 时间顺序 | 动态 |
| **协作图** | 对象间的处理怎么分布？ | 处理分布（与序图同信息） | 动态 |
| **类图** | 系统里有哪些类、什么关系？ | 类 + 属性 + 操作 + 关系 | **静态** |
| **状态图** | 一个对象的状态怎么变？ | 状态迁移 | 动态 |
| **组件图** | 软件分成哪些物理组件？ | 物理视图 / 软件组件 | 物理 |
| **部署图** | 组件装在哪台机器上？ | 网络物理布局 | 物理 |

> 记忆抓手：**用例看功能、时序看顺序、协作看分布、类图看结构、状态看变化、组件看零件、部署看机器。**

### 考试这样考

- **选择题（极高频）**：一张图配一个用途，然后四张图互换。必背的三组：
  - 「描述系统功能」→ **用例图**；
  - 「显示对象间处理过程的分布」→ **协作图**；
  - 「显示网络的物理布局和各种组件的位置」→ **部署图**；
  - 「对系统的动态功能建模」→ **状态图**；
  - 「显示系统中类与类之间的相互关系」→ **类图**；
  - 「显示模型的物理视图」→ **组件图**。
- **简答题**：说明统一建模语言的用途和适用范围。
- **数字题**：组件图中有**两种组件**（执行组件、代码库）；组件间的相关性包括**编译相关性**和**运行相关性**。

### 易错点

| 坑 | 正确做法 |
| --- | --- |
| 把「显示对象间处理过程分布」答成时序图 | 那是**协作图**。时序图体现的是**处理流程/时间顺序** |
| 认为时序图显示类 | 时序图**只显示对象，不显示类**；**类表示对象的类型**，且对象是特定的（如客户类的对象 Joe） |
| 把组件图和部署图搞混 | **组件图 = 软件的物理视图（有哪些组件、谁依赖谁）**；**部署图 = 网络物理布局（组件装在哪台机器上）** |
| 认为 UML 万能 | UML 是**离散**建模语言，**不适合连续系统**；GUI 设计、超大规模集成电路、基于规则的 AI 领域有更专门的语言和工具 |
| 认为 UML 是一种编程语言或开发方法 | UML 是**通用的可视化建模语言**，用于描述、可视化、构造和建立软件系统制品的文档 |

## 第 3 节　面向对象的需求分析

> 本节对应考核要求：识记 11 条、领会 6 条、综合应用 6 条。**这是全章内容最多、分值最高的一节，务必重点突破。**

### 一句话定义

> 「**面向对象的需求分析**是**抽取和整理用户需求并建立问题域精确模型**的过程，这些模型可以从**不同的角度**描述系统。」

**用「拍电影」来理解这一节的 5 种图**：要拍一部电影，你得先有——

| 电影筹备 | UML 图 | 作用 |
| --- | --- | --- |
| 剧本里每一场戏的流程 | **活动图** | 表现一个活动到另一个活动的控制流 |
| 演员表 + 每个角色的戏份 | **用例图** | 谁（角色）和系统交互做什么（功能） |
| 分镜脚本（第几秒谁说什么话） | **时序图** | 对象之间消息传递的时间顺序 |
| 人物关系图 + 每个人的设定 | **类图** | 系统中有哪些类、属性和操作、彼此什么关系 |
| 某个角色的心理变化曲线 | **状态图** | 对象状态如何随事件变化 |

#### 【识记】面向对象分析常用的 5 种图（必背）

> 教材原文：「在面向对象的分析和设计中通常采用 UML 作为建模语言。在面向对象的分析中，主要使用以下 **5 种类型**的 UML 图。」
> - **活动图**：表示一个**过程或数据处理中所涉及的活动**；
> - **用例图**：表示一个**系统和它所处环境之间的交互**；
> - **时序图**：表示**参与者和系统之间及系统各部分之间的交互**；
> - **类图**：表示**系统中的对象类及这些类之间的联系**；
> - **状态图**：表示**系统是如何响应内部和外部事件的**。

> 记忆：**活、用、时、类、状**（活动图、用例图、时序图、类图、状态图）。
> ⚠ 注意：**协作图、组件图、部署图不属于分析阶段常用的 5 种图**——它们不在这个名单里，这是很常见的干扰项。

#### 【领会】基于用例实现的面向对象的建模步骤（8 步，简答题高频）

| 步骤 | 做什么 | 产出 |
| --- | --- | --- |
| 1 | 通过与**用户沟通**了解用户的**基本需求** | —— |
| 2 | **确定系统的边界**，定义系统做什么和不做什么，以及目标系统和其他外部系统的交互 | **上下文模型** |
| 3 | 了解系统的**业务流程** | **活动图模型** |
| 4 | 从**用户与系统交互**的角度，确定目标系统功能 | **用例模型** |
| 5 | 通过**识别问题域内的全部实体对象和类**，包括定义其**属性和方法**、**类之间的层次关系** | **静态结构模型**（类图） |
| 6 | **基于用例**，通过**时序图**描述系统内各对象之间的**交互关系** | 时序图 |
| 7 | **识别对象的行为和系统的工作过程**，利用**状态图**从**事件驱动**角度分析对象状态的变化，**完善类图** | 状态图 |
| 8 | **迭代地执行步骤 1～7**，直到完成模型的建立 | —— |

> 记忆链条：**沟通 → 定边界（上下文） → 业务流程（活动图） → 功能（用例图） → 静态结构（类图） → 交互（时序图） → 动态（状态图） → 迭代**。
> 教你一个口诀：**"边活用它，类时状迭"**（定边界 → 活动图 → 用例图 → 类图 → 时序图 → 状态图 → 迭代）。

> ⚠ 教辅原题：「基于用例实现的面向对象的建模需要完成的任务**不包括**」，答案 **D. 了解系统的部署需求，建立部署模型**。部署模型属于**设计阶段**的事，不在需求建模的 8 步里。

#### 【综合应用】上下文模型：确定系统的范围

> 教材原文：「在系统描述的**早期阶段**，首先**界定系统的范围与边界**，与客户一起明确**系统应该做什么**。应该确保系统实现对一些业务过程的自动支持，其他的为**手工过程**或由**不同的系统支持**。查看现有系统在**功能上可能的重合部分**，并决定**应该在哪里实现新功能**。在过程的早期阶段就完成这些判断，以便**估算和控制系统成本、节省分析系统需求和设计花费的时间**。」
> 「**上下文模型**通常表示**目标系统与其他外部系统的关系**，外部系统**可能产生数据供目标系统使用，同时也使用该系统产生的数据**。」

**用「画院子围墙」来理解**：先拿粉笔在地上画一圈——圈里是你的系统要管的，圈外是要打交道的邻居。「系统做什么、不做什么」这条线画早了，后面就不会做无用功。

> 教辅原题：「在需求分析阶段表示**目标系统与其他外部系统的关系**的模型是」，答案 **B. 上下文模型**（干扰项：系统的静态模型、系统的组件模型、MVC 模型）。

#### 【综合应用】活动图：描述业务流程

> 教材原文：「项目初期时**了解系统内部的业务流程**是非常重要的，**UML 中最适合描述企业业务流程的工具就是活动图**。**活动图本质上是一种流程图**，它着重表现**一个活动到另一个活动的控制流**，是**内部处理驱动**的流程。」

**一句话**：**活动图就是"升级版的流程图"，用来画业务是怎么一步步跑完的。**

**活动图的常用图标（考纲要求"活动图的作用与图标"）：**

| 图标 | 图形 | 含义 |
| --- | --- | --- |
| **起始点** | 实心圆 ● | 流程开始，**只能有一个** |
| **活动（动作）** | 圆角矩形 | 一个具体的处理步骤 |
| **判断/合并** | 菱形 | 按条件分岔或把分支合回来 |
| **分叉/汇合** | 粗黑线（同步条） | 并行分支的开始与结束 |
| **结束点** | 牛眼形（圆圈套实心圆） | 流程结束，**可以有多个** |
| **控制流** | 带箭头的线 | 从一个活动到下一个活动 |

**活动图画法 4 步：**
1. 找出业务流程的**起点**（画实心圆）和**终点**（画牛眼）；
2. 按业务实际顺序，把每个**活动**画成圆角矩形，用箭头串起来；
3. 遇到**需要判断**的地方画**菱形**，每条分支标上条件（如「库存足够 / 库存不足」）；
4. 有**可以同时进行**的工作就画**分叉粗线**（如"通知仓库"和"通知财务"并行），完成后用粗线汇合。

#### 【识记 + 领会】用例图：从业务流程到系统功能

##### 1. 什么是用例

> 教材原文：「**用例**是在一个系统中所进行的一连串的处置活动，该活动要能够满足系统外部的执行者对于系统的某种预期，这种预期与系统要实现的**某一功能**相对应。」

##### 2. 用例图规范（4 项，识记考点）

| 元素 | 图形 | 说明 |
| --- | --- | --- |
| **用例** | **椭圆形** | 用例代表**用户对系统的一个完整的期望**，**对应一个完整的功能** |
| **执行者（角色）** | **棒状小人**图形 | 执行者代表着**扮演某些特定角色的用户或系统**。对于系统来说，执行者代表**系统外对于系统有影响力的用户或是外部系统** |
| **关联** | 执行者和用例之间**带箭头的线** | 根据标准的 UML 定义，执行者与用例之间的关系，**只能够使用关联关系**表示**执行者启动用例** |
| **包含关系** | 带箭头的虚线，标 `«include»` | 一个**基本用例**里可以包含其他用例具有的行为。**执行基本用例时，每次都必须执行被包含的用例**，**被包含的用例可以单独执行** |

> ⚠ 必背细节：**执行者与用例之间只能用「关联关系」**（教材用了"只能够"三个字）。这是原话，很容易被拿来出判断题。

##### 3. 从业务流程到用例图建模（3 个动作）

**（1）利用与用户的对话找出系统的用例**

做法：**将活动图中的每个活动当作候选的用例**，然后针对每个活动询问用户以下几个问题：
1. 在这个活动中，**谁是主要参与者**？
2. 在活动进行中，**需要系统提供服务吗**？
3. **系统需要提供什么服务**？
4. **系统需要其他信息系统的支持吗**？

> 这就是「**活动图 → 用例图**」的桥梁：**活动图上的每个活动，都是候选用例的种子。**

**（2）画用例图**（按上面的 4 项规范画出来）

**（3）完成用例的描述**——对用例图中的**每一个用例**进行详细描述，一般至少分成**4 个方面**：

| 方面 | 内容 |
| --- | --- |
| ① **用例的简述** | 通常用**一两句话**说明这个用例的目的是什么 |
| ② **用例的正常流** | 必须说明**执行者和系统交互的过程** |
| ③ **用例的替代流** | 在正常流中如果有"**替代路径**"，必须**利用另外的替代流来说明**，而不是直接在正常流中写 `if-then-else` |
| ④ **用例的意外处理** | 通常指**系统例外状态**的处理。与替代流不同的是：**替代流往往是执行者对于流程有不同的指示**，因而将流程导向不同的结束点；而**意外处理则通常是系统发生错误**导致的正常流的意外状况 |

> 一句话区分替代流和意外处理：**替代流是"用户想走别的路"，意外处理是"系统自己出错了"。**

#### 【识记 + 领会】类图与静态结构

##### 1. 对象模型的 3 种类（必背，高频）

| 类别 | 定义（教材原文） | 通俗理解 |
| --- | --- | --- |
| **实体类** | **问题域中的核心类**，从**客观世界中的实体对象**归纳抽象出来，用于**长期保存系统中的信息**，以及提供针对这些信息的相关处理行为 | 业务里真正"存下来"的东西：学生、图书、订单 |
| **边界类** | 从**系统和外界进行交互的对象**中归纳、抽象出来的，是**系统类的对象和系统外的执行者的连接媒介**，**外界的消息只有通过边界类的对象实例才能发送给系统** | 「窗口」「门」：登录界面、借书界面、POS 终端 |
| **控制类** | 用于**协调系统边界类和实体类之间的交互** | 「调度员」：借书控制器、支付控制器 |

**记忆抓手**：**实体 = 存数据的；边界 = 跟外面打交道的；控制 = 在中间调度的。**

> ⚠ 一条易考细节：教材在「类的筛选」里特别提到，在**分析阶段不应过早考虑实现**，要**去掉与实现有关的候选类与对象**，「**如控制类、边界类等**」——也就是说，在**纯分析阶段**这两类是应该被筛掉的，它们在**设计和实现阶段**才变得重要。

##### 2. 类图规范：类的组成（【识记】）

> 教材原文：「类图中最重要的元素就是**类**。类主要由**类名、属性及操作**组成。」

| 组成 | 定义（教材原文） |
| --- | --- |
| **类名** | 类名是**访问类的索引**，应当使用**含义清晰、用词准确、没有歧义**的名字作为类名 |
| **属性** | 属性用来**描述该类的对象所具有的特征**。比如学生类中学生的**姓名、学号、出生日期**都可能是学生类的属性 |
| **操作** | 操作**描述对数据的具体处理方法**，**存取或改变属性值或者执行某个动作**都是操作，操作说明了**该类能做些什么工作** |

> 教辅原题：「下列选项中，**适合作为类的属性**的是」，答案 **D. 手机型号**（干扰项：学生、计算机、服装——这些是类）。
> 教辅原题：「下列选项中，**适合作为类或对象**的是」，答案 **A. 员工**（干扰项：员工姓名、员工所述部门、员工身份证号——这些是属性）。

##### 3. 类之间的关系（【识记】图标 + 【领会】含义，本节第二大考点）

**（1）关联关系**
> 「类与类之间**最基本的关系**就是**关联**。关联表达了**两个类的对象彼此间的结构性关系**。关联的图标为**类之间的一根直线**。」

**（2）泛化关系**
> 「**泛化关系**表达了两个类之间"**一般**"与"**特殊**"的关系。泛化的图标为**一个由子类指向父类的箭头**。」

**（3）整体-部分关系**
> 「整体-部分关系是**关联的一个特例**，因此这种关系其实也属于**结构的关系**。针对整体-部分间**不同的强度**，整体-部分关系又分为**聚合**及**组合**两种关系。」
> - **聚合**：「处于部分方的类的实例，**可以同时参与多个处于整体方的类的实例的构成**，同时**部分方的类的实例也可以独立存在**。」
> - **组合**：「部分方的类的实例**完全隶属于**整体方的类的实例，**部分类需要与整体类共存**，一旦**整体类的实例不存在了，部分类的实例也会随之消失**，失去存在的价值。」

**（4）依赖关系**
> 「**依赖关系**是一种**使用**的关系，依赖关系的两个类**并没有结构上的关联**，一般称为"**弱相关**"。其中一个模型元素是**独立的**、另一个模型元素**不是独立的**，它**依赖于独立的模型元素**，需要有独立元素**提供服务**。如果**独立模型改变了，将影响依赖于它的模型元素**。」

**（5）多重性**
> 「**多重性**通常在**关联或整体-部分关系**中会加以使用，代表着对象关系结构中，彼此能够允许的**最少及最多的数量**。」

**关系对比总表（背下来就能做图标题）：**

| 关系 | 图标（文字描述） | 关键词 | 例子 |
| --- | --- | --- | --- |
| **关联** | 类之间的**一根直线** | 最基本、结构性关系 | 学生 —— 课程 |
| **泛化** | **由子类指向父类的箭头** | "一般"与"特殊" | 研究生 → 学生 |
| **聚合**（整体-部分，弱） | 整体端为空心菱形 | 部分**可独立存在**、可参与多个整体 | 班级 ◇—— 学生 |
| **组合**（整体-部分，强） | 整体端为实心菱形 | 部分**与整体共存亡** | 订单 ◆—— 订单项 |
| **依赖** | **带箭头的虚线** | **使用**关系、**弱相关**、无结构关联 | 报表 ——→ 数据库连接 |
| **多重性** | 在关联线两端写数字（如 `1`、`0..*`、`1..*`） | **最少及最多的数量** | 一个订单对应 1..* 个订单项 |

> 教辅原题：「表达类之间**一般性与特殊性**关系的是」，答案 **A. 泛化关系**（干扰项：聚合关系、关联关系、部分与整体的关系）。
> 教辅原题：「下列模型**能被自动转换为程序代码**的是」，答案 **C. 类图**（教材原文：「类图用于描述系统静态结构，**可以自动转换为程序代码**」）。

##### 4. 类图建模的 4 个步骤（【领会】「类的筛选」+ 综合应用）

> 教辅简答题答案：类图建模的基本步骤是 **① 识别类与对象 → ② 识别属性 → ③ 确定操作 → ④ 识别关联**。

**「识别类与对象」时要筛掉的 6 种候选（【领会】「类的筛选」，考试爱考"应该去掉哪一类"）：**

| 序号 | 名称 | 含义（教材原文） | 处理办法 |
| --- | --- | --- | --- |
| 1 | **冗余** | 如果**两个类表达了同样的信息** | 保留在此问题上**最富有描述力的名称** |
| 2 | **无关** | 现实世界中存在许多对象，不能把它们都纳入系统 | 仅把与问题**切相关的类与对象**放入目标系统 |
| 3 | **笼统** | 需求描述中常常使用一些**笼统的、泛指的名字** | 去掉 |
| 4 | **属性** | **有些名词实际上属于对象的属性** | 把这些名词从候选对象中**去掉** |
| 5 | **操作** | 需求描述中有时会使用一些**既可以作为名词又可以作为动词**的词 | **慎重考虑**它们在问题中的含义，以便**正确地决定把它们作为类还是作为类中的操作** |
| 6 | **实现** | 在分析阶段**不应过早地考虑怎样实现**目标系统，应去掉与实现有关的候选类与对象 | 如**控制类、边界类**等，在设计与实现阶段可能重要，分析阶段过早考虑反而分散注意力 |

> 记忆口诀：**冗、无、笼、属、操、实**。

#### 【领会】时序图与交互模型

##### 1. 时序图的 3 个主要任务（简答题高频）

> 教材原文：「一般来说，时序图的主要任务包括如下几项。
> 1）**表达设计人员心中关于将来程序在运行时的对象协作模型**。
> 2）**验证软件领域模型类图的正确性**。时序图是从**抽象层次的类图**而来的，因此，**时序图中的所有元素都必须在类图中存在**。
> 3）**为程序员提供编码的蓝图**。时序图表达的方式是**以时间为纵轴**的，这也恰巧符合编码的方式，它们都有"**顺序**"。」

##### 2. 时序图规范（识记 4 要素，必背）

| 要素 | 说明（教材原文） |
| --- | --- |
| **对象** | 在时序图中，**每个参与部分都是"对象"** |
| **消息** | 对象与对象之间**只能通过传递消息来联系**。所谓消息，**其实就是对象所属类的操作** |
| **生命线** | 对象有生命线且**用虚线表示**，因此在时序图中，**对象必须在其生命线中才能够彼此交换消息** |
| **活动棒** | 每个对象**生命线上的狭长矩形**是**活动棒**，**在活动棒内的所有消息之间存在清晰的时序关系** |

> ⚠ 教辅原题：「时序图中**不包括**」，答案 **C. 对象的属性**。教材解析：「时序图中包含的要素有**对象、消息、生命线**。」（活动棒是生命线上的矩形，也属于时序图的构成元素。）注意属性属于**类图**的内容，不是时序图的要素。

#### 【领会】状态图与事件驱动模型

##### 1. 事件驱动模型

> 教材原文：「**事件驱动模型**表示**系统内对外部事件的响应方式**，**事件引起一种状态向另一种状态的转变**。例如，当控制阀门的系统接收到操作员的指令时，可能从状态"**阀门开**"变为状态"**阀门关**"，这种系统观点**特别适合实时系统**。」

##### 2. 状态图规范（识记 5 项）

| 元素 | 图形 | 说明（教材原文） |
| --- | --- | --- |
| **起始状态** | **一个实心的圆形 ●** | 在一个状态机或状态机图中，**只能有一个起始状态**，这一点与**活动图的起始点**是相同的 |
| **结束状态** | 牛眼形（圆圈内套实心圆） | 代表**整个状态机到此活动结束**。在一个状态机或状态机图中，**可以有很多结束状态** |
| **状态** | **圆角矩形** | 其中可能包括**此状态中执行动作的简单描述** |
| **迁移** | 带标签的箭头 → | 状态与状态之间利用"**迁移**"来表达期间的关系，这代表**状态的变化情形**，**带标签的箭头代表使系统从一种状态变为另一种状态的触发事件** |
| **事件触发器** | 写在迁移上的标签 | 因为**某个事件发生而造成状态的迁移**时，在"迁移"关系上**标记该事件**，该事件被称为"**事件触发器**" |

> ⚠ 数字细节（易考）：**起始状态只能有 1 个；结束状态可以有多个。** 教材还特意点明这与**活动图的起始点相同**。

##### 3. 状态图的作用（简答题原题）

> 教辅简答答案：「**状态图用来描述一个类对象在不同用例间状态的迁移**。」

##### 4. 识别状态空间的 6 个步骤（简答题高频）

1. **识别对象在问题域中的生命周期**；
2. **确定对象生命周期阶段的划分策略**；
3. **重新按阶段描述对象生命周期，得到候选状态**；
4. **识别对象在每个候选状态下的动作**，并对状态空间进行调整；
5. **分析每个状态的确定因素（对象的数据属性）**；
6. **检查对象状态的确定性和状态间的互斥性**。

**其中第 1 步里，对象的生命周期分两种（易考对比）：**

| 类型 | 特点（教材原文） |
| --- | --- |
| **直线式生命周期** | 通常具有**一定的时间顺序特性**，即对象**进入初态后，经过一段时间会过渡到后续态**，如此直至对象生命结束 |
| **循环式生命周期** | 通常**并不具备时间顺序特性**，在一定条件下，对象会**返回到已经过的状态** |

> 用「电梯」和「红绿灯」理解：电梯从 1 楼到 10 楼再到 1 楼，更像循环式（会回到经过的状态）；一份合同"起草→审批→签署→归档→作废"是直线式，不会自己回到起草。

### 考试这样考

- **选择题（超高频）**：5 种分析用图是哪些；3 种类（实体/边界/控制）的判定；类之间关系的图标与含义；类图建模 4 步；时序图 4 要素；状态图规范（起始状态几个、结束状态几个）；「适合作为类的属性的是」。
- **简答题（高频）**：①在面向对象的分析中主要使用哪 5 种类型的 UML 图？②基于用例实现的面向对象的建模由哪几个步骤组成？③总结在面向对象分析过程中进行类图建模的基本步骤。④时序图的任务是什么？时序图中包含哪些要素？⑤状态图的作用是什么？如何识别对象的状态空间？
- **应用题**：给定业务场景（如杂货店库存管理），确定对象类并用泛化关系表示继承；或根据活动图推导用例图。

### 易错点

| 坑 | 正确做法 |
| --- | --- |
| 把协作图/组件图/部署图算进「分析常用的 5 种图」 | 分析常用 5 种图 = **活动图、用例图、时序图、类图、状态图** |
| 在需求建模里加上"建立部署模型" | 部署模型是**设计阶段**的产物，不在基于用例的需求建模 8 步中 |
| 认为执行者与用例之间可以用各种关系 | 教材原话是「**只能够使用关联关系**表示执行者启动用例」 |
| 把「替代流」和「意外处理」说成一回事 | **替代流 = 执行者对流程有不同的指示**；**意外处理 = 系统发生错误导致的正常流意外状况** |
| 混淆聚合和组合 | **聚合：部分可独立存在、可参加多个整体**；**组合：部分与整体共存亡** |
| 混淆起始状态和结束状态的个数 | **起始状态只有 1 个，结束状态可以有多个** |
| 把「依赖关系」说成有结构关联 | 依赖是**使用关系**、**弱相关**、**没有结构上的关联** |

## 第 4 节　面向对象的设计

> 本节对应考核要求：识记 9 条、领会 6 条、综合应用 5 条。核心是**设计准则**、**体系结构（分层/三层/MVC）**、**包图/构件图/部署图**、**构件级设计**、**界面黄金规则**。

### 一句话定义

> 「**面向对象的设计**以面向对象分析所产生的**系统规格说明书**为基础，**设计出描述如何实现各项需求的解决方案**。这个解决方案是后续进行**系统实现**的基础。从面向对象分析到面向对象设计，是一个**逐渐扩展模型**的过程，是用面向对象观点建立"**求解**"域模型的过程。」

**用「装修」对比理解**：第 3 节（分析）是「业主说要三室两厅、要开放式厨房」，是**问题域**；第 4 节（设计）是「工长拿出水电图、材料清单、施工排期」，是**求解域**。分析到设计，就是从「要什么」走到「怎么做到」。

### 关键概念逐个讲透

#### 【识记】面向对象软件设计需要完成的工作（4 项，必背）

| 序号 | 工作 | 定义（教材原文） |
| --- | --- | --- |
| 1 | **数据/类设计** | **类模型转化为设计类实现及软件实现要求的数据结构** |
| 2 | **体系结构设计** | 定义了软件主要**结构化元素之间的关系**、满足系统需求的**体系结构风格和模式**，以及**影响体系结构实现方式的约束** |
| 3 | **接口设计** | 描述**软件和协作系统之间、软件和使用人员之间是如何通信**的，接口意味着**信息流（数据和控制）和特定的行为类型** |
| 4 | **构件设计** | 将软件体系结构的**结构化元素变换为对软件构件的过程性描述** |

> 记忆：「**类、架、口、件**」——数据/类设计、体系结构设计、接口设计、构件设计。

#### 【识记】面向对象软件设计的基本步骤（3 步）

1. **通过建立模型表示系统或产品的体系结构**；
2. **为各类接口建模**，这些接口在**软件和最终用户、软件和其他系统与设备、软件和自身组成的构件**之间起到连接作用；
3. **详细设计系统的软件构件**。

#### 【领会】面向对象设计的准则（6 条，必背）

| 准则 | 要点（教材原文摘要） |
| --- | --- |
| **（1）模块化** | 大型系统的特点决定了系统的设计必然走模块化的道路。**自上向下、分而治之**是控制系统复杂性的重要手段。将一个问题分解成许许多多的子问题，由**不同的开发人员同时开发**，由此可得到很多**易于管理和控制**的模块。这些模块具有**清晰的抽象界面**，同时还**指明了该模块与其他模块相互作用的关系**，每个模块可以完成指定的任务 |
| **（2）抽象** | 面向对象方法**不仅支持过程抽象，而且支持数据抽象**。**类实际上是一种抽象数据类型**，它**对外开放的公共接口构成了类的规格说明（即协议）**，这种接口规定了**外界可以使用的合法操作**，利用这些操作可对类实例中包含的数据进行操作 |
| **（3）信息隐蔽** | 在进行模块化设计时，为了得到一组最好的模块，应该使一个模块内包含的信息（**操作和数据**）对于**不需要这些信息的其他模块来说是不能被访问的**，即要**提高模块的独立性**。**在面向对象方法中，信息隐蔽通过对象的封装来实现** |
| **（4）低耦合** | 在面向对象方法中，**对象是最基本的模块**，耦合主要指**不同对象之间相互关联的亲密程度**。低耦合的理想情况意味着**对系统某一部分的理解、测试或修改，无须涉及系统的其他部分** |
| **（5）高内聚** | 见下面的 3 种内聚 |
| **（6）可复用** | 设计出的构件应能被重复使用 |

**低耦合的两种类型（重点，容易出对比题）：**

> 「对象之间的耦合可分为**交互耦合**与**继承耦合**两大类。」

| 类型 | 定义 | 应该怎么做 |
| --- | --- | --- |
| **交互耦合** | 对象之间的耦合表现为**消息连接** | **尽可能松散**。准则：① **尽量降低消息连接的复杂程度**，应该尽量减少消息中包含的参数，降低参数的复杂程度；② **减少对象发送或接收的消息数** |
| **继承耦合** | **一般类与特殊类之间耦合的一种形式**（即父类与子类之间） | **与交互耦合相反，应该提高继承耦合的程度**！因为「通过继承结合起来的基类（父类）和派生类（子类）构成了系统中**粒度更大的模块**，因此，它们彼此之间**应该结合得越紧密越好**」 |

> ⚠⚠ **本节最大的陷阱**：「低耦合」是总原则，但**继承耦合反而要提高**。考试极爱在这里设反向选项。

**高内聚的 3 种（必背）：**

| 类型 | 定义 |
| --- | --- |
| **操作内聚** | 一个操作应该**完成一个且仅完成一个功能** |
| **类内聚** | 应该使一个类**只有一个用途**，类的属性和服务应该是**高内聚**的。类的属性和服务应该是**完成该类对象任务所必需的**，其中**不包含无用的属性或服务** |
| **泛化内聚** | 设计出的泛化结构应该**符合多数人的概念**，这种结构应该是对相应的**领域知识的正确抽取** |

#### 【领会】体系结构设计

##### 1. 分层体系结构

> 教材原文：「**分离性和独立性**的概念是体系结构设计的基础，因为**分离性和独立性使得软件的变更得以局部化**（**只改变局部，不影响整个系统**）。**分层体系结构**是实现分离性和独立性的一个方式，**系统的功能被划分成几个独立的层次，每一层只依赖紧接着的下一层所提供的服务和设施**。」

**用「楼房」来理解**：二楼的地板靠一楼的墙撑着，三楼靠二楼。你装修三楼，一楼二楼照常用；但你不能把一楼拆了还指望三楼站着。**「每一层只依赖紧接着的下一层」**就是这条"只往下靠一层"的规则。

##### 2. 三层架构

> 教材原文：「通常意义上的**三层架构**就是将整个业务应用划分为**界面层、业务逻辑层和数据访问层**。区分层次依据"**高内聚低耦合**"的思想。在软件体系架构设计中，**分层式结构是最常见、最重要的一种结构**。」

| 层 | 功能（教材原文） |
| --- | --- |
| **界面层** | 用于**显示数据**和**接收用户输入的数据**，为用户提供一个人机交互式操作的界面 |
| **业务逻辑层** | 主要是**针对具体问题的操作**，也可以理解成**对数据层的操作、对数据业务逻辑的处理** |
| **数据访问层** | 其功能主要是**负责数据访问** |

> 记忆：**界面层管"看和输"，业务逻辑层管"算"，数据访问层管"取存"。**

##### 3. MVC 模式的 Web 体系结构（极高频）

> 教材原文：「**MVC（模型-视图-控制器）模式**，是一种**软件设计典范**。MVC 模式用一种**业务逻辑、数据、界面显示分离**的方法组织代码，将业务逻辑聚集到一个部件中，在**改进和个性化定制界面及用户交互的同时，不需要重新编写业务逻辑**。」
> 「MVC 应用程序被分成 **3 个核心部件：视图、控制器、模型**。」

| 部件 | 定义（教材原文） |
| --- | --- |
| **视图** | **用户看到并与之交互的界面** |
| **控制器** | **接受用户的输入并调用模型和视图**去完成用户的需求 |
| **模型** | 负责**业务逻辑的处理及数据库的访问** |

**MVC 模式的 4 个优点（必背）：**

| 优点 | 说明（教材原文） |
| --- | --- |
| **（1）耦合性低** | 由于 MVC 应用程序的 3 个部件是**相互独立的**，**改变其中一个不会影响其他两个**，因此依据这种设想能构造良好的**松耦合的构件** |
| **（2）重用性高** | MVC 模式允许使用**各种不同样式的视图来访问同一个服务器端的代码**，**多个视图能共享一个模型**，包括任何 Web 浏览器或者无线浏览器（WAP） |
| **（3）有利于开发，提高生产效率** | —— |
| **（4）可维护性高** | —— |

> 教辅原题：「下列关于 MVC 模式的叙述中，正确的是」，答案 **C. MVC 将应用程序划分为视图、控制器、模型三个核心部件**。
> 干扰项 A「MVC 用视图、数据、操作三个部分组织程序」、B「将系统分为界面层、业务逻辑层和数据访问层」（那是**三层架构**，不是 MVC）、D「分成用户界面、计算程序、输出程序」——都是把三层架构或编造的三分法混进 MVC。

##### 4. 系统逻辑结构与包图（【识记】包图的作用与规范）

> 教材原文：「**包图**由**若干个包及包之间的关系**组成。**包是一种分组机制**，将同类的类、对象、模型元素放在一起，形成**高内聚、低耦合的类集合**，**一个包相当于一个子系统**。」

**包图规范（2 项）：**

| 元素 | 说明 | 图标 |
| --- | --- | --- |
| **包** | 包图中**最基本的元素**就是"包" | 带标签页的文件夹形状 |
| **依赖关系** | 一个包中的类**需要引用另一个包中的类或对象**才能完成其功能时，两个包之间形成依赖关系 | **一条加箭头的虚线** |

```
   ┌──────────────┐          ┌──────────────┐
   │  界面包       │          │  业务包       │
   │  (UI)        │          │  (Business)  │
   └──────┬───────┘          └──────┬───────┘
          │  «import»               │
          └────────────────────────►│
                                     │
                            ┌────────▼───────┐
                            │  数据访问包     │
                            │  (DAO)         │
                            └────────────────┘
```

> 记忆抓手：**一个包 = 一个子系统**；包之间主要是**依赖关系（加箭头的虚线）**，与「类之间」的关系图标要分清。

##### 5. 系统物理体系结构与构件图（【识记】构件图与构件图规范）

**先搞清什么是构件：**
> 教材原文：「**构件**是具有**相对独立功能**、**可以明显辨识**、**接口由契约制定**、**语境有明显依赖关系**、**独立部署**且**多由第三方提供**的**可组装软件实体**。按照 UML 的定义，**构件是系统的模块化部分，它封装了自己的内容，且它的声明在其环境中是可以替换的**。」

**构件图规范（4 项，必背）：**

| 元素 | 说明（教材原文） |
| --- | --- |
| **（1）构件** | 构件是系统中**可以被替换的物理部件**，一个构件通常会**实现一组特定的接口** |
| **（2）提供接口** | **向其他构件提供服务的**，在构件内部**需要实现该接口的全部特征** |
| **（3）需求接口** | 用于表达构件**如果需要其他构件的服务才能运作** |
| **（4）依赖关系** | 构件之间的关系**主要是依赖关系**，表示**一个构件需要另一些构件才能有完整的意义** |

```
   ┌──────────────┐  提供接口 ○──    ○ 需求接口  ┌──────────────┐
   │   订单构件    │ ───────────────────────────► │   支付构件    │
   └──────────────┘                              └──────────────┘
                  （构件间主要关系：依赖）
```

> 「提供接口」和「需求接口」是一对：**我给别人用的 = 提供接口；我需要别人的 = 需求接口。** 对应到"插座"和"插头"：插座是提供接口，插头是需求接口。

##### 6. 系统物理体系结构与部署图（【识记】部署图的作用与规范）

> 教材原文：「**部署图**是面向对象系统的**物理方面建模**时使用的图，用于描述**系统硬件的物理拓扑结构及在此结构上运行的软件**。部署图用于**静态建模**，是表示**运行时节点结构、构件实例及其对象结构**的图，展示了**构件图中所提到的构件如何在系统硬件上部署，以及各个硬件部件如何相互连接**。」

**部署图规范（2 项元素 + 构件与节点的 4 条关系）：**

| 元素 | 说明 |
| --- | --- |
| **节点** | 节点是**存在于运行时，并代表一项计算机资源的物理元素** |
| **构件** | 部署图中还可以包含构件，这里所指的构件是**构件图中的基本元素**，它是**系统可替换的物理部件** |

**构件和节点的关系（4 条，必背）：**

1. **构件是参与系统执行的事物，而节点是执行构件的事物**。假设**节点是一台服务器，则构件就是其上运行的软件**；
2. **构件表示逻辑元素的物理模块，而节点表示构件的物理部署**；
3. **关联关系**：用**一条直线**表示，指出**节点之间存在着某种通信路径**；
4. **依赖关系**：**节点和构件间的关系主要是依赖关系**，在 UML 中，依赖关系的图形表示是一致的。

```
        ┌────────────────────┐        ┌────────────────────┐
        │   «device»         │        │   «device»         │
        │   Web 服务器        │        │   数据库服务器      │
        │  ┌──────────────┐  │        │  ┌──────────────┐  │
        │  │  «component» │  │        │  │  «component» │  │
        │  │  订单应用     │  │        │  │  MySQL       │  │
        │  └──────────────┘  │        │  └──────────────┘  │
        └─────────┬──────────┘        └─────────┬──────────┘
                  │      通信路径（关联：直线）    │
                  └─────────────────────────────┘
```

> 一句话区分：**构件图说"软件切成哪几块"，部署图说"这几块装在哪几台机器上、机器怎么连"。**

#### 三、构件级设计

##### 【识记】构件级设计主要关注的问题

> 教材原文：「体系结构设计**第一次迭代完成之后**，就应该开始构件级设计。**如何把设计模型转换为运行软件，是构件级设计关注的主要问题。**」

##### 【识记】构件级设计的基础

> 教材原文：「**数据、体系结构和接口的设计表示构成了构件级设计的基础**。每个构件的**类定义或者处理说明**都转化为一种**详细设计**，该设计采用**图形或基于文本的形式**来详细说明**内部的数据结构、局部接口细节和处理逻辑**。」

**记法**：**基础 = 数据 + 体系结构 + 接口**（正好对应前面 4 项工作中的前 3 项）。

##### 【领会】构件级设计的重要性

> 教材原文：「必须在**构造软件之前就确定该软件是否可以工作**。为了保证设计的**正确性**、以及与**早期设计表示（即数据、体系结构和接口设计）的一致性**，构件级设计要**以一种可以评审设计细节的方式来表示软件**。它提供了一种**评估数据结构、接口和算法是否能够工作**的方法。」

##### 【综合应用】从分析类到设计类

> 教材原例：在需求工程中得到一个名为 **PrintJob** 的分析类。在体系结构设计中，PrintJob 被定义为软件体系结构的一个**构件**，有两个接口：**computerJob** 和 **initiateJob**。computerJob 具有**对任务进行定价**的功能，initiateJob 能够**把任务传给生产设备**。构件级设计将由此开始。

> 教材原文（从用例场景到设计类）：「从分析类到设计类，软件设计人员**以构件为单元围绕问题域增加了接口定义和实现接口类（设计类）的属性和方法**，但是经常会由于对问题域的思考不全面、疏漏漏掉一些实现环节中的细节。」
> 「**用例反映了系统的需求，界定了系统的边界，涵盖了所有系统的应用场景**，因此通过对**用例场景**进行分析设计、对**用例中对象间的通信机制**进行描述，可以准确识别出实现该用例的**全部设计类**，以及其所需的**属性、方法及接口的定义**，在面向对象的设计中，**用时序图来描述对象之间的通信机制**。」

**核心公式（必背）：**

```
分析类 + 设计模式 = 设计类
```

> 教材说明：「从分析类转换成设计类需要结合具体的设计模式，如本节前面所提到的 **MVC 三层模式**。」
> 「**时序图描述用例场景中需要三层设计类/对象（模型、视图、控制器）交互来实现其功能**，在 UML 中，**边界对象（Boundary）、控制对象（Control）、实体对象（Entity）**的图形表示如图。」

##### 【综合应用】构件详细类图建模

> 教材原文：「设计类模型中显示了**各层次之间的依赖关系**，**边界类依赖控制类，控制类依赖模型类**，当页面得到用户一个请求时，这个请求将**逐层向下传递处理**。」

```
   ┌──────────────┐
   │   边界类      │   ← 界面/页面（Boundary）
   └──────┬───────┘
          │ 依赖
          ▼
   ┌──────────────┐
   │   控制类      │   ← 控制器（Control）
   └──────┬───────┘
          │ 依赖
          ▼
   ┌──────────────┐
   │   模型类      │   ← 实体/业务模型（Entity/Model）
   └──────────────┘
```

> ⚠ 必背方向：**边界类 → 控制类 → 模型类**（请求逐层向下传递）。这个顺序与 MVC 中「控制器接受用户输入并调用模型和视图」是一致的。

#### 四、用户界面设计（【识记】黄金规则）

> 教材原文：「关于界面设计有以下 **3 条黄金规则**：
> 1）**把控制权交给用户**。
> 2）**减轻用户的记忆负担**。
> 3）**保持界面一致**。」

**（1）把控制权交给用户（6 条）**
1. 以**不强迫用户进入不必要的或不希望的动作**的方式来定义交互模式；
2. 提供**灵活的交互**；
3. 允许用户交互**被中断和撤销**；
4. 当**技能水平高**时可以使交互**流线化**并**允许定制交互**；
5. 使用户与**内部技术细节隔离**开来；
6. 设计应允许用户与出现在屏幕上的对象**直接交互**。

**（2）减轻用户的记忆负担（5 条）**
1. **减少对短期记忆的要求**；
2. 建立**有意义的默认设置**；
3. 定义**直观的快捷方式**；
4. 界面的视觉布局应该**基于真实世界的象征**；
5. 以一种**渐进的方式揭示信息**。

**（3）保持界面一致（3 条）**
1. 允许用户将当前任务**放入有意义的环境中**；
2. 在**完整的产品线内保持一致性**；
3. 如果过去的交互模式已经建立起了**用户期望**，除非有不得已的理由，否则**不要改变它**。

### 易错点

| 坑 | 正确做法 |
| --- | --- |
| 把三层架构当成 MVC | **三层架构 = 界面层 + 业务逻辑层 + 数据访问层**；**MVC = 视图 + 控制器 + 模型**。两者不是一个东西，教材把它们分别讲 |
| 认为继承耦合也要降低 | **交互耦合要尽量松散（降低），继承耦合要提高**——这是唯一的例外 |
| 把「构件」和「节点」的关系说反 | **构件是参与系统执行的事物，节点是执行构件的事物**；**节点 = 一台服务器，构件 = 其上运行的软件** |
| 认为包之间的图标和类之间的依赖图标不同 | 都是**加箭头的虚线**；但包图中两个包之间的主要关系是**依赖** |
| 把界面黄金规则答成"美观、易用、友好" | 教材原文三条：**把控制权交给用户、减轻用户的记忆负担、保持界面一致** |
| 认为「分析类 + 设计模式 = 设计类」中的设计模式只能是 MVC | 教材举 MVC 三层模式为例，但公式本身说的是"结合具体的设计模式" |

```
面向对象的需求分析（做什么）
  ├─ 分析常用 5 种图：活动图、用例图、时序图、类图、状态图
  ├─ 建模 8 步：沟通 → 定边界（上下文模型）→ 业务流程（活动图）→ 功能（用例图）
  │             → 静态结构（类图）→ 交互（时序图）→ 动态（状态图）→ 迭代
  ├─ 活动图：本质是流程图，表现活动到活动的控制流，内部处理驱动
  ├─ 用例图：椭圆=用例，棒状小人=执行者，执行者与用例只能用关联关系
  │          包含关系：执行基本用例时每次都必须执行被包含的用例
  │          用例描述 4 方面：简述、正常流、替代流、意外处理
  ├─ 类图：3 种类（实体/边界/控制）；类的组成 = 类名 + 属性 + 操作
  │        5 种关系：关联（直线）、泛化（子类指向父类的箭头）
  │                  整体-部分（聚合/组合）、依赖（带箭头虚线，弱相关）、多重性
  │        类图建模 4 步：识别类与对象 → 识别属性 → 确定操作 → 识别关联
  │        类筛选 6 排除：冗余、无关、笼统、属性、操作、实现
  ├─ 时序图：要素 = 对象、消息、生命线（虚线）、活动棒（生命线上的狭长矩形）
  │          任务 3 项：表达运行时对象协作模型、验证类图正确性、为程序员提供编码蓝图
  └─ 状态图：起始状态只 1 个（实心圆），结束状态可多个；状态=圆角矩形，迁移=带标签箭头
             作用：描述一个类对象在不同用例间状态的迁移
             识别状态空间 6 步
                              ↓
面向对象的设计（怎么做）
  ├─ 需要完成 4 项工作：数据/类设计、体系结构设计、接口设计、构件设计
  ├─ 基本步骤 3 步：建模型表示体系结构 → 为各类接口建模 → 详细设计软件构件
  ├─ 设计准则 6 条：模块化、抽象、信息隐蔽、低耦合、高内聚、可复用
  │    低耦合含交互耦合（要松散）与继承耦合（要提高！）
  │    高内聚含操作内聚、类内聚、泛化内聚
  ├─ 体系结构：分层体系结构（每层只依赖紧接着的下一层）
  │            三层架构（界面层 + 业务逻辑层 + 数据访问层）
  │            MVC（视图 + 控制器 + 模型）；优点：耦合性低、重用性高、有利于开发、可维护性高
  ├─ 包图：包是分组机制，一个包相当于一个子系统；包间主要关系 = 依赖（加箭头虚线）
  ├─ 构件图：4 项规范（构件、提供接口、需求接口、依赖关系）
  ├─ 部署图：节点 + 构件；构件参与执行，节点执行构件；节点间关联（直线），节点与构件依赖
  ├─ 构件级设计：关注"如何把设计模型转换为运行软件"；基础 = 数据 + 体系结构 + 接口
  │              分析类 + 设计模式 = 设计类
  │              依赖方向：边界类 → 控制类 → 模型类
  └─ 界面设计黄金规则 3 条：把控制权交给用户｜减轻用户的记忆负担｜保持界面一致
```

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 把第 2 章和第 3 章的图混在一起 | **第 2 章**：数据流图、数据字典、判定表/判定树（需求）；SC 图（概要设计）；程序流程图、N-S 图、伪代码（详细设计）。**第 3 章**：活动图、用例图、时序图、类图、状态图（分析）；包图、构件图、部署图、设计类图（设计） |
| UML 七种图的用途互相张冠李戴 | 死记这张对照：用例图=功能；时序图=时间顺序；协作图=处理分布；类图=类与关系；状态图=状态迁移；组件图=物理视图；部署图=网络物理布局 |
| 认为「低耦合」在面向对象里没有例外 | **继承耦合要提高**——父类与子类构成的粒度更大的模块，应结合得越紧密越好 |
| 把三层架构和 MVC 当成同一个东西 | 三层架构 = 界面层/业务逻辑层/数据访问层；MVC = 视图/控制器/模型。MVC 是**设计典范**，三层架构是**体系结构分层** |
| 分析阶段就把边界类、控制类都建进去 | 教材在「类的筛选」中明确：**分析阶段应去掉与实现有关的候选类**，如控制类、边界类等；它们在设计实现阶段才重要 |
| 认为状态图的起始状态和结束状态数量规则一样 | **起始状态只能有 1 个**（与活动图的起始点相同）；**结束状态可以有很多个** |

## 大纲与教辅的差异

本章考纲与《电子教辅（通用版）》正文的覆盖情况**高度一致**，未见"教辅标注不考而考纲要求考"的情形。以下是几处需要在表述上留意的细微出入：

| 序号 | 考纲表述 | 教辅正文情况 | 处理建议 |
| --- | --- | --- | --- |
| 1 | 领会：「**环境复杂度**」出现在第 2 章 | 与本章无关 | 见第 2 章差异表 |
| 2 | 识记：「**对象模型中的实体类、边界类、控制类**」 | 教辅在「1.对象模型的类」中给出三类定义，但在「类的筛选」中又指出分析阶段应去掉**控制类、边界类**等与实现有关的候选类 | 两者不矛盾：**三类都要会定义**，「筛选时排除」讲的是**分析阶段的取舍原则**。答题按问题问的角度作答 |
| 3 | 领会：「对**用例图的描述**」 | 教辅给出用例描述的 4 个方面（简述、正常流、替代流、意外处理），但「用例图规范」标题下只列了用例、执行者、关联、包含关系 4 项 | 4 项规范 + 4 方面描述都要记 |
| 4 | 识记：「**组件图**与构件图规范」 | 教辅第 2 节用「**组件图**」（两种组件：执行组件、代码库），第 4 节用「**构件图**」（4 项规范）；正文有时混用「组件」「构件」 | 「组件图」与「构件图」在教材中指同一类图（Component Diagram），答题按题目用词照抄即可 |
| 5 | 识记：「**构件级设计的基础**」 | 教辅表述为「数据、体系结构和接口的设计表示构成了构件级设计的基础」 | 一致 |
| 6 | 综合应用：「画出**基于实体类的**构件图」 | 教辅第 4 节主要讲「系统物理体系结构与构件图」的一般规范，未专门用「基于实体类」这个措辞组织小节 | 按构件图 4 项规范作图，把问题域中的实体类映射为构件即可 |
| 7 | 考纲课程内容未单列「用户界面设计」 | 教辅第 4 节「四、用户界面设计」给出 3 条黄金规则及各自的具体条目 | 属于考纲识记词条「用户界面设计的黄金规则」的展开，必须记忆 |
