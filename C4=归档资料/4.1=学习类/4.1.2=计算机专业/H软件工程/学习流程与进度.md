# 第 1 章 软件工程概述

## 本章要解决的问题

1. 软件究竟包含什么，为什么代码不能代表完整的软件？
2. 为什么会出现软件危机，软件工程怎样应对？
3. 软件从需求到上线、维护，要经历哪些活动？
4. 面对不同项目，怎样选择软件过程模型？
5. 敏捷开发、Scrum 和 XP 分别解决什么问题？

## 一页总览

`软件 = 程序 + 数据 + 相关文档`

`软件工程 = 系统化 + 规范化 + 可度量`

`软件过程 = 需求分析 -> 软件设计 -> 软件实现 -> 软件测试 -> 软件维护`

| 场景关键词 | 优先想到的概念 |
| --- | --- |
| 延期、超支、缺陷多、难维护 | 软件危机 |
| 需求明确、变化少、顺序推进 | 瀑布模型 |
| 用户说不清需求、先做样稿 | 原型模型 |
| 项目风险高、反复分析风险 | 螺旋模型 |
| 面向对象、迭代、增量交付 | 统一过程模型 |
| 短周期交付、持续反馈、需求可变 | 敏捷开发 |
| 修复已发现的缺陷 | 改正性维护 |
| 适应系统外部环境或政策变化 | 适应性维护 |
| 新增功能、改善体验或性能 | 完善性维护 |
| 重构、补文档以降低未来风险 | 预防性维护 |

## 1.1 软件

### 1. 定义

软件是**程序、数据及其相关文档的完整集合**。

- **程序**：让计算机执行工作的指令。例如选课系统的前后端代码、安装包。
- **数据**：程序要处理、保存或依赖的信息。例如学生信息、课程信息、选课记录、初始化数据。
- **相关文档**：帮助人正确使用、部署、开发和维护软件的资料。例如需求说明书、设计说明书、部署手册、用户手册、API 文档、测试报告。

只有代码通常不算完整的软件交付：没有数据，系统可能无法正常运行；没有文档，用户和后续维护人员很难正确使用、部署或修改系统。

### 2. 软件与硬件的主要区别

| 角度 | 软件 | 硬件 |
| --- | --- | --- |
| 产生方式 | 以开发和设计为主 | 以制造和装配为主 |
| 复制成本 | 首个版本开发成本高，复制成本低 | 每增加一件产品都需要材料和制造成本 |
| 失效方式 | 不会因运行次数而物理磨损，但会因环境变化、补丁累积或设计老化而退化 | 会磨损、老化和损坏 |
| 标准化程度 | 常因业务不同而高度定制 | 零件、接口通常有较高标准化程度 |
| 复杂性来源 | 逻辑、需求、协作和组织因素 | 物理结构、材料和制造因素 |

### 3. 例子

学校选课系统：

- 程序：选课、退课、容量检查的代码。
- 数据：学生、课程、选课记录。
- 文档：管理员部署说明、学生使用说明、接口文档。

### 4. 易错点

- “安装包”主要是程序，不等于完整软件。
- “选课记录”是数据，不是文档。
- “部署说明”和“API 文档”是文档，不是程序。

## 1.2 软件工程

### 1. 定义

软件工程是用**系统化、规范化、可度量**的方法，对软件进行开发、运行和维护。

它不是单纯的写代码，而是让多人能够在可控的成本、进度和质量下，持续交付和维护软件的工程方法。

### 2. 软件危机

**软件危机**指软件开发或维护中出现的一系列严重问题，例如：

- 项目延期；
- 成本或预算失控；
- 缺陷多、质量差；
- 用户需求得不到满足；
- 后期修改困难、维护成本很高。

软件规模变大、需求复杂且变化频繁、多人协作缺少规则时，更容易出现软件危机。

### 3. 三个核心特点

| 特点 | 含义 | 典型例子 |
| --- | --- | --- |
| 系统化 | 按完整过程组织工作，明确活动之间的先后和输入输出 | 先分析需求，再设计、实现、测试 |
| 规范化 | 使用统一的标准、文档和约定，减少个人随意性 | 统一代码格式、接口规范、需求模板 |
| 可度量 | 用数据判断进度、成本和质量，而不是只凭感觉 | 统计缺陷数、完成任务数、测试覆盖情况 |

### 4. 快速判断

- “写需求文档”主要体现：系统化。
- “统一代码命名与格式”主要体现：规范化。
- “统计剩余缺陷数量”主要体现：可度量。

## 1.3 软件过程

### 1. 定义

软件过程是将用户需求转化为可运行、可使用、可维护的软件的一系列活动和工作步骤。

### 2. 基本活动

| 阶段 | 核心问题 | 典型工作 | 选课系统例子 |
| --- | --- | --- | --- |
| 需求分析 | 要做什么？ | 收集、分析、确认功能和约束 | 明确“同一学生不能重复选课”“满员后不能选” |
| 软件设计 | 怎么做？ | 设计架构、模块、数据库、接口和界面 | 设计学生表、课程表、选课记录表及字段关系 |
| 软件实现 | 怎样变成程序？ | 编码、构建、集成 | 编写选课、退课、容量检查代码 |
| 软件测试 | 是否做对了？ | 执行测试、发现并定位缺陷 | 验证满员时不能选课，退课后名额会释放 |
| 软件维护 | 上线后怎样持续可用？ | 修复、适应、完善和预防 | 修复重复选课；因新政策调整规则；增加候补功能 |

### 3. 最容易混淆的边界

| 描述 | 阶段 | 原因 |
| --- | --- | --- |
| “课程容量满后不能继续选课” | 需求分析 | 这是业务规则，先决定系统要做什么 |
| “课程容量字段放在哪张表、如何加锁” | 软件设计 | 这是实现业务规则的方案 |
| “写容量检查代码” | 软件实现 | 把设计转化为程序 |
| “验证满员后确实不能选课” | 软件测试 | 检查结果是否符合需求 |
| “系统上线后新增候补排队” | 软件维护 | 上线后的功能变化 |

### 4. 软件维护的四种常见类型

这部分会在第 6 章进一步学习，这里先用于理解软件过程：

| 类型 | 目的 | 例子 |
| --- | --- | --- |
| 改正性维护 | 修复已发现的缺陷 | 修复重复扣款、登录失败 |
| 适应性维护 | 适应环境、硬件、操作系统、政策或法规变化 | 因操作系统升级修改兼容性；因新政策修改税率 |
| 完善性维护 | 新增功能或改善性能、易用性 | 增加候补排队、导出 Excel |
| 预防性维护 | 降低未来出问题和维护困难的风险 | 重构复杂代码、补齐关键文档 |

## 1.4 软件过程模型

软件过程模型规定了如何组织软件过程中的活动。没有一种模型适合所有项目，选择依据主要是需求是否明确、变化频率、风险大小、项目规模和团队特点。

### 1. 瀑布模型

**核心思路**：需求、设计、实现、测试等阶段按顺序推进；前一阶段形成较稳定的成果后，再进入下一阶段。

- 适合：需求明确、变化少、规则稳定的项目。
- 优点：阶段清楚，文档和管理相对容易。
- 局限：若后期才发现需求错误，回头修改的成本很高。
- 关键词：`需求明确`、`顺序推进`、`变化少`。

### 2. 原型模型

**核心思路**：先快速构建可演示的原型，让用户体验和反馈，再逐步明确需求并开发正式系统。

- 适合：用户说不清需求，特别是界面、交互流程不明确的项目。
- 优点：尽早获得反馈，减少“做出来才发现不是用户想要的”风险。
- 局限：原型可能质量不足，不能简单把演示原型直接当作正式产品。
- 关键词：`需求不清`、`先做样稿`、`用户反馈`。

### 3. 螺旋模型

**核心思路**：以迭代方式推进，每一轮都围绕目标、风险分析、开发验证和下一轮计划开展工作。

- 适合：规模大、成本高、技术或业务风险高的项目。
- 优点：能较早识别并处理风险。
- 局限：管理复杂，对风险分析能力要求高，成本通常较高。
- 关键词：`风险高`、`反复风险分析`、`迭代`。

### 4. 统一过程模型

**核心思路**：面向对象的迭代、增量开发。系统不是一次做完，而是在多轮迭代中逐渐交付更多可用功能并完善架构。

- 适合：面向对象的大中型项目。
- 关键词：`面向对象`、`迭代`、`增量交付`。

### 5. 模型选择速记

`需求清楚选瀑布；需求不清先原型；风险很高用螺旋；面向对象迭代用统一过程。`

## 1.5 敏捷开发

### 1. 基本思想

敏捷开发把大任务拆为短周期的小任务，通过频繁交付可用成果和持续获得反馈来适应需求变化。

- 小步迭代：一次完成一小部分功能。
- 频繁交付：尽早让用户体验可用成果。
- 持续反馈：根据用户、测试和团队反馈调整下一轮工作。
- 拥抱变化：需求变化时，优先安排和评估，而不是机械坚持旧计划。
- 团队协作：开发人员、产品人员和用户保持沟通。

### 2. Scrum

Scrum 是一种常见的敏捷开发框架，用固定周期的**冲刺（Sprint）**组织工作。冲刺常见时长为 1 至 4 周。

#### 角色

| 角色 | 主要职责 |
| --- | --- |
| 产品负责人 | 明确产品需求，确定需求优先级 |
| Scrum Master | 促进 Scrum 流程，帮助团队排除协作障碍 |
| 开发团队 | 完成冲刺中承诺的功能，产出可用成果 |

#### 常见事件

| 事件 | 目的 | 易混点 |
| --- | --- | --- |
| 冲刺 | 固定时长的开发周期 | 不是会议，是一段工作周期 |
| 每日站会 | 同步进度、下一步计划和阻碍 | 不用于向用户展示成果 |
| 冲刺评审会 | 展示本次冲刺的成果，收集用户或相关方反馈 | 面向成果和反馈 |
| 冲刺回顾会 | 团队复盘工作方式，决定下一轮如何改进 | 面向过程改进 |

### 3. XP（极限编程）

XP 更强调高质量代码和工程实践，常见实践包括：

- 结对编程；
- 测试驱动开发；
- 持续集成；
- 重构。

### 4. 敏捷开发的场景判断

用户想先看到“课程查询”功能，再决定选课和候补排队怎样做。团队可以先在一个冲刺中交付课程查询，再根据反馈安排下一轮工作。这体现了敏捷开发的短周期交付与持续反馈。
