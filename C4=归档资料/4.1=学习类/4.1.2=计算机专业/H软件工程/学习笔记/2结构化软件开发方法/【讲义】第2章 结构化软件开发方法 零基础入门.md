## 开篇：这一章到底在讲什么？

第 1 章说「做软件要按工程化的套路来」，但没说套路具体长什么样。这一章就是**把套路铺开**：

1. **先搞清楚要做什么** —— 需求分析（第 1 节），产出需求规格说明书；
2. **再想清楚怎么做** —— 软件设计（第 2 节），分「概要设计」（搭骨架）与「详细设计」（填血肉），核心思想是模块的独立性；
3. **骨架怎么搭才结实** —— 结构化系统设计（第 3 节），核心工具是 SC 图；
4. **每个零件的做法怎么写清楚** —— 详细设计（第 4 节），工具是程序流程图、N-S 图、伪代码。

一句话概括逻辑链：**需求 → 设计 → 结构 → 细节**。这一章是全书**工具最密集**的一章，画图题几乎全在这里。

## 第 1 节　软件需求分析

> 本节对应考核要求：识记 6 条、领会 3 条、简单应用 3 条、综合应用 3 条，是**全章第一大重点**。

### 1.1 需求分析的任务（识记）

> **定义（必背）**：需求分析的任务是**弄清用户对软件系统的确切要求，并用需求规格说明书的形式把它表达出来**。

两个动作缺一不可，考试常把第二个漏掉：

| 动作 | 做什么 | 漏答后果 |
| --- | --- | --- |
| **弄清** | 搞明白用户对目标系统的确切要求 | 只答这个 → 变成「光问不写」 |
| **表达** | 用**需求规格说明书**的形式写下来 | 只答这个 → 变成「光写不问」 |

**辨析（本节最关键的边界）**：需求分析回答的是「**做什么**」，不是「**怎么做**」。「怎么做」属于下一节软件设计。

> **为什么这一步最要命**：装修最贵的错误不是手艺差，而是「我以为是开放式厨房，你想要封闭式」。软件同理——需求错了，后面图画得再漂亮、代码写得再优雅，全是白干。这也是需求分析被称为「连接计划时期与开发时期的桥梁」的原因。

### 1.2 需求分析应遵循的原则（识记，2 条，必背）

> **原则一**：需求说明应具有**准确性和一致性**。
> **原则二**：需求说明应**清晰、准确，且没有二义性**。

两条原则管的是两件不同的事，别混：

| 原则 | 管什么 | 为什么重要 | 反例 |
| --- | --- | --- | --- |
| 一 | **对不对、打不打架** | 需求说明是**连接计划时期与开发时期的桥梁**，也是**软件设计的依据**；任何含糊、矛盾或微小错漏都可能铸成大错 | 前面写「必须登录后才能下单」，后面写「游客可直接下单」 |
| 二 | **清不清楚、有没有两种读法** | 需求说明是**沟通用户与系统分析员思想的媒介**，双方要靠它达成**共同理解** | 见下面的经典例子 |

**经典例子（很可能原样出题）**：工资管理软件的需求写着「具备中级职称**三年以上**者，岗位薪酬增加 100 元」。问题在于「三年以上」可以理解为**包含三年**，也可以理解为**不包含三年**——必须明确到底是哪一种。这就是「二义性」。

> **一句话记忆**：原则一管「对对碰」，原则二管「不歧义」。

### 1.3 需求分析的 5 个步骤（识记，必背，顺序不能乱）

先分清两个术语：

- **当前系统**：用户目前正在使用的系统（可能是手工方式，也可能是旧软件）；
- **目标系统**：准备开发的新系统。

| 步骤 | 做什么 | 通俗理解 |
| :---: | --- | --- |
| 1 | 通过对现实环境的**调查研究**，获得**当前系统**的具体模型 | 先去看人家现在怎么干活，原样记录 |
| 2 | 去掉具体模型中的**非本质因素**，抽象出**当前系统**的**逻辑模型** | 剥掉「用哪支笔、放哪个柜子」，只留「谁给谁什么数据」 |
| 3 | 分析当前系统与目标系统的**差别**，建立**目标系统**的逻辑模型 | 找出哪些环节该由计算机接手，画出新系统的逻辑模型 |
| 4 | 对目标系统进行**完善和补充**，写出完整的**需求说明** | ①确定**人机界面**（哪些工作由计算机做、哪些由人做）；②补上原来没考虑到的细节 |
| 5 | 对需求说明进行**复审**，直到确认文档齐全且符合用户的全部需求 | 拿回去跟用户逐条对 |

**顺序要点（最易被打乱出题）**：第 1、2 步讲的是**当前系统**，第 3 步才转向**目标系统**；第 4 步先定人机界面、再补细节；第 5 步才是复审。

> **口诀**：**调查当前 → 抽象当前 → 对比建目标 → 完善写文档 → 复审**。

### 1.4 结构化分析的定义（识记）

> **定义（必背）**：**结构化分析**就是使用**数据流图、数据结构图、结构化英语、判定表和判定树**等工具，来建立一种称为**结构化说明书**（即**软件需求规格说明书**）的目标文档。

记忆抓手：**5 个工具 + 1 份文档**。

- 5 个工具：数据流图、数据结构图、结构化英语（结构化语言）、判定表、判定树；
- 1 份文档：结构化说明书 = 软件需求规格说明书（SRS）。

**辨析（教材级原题）**：「可用于描述需求的图、表有：**数据流图、数据结构图、数据字典、判定树、判定表**」——**注意这句话里没有 SC 图、程序流程图、N-S 图**，那些是设计阶段的工具。看到把 SC 图塞进「需求工具」的选项，判错。

### 1.5 需求规格说明书的主要内容（领会，5 项，必背）

> **定义**：**需求规格说明书**又称**软件需求说明书（SRS）**，是需求分析阶段的最终产出，用来完整、准确地描述目标系统要做什么。

| 序 | 内容 | 说明 |
| :---: | --- | --- |
| 1 | **引言** | 叙述**问题定义阶段**确定的软件**目标与范围** |
| 2 | **数据描述** | ① **数据流图（DFD）**：表达目标系统的**逻辑模型**；② **数据字典（DD）**：汇集系统中使用的**一切数据的定义** |
| 3 | **功能描述** | 对软件功能要求的说明 |
| 4 | **性能描述** | 含**处理速度、响应时间、安全限制**等 |
| 5 | **质量保证** | 阐明交付前要做的**功能测试与性能测试**，并规定**源程序和文档应遵守的标准** |

> **口诀**：**引 — 数 — 功 — 性 — 质**。

### 1.6 数据流图 DFD（识记符号 / 简单应用画法 / 综合应用）

> **定义**：**数据流图（DFD）**是描述系统**数据流动与加工过程**的图形工具，用来表达目标系统的**逻辑模型**——它只回答「数据从哪来、经过什么加工、到哪去」，**不关心用什么技术实现**。

**四类组成元素（识记，必背）**：

| 元素 | 画法 | 含义 | 记忆 |
| --- | --- | --- | --- |
| **外部实体** | 矩形 | 系统之外、与系统交换数据的人或单位 | 「谁跟系统打交道」 |
| **加工（处理）** | 圆圈 | 对数据做变换处理 | 「数据被怎么处理」 |
| **数据流** | 带箭头的线 | 数据流动的方向与名称 | 「数据往哪走」 |
| **数据存储（文件）** | 开口条（双横线） | 数据的静态存放 | 「数据停在哪」 |

**画法五步（简单应用，可照做）**：

1. **找外部实体**——先确定系统边界：谁给系统数据、系统给谁数据；
2. **找加工**——把系统要做的事拆成若干个「动词短语」，一个动词一个圈；
3. **连数据流**——按业务顺序把实体、加工、存储用带箭头的线连起来，**每条流都要起名字**（名字应是一个名词）；
4. **补数据存储**——数据需要停留、被反复读取的地方画开口条；
5. **查平衡**——每个加工的输入输出要与它的说明一致，**不能凭空产出数据，也不能让数据凭空消失**。

**分层数据流图的思想（领会 + 综合应用）**：复杂系统的 DFD 可能有成百上千个加工，**不能一次画全**。正确做法是**从系统的基本模型（把整个系统看成一个加工）开始，逐层向下分解**；每分解一次，加工数量增多、每个加工的功能更具体；一直分解到**所有加工都足够简单、不必再分解**为止。

> **通俗理解**：像地图 App。第一层是「全国图」，双击某省进「省图」，再双击某市进「市区图」。全国图上看不见「XX 路 12 号」，也不需要看见——**层次就是用来控制信息量的**。

### 1.7 数据字典 DD（识记符号 / 简单应用）

> **定义**：**数据字典（DD）**是对数据流图中出现的**每一个数据元素、数据流、数据存储和加工**给出**准确定义**的集合，是数据流图的配套说明。

**为什么必须有它**：DFD 只画了「有股叫『订单』的数据流过来」，但「订单」到底由哪些字段组成、什么类型、多长，图上看不出来。**数据字典就是给图上的每一个名字写档案。**

**定义数据时使用的符号（识记）**：

| 符号 | 含义 | 例子 |
| :---: | --- | --- |
| `=` | **表示**（定义为） | `订单 = 订单号 + 客户 + 明细` |
| `+` | **顺序连接**（与） | `姓名 = 姓 + 名` |
| `[ \| ]` | **选择**（或，从中选一个） | `性别 = [男 \| 女]` |
| `{ }` | **重复**（出现零次或多次） | `明细 = {商品项}` |
| `( )` | **可选**（可有可无） | `客户 = 客户号 + 姓名 + (联系电话)` |

**不同类型数据的描述方法**：数据字典通常按**数据元素 → 数据结构 → 数据流 → 数据存储 → 加工**逐级定义，越往下越细，直到每个数据元素都能落到具体类型与取值范围。

### 1.8 加工说明：结构化语言、判定表、判定树（简单应用）

DFD 上的圆圈（加工）如果逻辑复杂，光有名字不够，要另写「加工说明」。三种常用表达方式：

| 工具 | 适合什么 | 特点 |
| --- | --- | --- |
| **结构化语言** | 逻辑不太复杂的加工 | 用「如果…则…否则…」这类受限的规范语句描述，介于自然语言与程序语言之间 |
| **判定表** | 条件组合多、规则密集 | 用表格把「条件」与「动作」一一对应，**不漏组合、不重规则** |
| **判定树** | 条件有先后层次 | 用树形结构自上而下逐层判断，**直观、易读** |

**判定表的基本结构**：上半部分是**条件**（列出所有条件及其取值组合），下半部分是**动作**（每种组合下该做什么）。条件 n 个、每个取「是/否」时，组合数为 **2ⁿ**。

> **辨析**：条件组合多、需要保证覆盖率 → 用**判定表**；条件本身有先后顺序、要给人看 → 用**判定树**。

### 1.9 考试这样考

- **名词解释**：结构化分析、数据流图、数据字典、需求规格说明书。
- **简答**：需求分析的任务是什么？（两个动作：弄清 + 表达）
- **简答**：需求分析应遵循哪两条原则？（准确性一致性 / 清晰准确无二义性）
- **简答**：需求分析分哪 5 个步骤？（注意第 1、2 步是当前系统，第 3 步转向目标系统）
- **简答/综合**：画出某系统的数据流图（分层）；给出数据字典的符号定义。
- **单选**：DFD 四类符号的辨析；「哪些工具用于需求阶段」的辨析题。

### 1.10 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 需求分析 = 只「问」用户 | 是「弄清」+「用需求规格说明书表达」两个动作 |
| 需求分析回答「怎么做」 | 回答「做什么」；「怎么做」是设计 |
| 两条原则混为一谈 | 一管「准确一致」，二管「清晰无二义」 |
| 5 步骤里第 1、2 步就是目标系统 | 第 1、2 步是**当前系统**，第 3 步才建**目标系统**模型 |
| 把 SC 图、程序流程图当作需求工具 | 需求工具是数据流图、数据结构图、数据字典、判定表、判定树；**SC 图与程序流程图属于设计阶段** |
| 数据流图一次画全 | 复杂系统要**分层**，从整体到逐步分解 |

## 第 2 节　软件设计

> 本节是**全章第二大重点**，也是「耦合内聚」这一考试高频区的所在。

### 2.1 软件设计的基本步骤与任务（识记）

> **定义（必背）**：**软件设计**是把**软件需求转化为软件表示**的过程。

需求回答「做什么」，设计回答「怎么做」并把答案表达成图与文档，让编码的人照着实现。

**软件设计的基本步骤 = 两个阶段**：

| 阶段 | 做什么 | 回答的问题 |
| --- | --- | --- |
| **概要设计** | 将软件需求转化为**数据结构和软件的体系结构** | 系统分成哪些部分？各部分什么关系？ |
| **详细设计** | 对体系结构细化，得到各组成部分的**详细数据结构和算法** | 每个部分内部具体怎么做？ |

**软件设计的任务（从技术内容角度）= 三类**：**数据设计**、**体系结构设计**、**实现过程设计**。

> **易混辨析（第 1 章已出现过同一组，这里再固化一次）**：问「设计的**步骤**」答**概要 + 详细**（2 个）；问「设计的**任务**」答**数据 + 体系结构 + 实现过程**（3 类）。

### 2.2 概要设计阶段的工作内容与文档（识记）

**概要设计要完成的四件事**：

1. **体系结构的总体设计**——确定软件的总体结构（分解出模块及模块间关系）；
2. **处理方式的设计**——确定系统采用什么处理方式（如批处理、联机实时处理、分布式处理等）；
3. **数据结构设计**——设计系统要用到的数据（数据库、文件、全局数据等）的结构；
4. **设计规范的制定**——统一设计过程中要遵守的约定与文档格式。

**概要设计阶段的文档构成**：概要设计说明书（含体系结构图、模块说明、接口说明、数据结构设计说明）、数据库/文件设计说明、模块清单等。

### 2.3 软件设计的基本策略与可靠性（领会）

**软件设计的基本策略**，把需求变成结构的几条主线：

| 策略 | 含义 |
| --- | --- |
| **由外向里** | 从外部接口和输入输出出发，逐步向内设计 |
| **自顶向下、逐步求精** | 先定总体结构，再逐层细化到每个模块内部 |
| **分解与抽象** | 把复杂问题分解为若干子问题，并在不同抽象层次上描述 |
| **信息隐蔽** | 模块内部的具体实现细节对外隐藏，只暴露必要的接口 |
| **模块化** | 把系统划分为若干相对独立的模块 |

**数据结构设计包括的内容**：逻辑结构设计（数据以什么逻辑形式组织）、物理结构设计（数据在存储介质上如何存放）、数据完整性设计（约束与校验规则）。

**可靠性的含义（领会）**：**可靠性**指软件在规定条件下、规定时间内**完成规定功能的能力**——通俗说就是「不出故障、能一直正确干活」。它与「正确性」不同：正确性看结果对不对，可靠性还要看**能不能持续稳定地对**。

### 2.4 模块与模块化（领会）

> **定义**：**模块**是软件中**具有独立功能、可以单独命名与访问**的组成单位（在结构化方法里通常对应一个过程/函数）。

| 概念 | 含义 |
| --- | --- |
| **模块的基本属性** | ①**接口**（对外怎么调用、传什么）；②**功能**（做什么）；③**内部逻辑**（怎么做）；④**状态**（运行中保留什么数据） |
| **模块化** | 把系统划分为若干模块来开发的做法 |
| **模块化带来的好处（必背）** | ①**降低系统的复杂性**，使系统**容易修改**；②**推动各个部分的并行开发**，从而**提高软件的生产效率** |
| **模块的独立性（必背）** | 模块之间「关系松散、各自完整」的程度。独立性越**高**，模块越容易理解、测试和修改，系统的**可维护性越高** |

> **辨析**：模块化**不等于**模块越多越好。模块划分过细，接口数量剧增、调用开销变大；划分过粗，独立性又不够。**目标是「高内聚、低耦合」这个平衡点。**

### 2.5 耦合与内聚（领会，本节最高频考点）

**总纲一句话**：**高内聚、低耦合 = 好设计。** 内聚衡量「模块内部抱得紧不紧」，耦合衡量「模块之间粘得牢不牢」。

#### 耦合（模块之间）——从好到坏

| 耦合类型 | 含义 | 好坏 |
| --- | --- | --- |
| **非直接耦合** | 两个模块之间没有直接联系，只通过上级模块的调用间接相关 | 最好 |
| **数据耦合** | 模块间只传递**简单数据参数** | 好 |
| **标记耦合** | 模块间传递的是**数据结构（记录/结构体）**，而对方只用其中一部分 | 较差 |
| **控制耦合** | 模块间传递**控制信息**（如传一个开关变量决定对方走哪条分支） | 差 |
| **外部耦合** | 多个模块都依赖**同一个外部环境/外部数据格式** | 差 |
| **公共耦合** | 多个模块都访问**同一个全局数据区** | 很差 |
| **内容耦合** | 一个模块**直接访问另一个模块的内部数据或内部逻辑** | 最差，必须避免 |

> **记忆抓手**：**只看「传的是什么、碰没碰别人的内部」**。传简单数据最好 → 传结构体次之 → 传控制开关更差 → 共享全局变量很差 → 直接伸手进别人内部最差。

#### 内聚（模块内部）——从坏到好

| 内聚类型 | 含义 | 好坏 |
| --- | --- | --- |
| **巧合内聚** | 模块内各成分之间毫无关系，只是碰巧放在一起 | 最差 |
| **逻辑内聚** | 各成分逻辑上相似（如「所有输入类操作」放一起），由传入参数决定执行哪一个 | 很差 |
| **时间内聚** | 各成分因为**在同一时间段执行**而放在一起（如「初始化模块」） | 差 |
| **过程内聚** | 各成分必须**按特定次序执行**才放在一起 | 中 |
| **通信内聚** | 各成分**处理同一份输入数据**或**产生同一份输出数据** | 较好 |
| **信息内聚（功能内聚）** | 模块内所有成分**共同完成一个单一功能**，且只做这一件事 | 最好 |

> **记忆抓手（从坏到好）**：**巧 → 逻 → 时 → 过 → 通 → 信**。
> 谐音口诀：**「巧逻时过通信」**——巧合、逻辑、时间、过程、通信、信息。

#### 高内聚低耦合的判定练习

看到一段描述，先问两个问题：

1. **模块之间传来传去的是什么？**（简单数据 = 好；结构体 = 次；开关 = 差；全局区 = 很差；直接改别人内部 = 最差）
2. **模块内部这些语句为什么凑在一起？**（因为都要做同一件事 = 好；因为碰巧/相似/同时/同序 = 依次变差）

### 2.6 考试这样考

- **名词解释**：模块、模块化、模块的独立性、耦合、内聚、可靠性。
- **简答**：模块化设计带来哪些好处？（降低复杂性便于修改 + 推动并行开发提高生产效率）
- **简答/单选**：给一段场景，判断属于哪种耦合或哪种内聚（**本章最典型的送分题，也是失分题**）。
- **单选**：高内聚低耦合与可维护性的关系（独立性越强 → 越易理解、测试、修改 → 可维护性越高）。
- **简答**：概要设计阶段的工作内容有哪几项？设计文档由哪些部分构成？

### 2.7 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 「设计的步骤」与「设计的任务」混答 | 步骤 = 概要 + 详细（2）；任务 = 数据 + 体系结构 + 实现过程（3） |
| 耦合越低越好、内聚越高越好，但把两者搞反 | **低耦合、高内聚**才对应「独立性高」 |
| 把「标记耦合」当成「数据耦合」 | 传**数据结构**是标记耦合；传**简单数据**才是数据耦合 |
| 把「控制耦合」与「逻辑内聚」混为一谈 | 控制耦合讲**模块之间**传控制信息；逻辑内聚讲**模块内部**成分相似 |
| 认为模块越小越多就越好 | 划分离散度要平衡，目标才是「高内聚低耦合」 |
| 认为可靠性 = 正确性 | 可靠性强调**在规定条件与时间内持续完成规定功能** |

## 第 3 节　结构化系统设计

> 本节的核心是 **SC 图**：识记符号、领会两种基本模型、综合应用两种分析法。

### 3.1 软件结构的典型形式（识记）

> **定义**：**软件结构**指软件由哪些模块组成、以及模块之间的**调用关系与层次关系**。它通常用**层次图**（树形结构）表示。

**典型形式**：

| 形式 | 特征 |
| --- | --- |
| **变换型** | 数据从外部进入系统后，经过一串加工，再输出到外部；结构上呈现「输入 → 处理 → 输出」三段 |
| **事务型** | 系统根据**事务（一种触发信号/请求的类型）**决定走哪一条处理分支；结构上呈现「一个调度中心 + 多条平行处理路径」 |

### 3.2 SC 图（识记符号 / 综合应用画法）

> **定义**：**SC 图（Structure Chart，结构图）**是描述软件**模块层次与调用关系**的图形工具，用来表达概要设计的结果。

**SC 图的表示符号（识记）**：

| 元素 | 画法 | 含义 |
| --- | --- | --- |
| **模块** | 矩形框（框内写模块名） | 一个功能单位 |
| **调用** | 带箭头的线（自上而下） | 上层模块调用下层模块 |
| **数据传递** | 调用线旁带**空心小箭头**，标数据名 | 调用时**传入/传出数据** |
| **控制信息传递** | 调用线旁带**实心小圆点**（或实心箭头），标控制名 | 调用时传递**控制标志** |

> **辨析**：SC 图画的是**模块结构**，不是流程。它不表示「先做哪步、后做哪步」，只表示「谁调用谁、传什么」。别把它和数据流图（画数据流动）、程序流程图（画执行顺序）混起来。

### 3.3 变换分析法与事务分析法（综合应用）

**变换分析法（把 DFD 变成 SC 图）**：

1. 在 DFD 上找出**传入部分**（把外部数据变成系统内部逻辑输入的那一段）；
2. 找出**传出部分**（把系统内部结果变成外部输出的那一段）；
3. 中间剩下的就是**变换中心**（真正做处理的部分）；
4. 为上三层各选一个模块：**主控模块**（顶层）、**输入模块**、**变换模块**、**输出模块**；
5. 把传入部分、变换中心、传出部分分别分解到下层，**逐层细化**；
6. 用 SC 图的符号画出层次与数据传递，并复查「每个模块只做一件事」。

**事务分析法**：

1. 在 DFD 上找出**事务中心**（接收事务请求、决定分派的那一点）；
2. 为它设一个**调度模块**（顶层），负责读入事务并选择分支；
3. 每一条事务处理路径各建一个**事务处理模块**；
4. 把各分支继续向下分解；
5. 画出 SC 图并复查。

**对软件模块结构的改进（综合应用常考）**：检查 SC 图是否能优化——合并功能重复的模块、把扇入扇出控制在合理范围、消除只做转发的「传声筒模块」、让上层模块少依赖下层的实现细节（即提高内聚、降低耦合）。

### 3.4 考试这样考

- **名词解释**：SC 图、变换型、事务型。
- **简答/综合**：给出 DFD，用变换分析法或事务分析法画出 SC 图（**分值最高的一类题**）。
- **单选**：SC 图四类符号的辨析；判断某系统属变换型还是事务型。
- **简答**：如何改进软件的模块结构？

### 3.5 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 把 SC 图当成流程图 | SC 图只表示**模块层次与调用**，不表示执行顺序 |
| 混淆变换型与事务型 | 变换型 = 「输入→处理→输出」三段；事务型 = 「一个调度中心 + 多条分支」 |
| 画 SC 图时把数据流也画成一堆箭头 | SC 图上只标**数据传递**与**控制信息传递**两类，且要区分空心/实心 |
| 认为 SC 图一次画好就行 | 画完要**复查与改进**（合并重复、控制扇入扇出、消除传声筒模块） |

## 第 4 节　详细设计

> 本节的核心是**三种表达工具**：程序流程图、N-S 图、伪代码。

### 4.1 详细设计的目的与任务（识记）

> **定义（必背）**：**详细设计**的目的是**为软件结构中的每一个模块确定其内部的数据结构与算法**，并用某种表达形式把算法描述清楚，使程序员能据此直接编码。

**任务（3 个主要方面）**：

1. 确定每个模块的**算法**与**内部数据组织**；
2. 选择恰当的**表达形式**（流程图、N-S 图、伪代码等）把算法描述出来；
3. 对设计结果进行**评审**。

### 4.2 详细设计的原则（领会）

| 原则 | 含义 |
| --- | --- |
| **模块逻辑简明** | 一个模块只做一件事，逻辑尽量简单、层次尽量少 |
| **单入口单出口** | 每个模块只有一个入口、一个出口，避免随意跳转 |
| **自上而下** | 按层次逐级细化，先定框架再填细节 |
| **使用规范工具表达** | 用流程图、N-S 图、伪代码等标准工具，而不是随手写自然语言 |

### 4.3 程序流程图及其标准符号（识记）

> **定义**：**程序流程图**是用图形符号描述程序**执行顺序**的工具，是最经典、最直观的详细设计表达方式。

**常用标准符号（识记）**：

| 符号 | 形状 | 含义 |
| --- | --- | --- |
| **起止框** | 圆角矩形（或椭圆） | 开始 / 结束 |
| **处理框** | 矩形 | 执行一个处理或计算 |
| **判断框** | 菱形 | 条件判断，产生「是/否」两条分支 |
| **输入/输出框** | 平行四边形 | 数据的输入或输出 |
| **流程线** | 带箭头的线 | 执行方向 |
| **连接符** | 小圆圈 | 图被断开时的接续点 |

> **辨析**：程序流程图**允许**任意跳转（所以容易画出「面条式」代码），这是它最大的缺点；N-S 图正是为了消除这个缺点才被提出。

### 4.4 N-S 图与伪代码（综合应用）

**N-S 图（盒图）**：

> **定义**：**N-S 图**是用**嵌套的矩形盒**表示程序结构的工具，它把每种控制结构画成固定形状的盒子，**取消了流程线**，从而强制单入口单出口。

**三种基本结构的画法**：

| 结构 | 画法 |
| --- | --- |
| **顺序** | 上下排列的两个矩形盒 |
| **选择** | 上方一个「条件盒」，其下分成左右两个盒，分别对应「条件成立」「条件不成立」 |
| **循环（当型）** | 一个外盒，内部上方是条件、下方是循环体，循环体部分用箭头表示重复 |

**优点**：结构清晰、不能随意跳转，**天然保证结构化**。**缺点**：嵌套太深时图会很大，不便修改。

**伪代码**：

> **定义**：**伪代码**是用介于自然语言与程序设计语言之间的**类代码文本**描述算法的工具。

- 它**没有严格的语法**，但保留了程序的结构（顺序、选择、循环）；
- 好处是**写起来快、便于修改、篇幅小**，适合表达复杂算法；
- 坏处是**不如图形直观**，且容易写成「既不像中文也不像代码」的模糊描述。

**三种工具对比（建议直接背这张表）**：

| 工具 | 形式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **程序流程图** | 图形 | 直观、符号标准、易上手 | 允许任意跳转，易画成「面条」 |
| **N-S 图** | 图形（盒式） | 强制结构化、无流程线、结构清晰 | 嵌套深时图幅大，不便修改 |
| **伪代码** | 文本 | 简洁、易改、篇幅小 | 不直观，规范性依赖书写者 |

### 4.5 结构复杂性度量（领会）

> **定义**：**结构复杂性度量**是用数值指标衡量程序**控制结构复杂程度**的方法，用来判断一段程序好不好理解、好不好测试。

大纲要求的三个度量：

| 度量 | 衡量什么 |
| --- | --- |
| **结构复杂性** | 程序控制结构的复杂程度（与判定结点的数量密切相关：**判定结点越多，程序越复杂，越难理解与测试**） |
| **环境复杂度** | 程序所处环境因素带来的复杂程度（该点在考纲中**仅要求识记名词**，本讲义不给编造的定义） |
| **交叉点复杂度** | 程序图中**交叉点**的多少带来的复杂程度；交叉点越多，越难读 |

> **可用的结论**：程序图记为 `G = (N, E)`，其中 `N` 为结点数、`E` 为边数；判定结点越多，结构越复杂，且一般认为结构复杂程度有上限（如考核中常以某阈值作为「过于复杂」的界）。**计算题以试卷给出的公式为准**，本讲义不提供未经核实的公式。

### 4.6 考试这样考

- **名词解释**：详细设计、程序流程图、N-S 图、伪代码。
- **简答**：详细设计的目的与任务是什么？（确定每个模块的内部数据结构与算法，并选择表达形式描述、组织评审）
- **综合应用**：给出一个算法（如「求 1 到 n 的和」「判断素数」「按成绩分档」），**用程序流程图 / N-S 图 / 伪代码三种形式分别描述**（最常出的大题）。
- **单选**：三类工具的优缺点辨析；流程图中符号的识别。

### 4.7 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 认为 N-S 图也能任意跳转 | N-S 图**取消了流程线**，强制单入口单出口 |
| 认为伪代码「越像代码越好」 | 伪代码重在**结构与可读性**，不追求语法严格 |
| 把「环境复杂度」当成有明确公式的量 | 考纲只要求识记该名词，不要自行编公式 |
| 结构复杂性只看代码行数 | 看**控制结构**，尤其判定结点的多少 |
| 把详细设计与概要设计的任务搞混 | 概要设计定**模块与体系结构**；详细设计定**模块内部的算法与数据结构** |

```
  产物：需求规格说明书 SRS（引—数—功—性—质）
        │
        ↓ 怎么做？
软件设计（怎么做）
  步骤：概要设计（数据结构 + 体系结构）→ 详细设计（详细数据结构 + 算法）
  任务：数据设计 + 体系结构设计 + 实现过程设计
  灵魂：模块的独立性 —— 高内聚、低耦合
        耦合（差→好）：内容 > 公共 > 外部 > 控制 > 标记 > 数据 > 非直接
        内聚（好→差）：信息 > 通信 > 过程 > 时间 > 逻辑 > 巧合
        │
        ├── 结构怎么搭 → 结构化系统设计
        │     SC 图（模块 + 调用 + 数据传递 + 控制信息传递）
        │     变换型：输入 → 处理 → 输出
        │     事务型：一个调度中心 + 多条分支
        │     画法：变换分析法 / 事务分析法 → 复查改进
        │
        └── 内部怎么做 → 详细设计
              程序流程图（直观，但可任意跳转）
              N-S 图（无流程线，强制结构化）
              伪代码（简洁易改，不直观）
              复杂性度量：结构复杂性 / 环境复杂度 / 交叉点复杂度
```

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 把需求工具和设计工具混在一起 | 需求：数据流图、数据字典、结构化语言、判定表、判定树；设计：SC 图、程序流程图、N-S 图、伪代码 |
| 认为需求分析回答「怎么做」 | 需求回答「做什么」，设计才回答「怎么做」 |
| 5 步骤里把当前系统与目标系统搞混 | 第 1、2 步是**当前系统**，第 3 步起才是**目标系统** |
| 需求两原则背串 | 一管「准确一致」，二管「清晰无二义」 |
| 「设计的步骤」与「设计的任务」混答 | 步骤 2 个（概要、详细）；任务 3 类（数据、体系结构、实现过程） |
| 耦合内聚顺序记反 | 耦合**越低越好**，内聚**越高越好**；口诀「巧逻时过通信」是从坏到好 |
| 把 SC 图当流程图 | SC 图只画模块层次与调用；流程图才画执行顺序 |
| 认为 N-S 图也能跳转 | N-S 图取消流程线，强制单入口单出口 |
| 给「环境复杂度」自编公式 | 考纲仅要求识记名词，计算以试卷给出的公式为准 |

## 大纲与教辅的差异登记

编写本讲义时对照考纲与教学辅导材料，发现以下需要留意之处，均已按考纲处理：

| # | 位置 | 情况 | 本讲义的处理 |
| :---: | --- | --- | --- |
| 1 | 详细设计·领会「环境复杂度」 | 教学材料全文未解释该词，只讲了程序图、交叉点复杂度、环域复杂度 | 只标注它的名词归属，**不编造定义**；计算结论以试卷公式为准 |
| 2 | 软件设计·领会「内聚」 | 考纲点名 6 种（巧合、逻辑、时间、过程、通信、信息），教学材料写「分为 8 种」并实际讲了 8 种 | 按考纲重点讲 6 种，同时保留「共 8 种」这个数字（易出数字题） |
| 3 | 软件设计·识记「详细设计过程中需要完成的 3 个主要任务」 | 教学材料第 2 节列 3 条，第 4 节又列了 4 条设计人员任务 | 以考纲的「**3 个主要任务**」为准，本讲义按 3 条组织 |
| 4 | 数据流图符号、环域复杂度公式 | 教学材料这两处是图片，文字层取不到 | 数据流图四类符号按结构化分析通用标准给出；公式不给未核实的形式 |
| 5 | 软件设计·领会「模块间耦合」 | 考纲点名 7 类，教学材料计数与点名略有出入 | 以考纲点名的 7 类为准列出 |

> 说明：第 1 条与第 4 条属教学材料缺口，第 2、3、5 条属计数或口径不一致——**考试以考纲为准**，本讲义已按考纲组织内容。
