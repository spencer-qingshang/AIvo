## 第 1 节　移动应用的特点

### 一句话定义

**移动应用（移动 App）= 可以运行在移动设备中的应用程序**，它包括支持移动设备的 WebApp、虚拟现实以及移动游戏。

移动设备则包括智能手机、平板电脑、可穿戴设备、手持游戏设备及其他专业化的产品。

### 用「日常生活比喻」来理解

把「电脑软件」想成**开一家大饭店**，把「移动 App」想成**开一辆流动餐车**：

| 对比点 | 大饭店（传统 PC 软件） | 流动餐车（移动 App） |
| --- | --- | --- |
| 顾客期待 | 好吃就行，等 20 分钟能接受 | 又好吃又要快，等 3 分钟就骂人 → **强调用户体验** |
| 经营环境 | 店面固定，水电稳定 | 今天在写字楼、明天在学校门口，还怕下雨 → **需求及环境复杂** |
| 硬件条件 | 大厨房、大冰箱、煤气管够 | 车小、电瓶供电、只能带一个炉子 → **技术难度更高** |

这三个「不一样」，就是考纲里「移动应用具有的 3 个特点」，一个都不能少，顺序也别记反。

### 关键概念逐个讲透

#### 1）特点一：强调用户体验（识记 + 领会）

**日常说法**：用户不看你功能有多少，只看「用起来爽不爽」。

**教材原话**：虽然不同的移动设备有许多相同的产品功能，但是用户更关心自己的移动产品所附带的功能体验。一些用户希望自己的计算机能有移动设备的功能，另一些用户则关注移动设备给他们带来的自由，而宁愿接受移动设备上类似软件产品功能和性能方面的局限性。

**翻译成大白话**：用户宁愿要「随时能用的 80 分功能」，也不要「必须坐在电脑前才能用的 100 分功能」。所以移动 App 的第一评价标准是**体验**，不是功能数量。

#### 2）特点二：需求及环境复杂（识记 + 领会）

**日常说法**：同一个 App，要在几百种手机、两三种操作系统、上千个机型上都能跑。

**教材原话**：移动平台因其所交付软件的不同而不同，操作系统（如安卓或苹果系统）与能够提供广泛功能的成百上千的移动 App 相结合。现在新的工具允许那些几乎没有经过正规培训的个人去开发或者销售应用产品。

**注意后半句的考点**：开发门槛降低 → 开发者水平参差不齐 → 需求与运行环境更加复杂、更不可控。

#### 3）特点三：技术难度更高（识记 + 领会）

**日常说法**：屏幕小、电量少、网络飘、传感器多，全是麻烦。

**教材原话**：针对各种不同硬件平台开发基于网络的应用需要解决各种复杂的技术问题。

#### 4）移动应用开发需要解决的 11 个技术难题（领会，简答题高频）

这 11 条是「技术难度更高」的展开，**简答题几乎年年能出**，建议按「平台—商店—周期—交互—环境—电—安全—资源—外部—测试」的顺序背：

| 序号 | 技术难题 | 一句话理解 | 关键词 |
| --- | --- | --- | --- |
| 1 | 多元化的硬件和软件平台 | 包括移动平台和固定平台 | 平台多 |
| 2 | 多种开发框架和程序设计语言 | 苹果、安卓、Windows 各不相同；很少有移动设备允许在设备上直接开发，通常在桌面系统的**模拟器**上开发 | 语言多、模拟器 |
| 3 | 多种具有不同规则和工具的应用商店 | 苹果、谷歌、微软、亚马逊都发布了自己的标准 | 商店多 |
| 4 | 开发周期短 | 移动产品市场竞争非常激烈 | 抢时间 |
| 5 | 用户界面的限制以及传感器与设备之间交互的复杂性 | 触摸、手势、摄像等和基于环境感知的使用场景 | 触摸手势 |
| 6 | 环境的有效利用 | 用户期望 App 基于设备的**物理位置**及可利用的**网络功能**提供个性化体验 | 位置＋网络 |
| 7 | 电源管理 | 背光、存储器读写、无线网络连接、专业硬件设备、处理器速度都影响电池 | 五因素见下 |
| 8 | 安全保密性、隐私模式和策略 | 无线网络可能被窃听，阻止窃听对用户安全至关重要 | 防窃听 |
| 9 | 计算和存储限制 | 海量信息会让移动设备不堪重负（存储、处理速度、能量消耗） | 存储/速度/能耗 |
| 10 | 依赖外部服务的应用 | 瘦客户端依赖 Web 服务提供商和云存储，引发可访问性与安全性担忧 | 瘦客户端 |
| 11 | 测试的复杂性 | 可用传统测试方法，或用 PC 上的模拟器测试 | 模拟器测试 |

**必背小清单**：影响移动设备**电池待机时间**的 5 个因素 = 背光、存储器读写、无线网络连接的使用、专业硬件设备的利用、处理器速度。

### 考试这样考

- **单选题（定义/判断）**：几乎都是「下列属于/不属于移动应用特点的是」「移动应用不同于传统主机应用的特点是」。
  - 教辅例题：移动应用不同于传统主机应用的特点是 → 答「移动应用需要支持更多样化的人机交互方式」（因为移动设备屏幕更小、交互方式更丰富：触摸、手势、摄像，还有基于环境感知的使用场景）。
- **单选题（技术判断）**：教辅例题「关于开发移动应用技术的叙述中，正确的是」→ 答「针对不同平台的移动应用需要在不同的环境下分开开发」。
  - 错误选项长这样：「移动设备资源有限，所以适合采用机器级语言」（错，语言要高级、要多语言）；「应该在移动硬件上直接开发」（错，通常在模拟器上开发）；「规模小，适合瀑布模型」（错，采用敏捷）。
- **简答题**：
  - 「移动应用有哪些特征？」→ 强调用户体验、需求及环境较复杂、技术难度更高。
  - 「列举一些解决移动应用开发的技术因素」→ 写上面 11 条。
  - 「哪些因素会影响移动设备电池的待机时间？」→ 5 个因素。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「移动应用的特点 = 界面小、运行快、价格低」 | 大纲的 3 个特点是**强调用户体验、需求及环境复杂、技术难度更高**，要原样记 |
| 「资源有限，所以用机器级语言开发」 | 恰恰相反：移动开发用**多种高级语言和框架**，而且多在**模拟器**上开发 |
| 「移动应用小，用瀑布模型更快」 | 移动应用采用**敏捷开发模型**，因为开发周期短、需求变化快 |
| 把电池因素记成「屏幕大小、CPU 型号」 | 教材列的是：背光、存储器读写、无线网络连接、专业硬件设备、处理器速度 |

## 第 2 节　移动应用开发的软件过程

### 一句话定义

**移动应用采用敏捷开发模型，其开发过程包括 5 个主要迭代阶段：需求分析、设计、开发、稳定、部署。**

### 用「日常生活比喻」来理解

把开发一个 App 想成**短视频博主做一档系列节目**：

1. **需求分析**：看评论区，决定这期讲什么（用户要什么）。
2. **设计**：写脚本、画分镜（= 体系结构设计、导航设计、界面设计、内容设计）。
3. **开发**：实拍（= 写代码，既有功能性部分也有非功能性部分）。
4. **稳定**：先出个 15 秒预告试水（可行性原型）→ 发一个粗剪版（alpha 原型）→ 发给朋友看（beta 原型）→ 定剪成片（候选发布版）。
5. **部署**：上传平台、过审、上线。

关键在「**迭代**」两个字：不是一次做完，而是**一轮一轮地做、每轮都能看到能跑的东西**。

### 关键概念逐个讲透

#### 1）移动应用的开发过程与 5 个迭代阶段（识记，必背）

| 阶段 | 做什么 | 记忆要点 |
| --- | --- | --- |
| ① 需求分析 | 搞清楚要做成什么样 | 起点 |
| ② 设计 | 包括**体系结构设计、导航设计、界面设计以及内容设计** | 4 个「设计」 |
| ③ 开发 | 开发人员为移动软件编码，包含**功能性**以及**非功能性**部分 | 两种部分 |
| ④ 稳定 | 用 4 级递进的原型把软件逐步「稳住」 | 4 个原型 |
| ⑤ 部署 | 产品稳定后由**应用商店**审查，并可出售和下载 | 应用商店 |

**稳定阶段的 4 级原型（识记，选择题爱考顺序）**：

1. **可行性原型**：作为一个概念证明，证明整个应用程序中也许只存在一条完整的逻辑路径。
2. **alpha 原型**：包含**最小可行产品**的功能。
3. **beta 原型**：已基本完成并包含大部分通过测试的功能。
4. **候选发布版**：包含所有必需的功能，所有计划的测试均已完成。

> 记忆口诀：**可行 → alpha → beta → 候选发布**，一级比一级「功能更全、测试更完整」。

#### 2）移动应用界面设计需要考虑的问题（领会）

教材先说一句总纲：**可访问性是一个重要的设计问题**，采用以用户为中心的设计时必须考虑在内。

为了满足利益相关者对于可用性的期望、评估设备的外部表现，开发者应该了解以下 3 个问题：

1. 用户界面在多个应用中是否**一致**？
2. 设备是否能与不同的**网络服务**相互协作？
3. 在目标市场中，就利益相关者的价值观而言，设备是否能被**大众所认可**？

#### 3）用于移动应用界面设计的 3 种模型（识记，选择题必考）

| 模型 | 关注什么 | 一句话理解 |
| --- | --- | --- |
| **平台模型** | 设备本身的特性 | 手机是「什么硬件」 |
| **表示模型** | 界面的表现形式 | 界面「长什么样」 |
| **任务模型** | 用户要完成的任务 | 用户「要干什么」 |

> 教辅例题：下列选项中，可用于移动应用的界面设计的是 → 答「**任务模型**」。干扰项「内容模型」「接口模型」「设计模型」都不是这 3 种模型的名字。

#### 4）3 种设计移动应用程序的方法（领会，注意与上一条区分）

以下是由经验丰富的技术人员提出的 3 种设计移动应用程序的方法：

1. **使用场景**：开发者必须考虑相关环境因素（位置、用户和设备）及相关场景之间的转换（如用户从卧室移动到厨房，或使用手指代替手写笔）。
2. **观察不同应用者**：这是一种广泛使用的方法，用来收集所设计的软件产品具有代表性的用户信息。
3. **低保真度的纸质原型**（如卡片或便条）：在用户界面设计中，这是一种**成本效益高**的可用性评估方法，可以在**任何编程之前**使用。

> 一句话区分：**「3 种模型」是工具（平台/表示/任务），「3 种方法」是做法（场景/观察/纸质原型）。**

#### 5）在移动应用的设计中应该尽量避免的问题（领会，多选题/简答题）

一共 8 项，建议按「功能—风格—性能—交互—帮助」归类背：

| 归类 | 要避免的问题 |
| --- | --- |
| 功能 | 功能复杂 |
| 风格 | 前后矛盾、设计过度、废话连篇 |
| 性能 | 加载过慢 |
| 交互 | 非标准的交互 |
| 帮助 | 对常见问题的回答和帮助（即：连常见问题的答案和帮助都没有） |

完整 8 项：**功能复杂、前后矛盾、设计过度、加载过慢、废话连篇、非标准的交互、对常见问题的回答和帮助**。

### 考试这样考

- **单选题（顺序/名称）**：教辅例题「正确的移动应用开发的 5 个迭代阶段是」→ 答「**需求分析、设计、开发、稳固、部署**」。
  - 干扰项：A「可行性分析、需求分析、设计、测试、维护」（这是传统软件生命周期）；B「需求分析、设计、编码、测试、维护」；C「需求分析、设计、编码、稳固、部署」（把「开发」写成「编码」）。
- **单选题（模型）**：见上面「任务模型」那一题。
- **简答题**：「移动应用的设计包括哪些内容？」→ 体系结构设计、导航设计、界面设计以及内容设计。
- **简答题**：「移动应用开发采用什么模型？分几个阶段？」→ 敏捷开发模型，5 个迭代阶段。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 5 个阶段写成「需求、设计、编码、测试、维护」 | 正确是**需求分析、设计、开发、稳定、部署**；「编码」应为「开发」，「测试/维护」不在这 5 个里 |
| 把「稳定阶段」漏掉 | 稳定阶段是移动应用特有的，且含 4 级原型 |
| 把 3 种模型与 3 种方法搞混 | 模型 = 平台/表示/任务；方法 = 使用场景/观察不同应用者/低保真度纸质原型 |
| 以为「低保真度纸质原型」很贵 | 教材说它**成本效益高**，且可在任何编程之前使用 |
| 把「稳定性原型」顺序记成 beta → alpha | 顺序是可行性原型 → alpha → beta → 候选发布版 |

## 第 3 节　移动计算环境与环境感知 App

### 一句话定义

移动应用**依赖于服务计算和云计算环境**：这两种计算模式让大规模分布式应用可以更容易、更经济地创建在不同设备（笔记本计算机、手机、平板电脑）上，也把资源外包出去，减轻移动设备有限资源对软件运行的影响。

**云计算的体系结构有三层，每一层都可以称为一个服务，控制程度由弱到强：软件即服务（SaaS）→ 平台即服务（PaaS）→ 基础设施即服务（IaaS）。**

### 用「日常生活比喻」来理解

把「做一顿饭」外包出去，有 3 种由浅到深的偷懒方式：

| 云服务层次 | 生活比喻 | 你负责什么 | 别人负责什么 | 你的控制程度 |
| --- | --- | --- | --- | --- |
| **SaaS** 软件即服务 | 直接**点外卖** | 只管吃 | 厨房、厨师、菜谱全由第三方服务提供商提供 | **最弱** |
| **PaaS** 平台即服务 | **租一个共享厨房** | 自己配菜、自己炒 | 灶台、水电、场地由平台提供 | 中等 |
| **IaaS** 基础设施即服务 | **租一间空铺面** | 装修、买设备、定菜单全自己来 | 只提供房子（虚拟计算资源） | **最强** |

所以「由强控制到弱控制」的顺序是：**IaaS → PaaS → SaaS**（这是教辅例题的答案方向，别记反）。

### 关键概念逐个讲透

#### 1）移动计算环境：服务计算与云计算（识记的理解基础）

- 这两种模式可以让**资源外包**，或把信息技术管理的信息**转移给服务提供商**；
- 目的是**减轻某些移动设备上有限的资源对软件运行的影响**（对应第 1 节的「计算和存储限制」难题）。

#### 2）云计算的 3 层体系结构（识记，必考）

| 层次 | 教材定义 | 关键词 |
| --- | --- | --- |
| **软件即服务（SaaS）层** | 包括由**第三方服务提供商提供的软件构件和应用** | 拿来就用 |
| **平台即服务（PaaS）层** | 提供了一个**协同开发平台**，协助**地理上分散**的团队成员进行设计、实施和测试 | 协同开发 |
| **基础设施即服务（IaaS）层** | 为云计算提供**虚拟计算资源**（存储、处理能力、网络连接） | 虚拟资源三件套 |

> 教材原文的顺序是先说「控制程度由弱到强」，然后依次介绍 SaaS、PaaS、IaaS——也就是说：**SaaS 控制最弱，IaaS 控制最强**。

#### 3）环境感知的含义（大纲要求理解，教辅未展开）

教辅在「第四节 环境感知 APP」标了「（不考）」，但**考纲把「移动计算环境与环境感知 App」列为课程内容 3**，且「学习目的与要求」明确要求理解**环境感知的含义**。因此这里只能给教材留下的线索：

- 教材在第 1 节讲「用户界面的限制以及传感器与设备之间交互的复杂性」时写道：**触摸、手势、摄像等和基于环境感知的使用场景**；
- 教材在第 1 节讲「环境的有效利用」时写道：**用户期望移动 App 能够基于设备的物理位置及其可利用的网络功能提供个性化的用户体验**。

**由此可以把握的要点（推断，非教材原文）**：环境感知 = App 能「感知」自己所处的环境（位置、时间、网络、设备状态、用户情境等），并据此自动调整自己的行为、提供个性化服务。

> ⚠️ 备考建议：这一条尽量按「位置 + 网络 + 传感器 → 自动调整行为、个性化体验」的大意作答，**不要硬背某个定义**；如果考纲外还有正文教材，务必回正文确认原话。

### 考试这样考

- **单选题（顺序）**：教辅例题「移动计算环境的层次按照由强控制到弱控制的顺序，三个层次依次为」→ 答「**基础设施即服务层、平台即服务层、软件即服务层**」。
- **单选题（对应关系）**：问「提供虚拟计算资源（存储、处理能力、网络连接）的是哪一层」→ IaaS；问「提供协同开发平台」→ PaaS；问「提供软件构件和应用」→ SaaS。
- **简答题**：可能问「云计算的三层体系结构分别是什么」，直接写 3 层名称 + 各自定义。

### 易错点

| --- | --- |
| 「控制程度由强到弱 = SaaS、PaaS、IaaS」 | 反了：**SaaS 最弱、IaaS 最强** |
| 「PaaS 提供虚拟计算资源」 | 提供虚拟计算资源的是 **IaaS**；PaaS 提供的是**协同开发平台** |

| 认为「环境感知 APP 不考，整节可以跳过」 | 教辅写「不考」，但**考纲把这一节列为课程内容 3**，范围以考纲为准 |

## 第 4 节　WebApp 设计

### 一句话定义

**WebApp 是运行在浏览器/网络环境中的那类应用**；WebApp 设计就是围绕「界面、美学、内容、体系结构、导航、构件」6 个方面，把「用户在浏览器里看到和用到的东西」设计出来。

WebApp 设计的内容（识记）= **界面设计、美学设计、内容设计、体系结构设计、导航设计、构件设计**。

### 用「日常生活比喻」来理解

把 WebApp 想成**一座购物中心**：

| WebApp 设计 | 商场里的对应物 |
| --- | --- |
| 界面设计 | 大门、大堂、总服务台（用户从这里进入内容和功能） |
| 美学设计 | 装修风格：留白、灯光、视线动线 |
| 内容设计 | 每家店铺卖什么货（内容对象） |
| 体系结构设计 | 楼层分区与动线规划（内容体系结构 + WebApp 体系结构） |
| 导航设计 | 指示牌体系：楼层导览图（NSU）、指示牌（WoN）、路口（NN） |
| 构件设计 | 标准店铺单元：既能陈列商品（内容），也能提供服务（功能） |

**MVC 就像商场里的三类人**：**模型**是仓库和账本（存着所有内容和处理逻辑），**视图**是顾客看到的一切（界面），**控制器**是大堂经理（安排谁能进仓库、谁先看哪个界面）。

### 关键概念逐个讲透

#### 1）WebApp 界面的目标（识记，3 条）

1. 建立**一致性的窗口**，用户由此进入界面提供的内容和功能；
2. 通过一系列与 WebApp 的交互以**指导用户**；
3. **组织用户可用的导航选项和内容**。

> 第 3 条展开成一个重要原则：为了提供导航选项，可以选择网页中**位置固定的导航菜单**，可以选择用户**容易识别和理解的图标**作为导航元素，也可以选择**链接到内容主题或 WebApp 功能的图像**。要特别注意：**在内容层次的每个级别上都应提供一种或多种导航机制**。

#### 2）导航元素（识记）

**导航元素也称导航通路（WoN）**，包括：**菜单、按钮、链接、操作栏**等。

配套的 3 个缩写必须分清（领会「导航设计的内容和方法」）：

| 缩写 | 全称 | 含义 |
| --- | --- | --- |
| **NSU** | 导航语义单元 | 一组导航元素，或者说**信息和相关的导航结构的集合**；描述每个用例的导航需求，显示每个角色如何在内容对象或 WebApp 功能之间移动 |
| **WoN** | 导航通路 | 就是**导航元素**：菜单、按钮、链接、操作栏等 |
| **NN** | 导航节点 | 由导航链接连接起来的节点；某些情况下，导航链接可能就是另一个 NSU |

**导航设计的做法**：先考虑**用户层次**和为每一类**用户角色**创建的相关**用例**；每一类角色使用 WebApp 的方式不同 → 导航要求不同；用例会定义一组类（含一个或多个内容对象，或含 WebApp 功能）。最终可以把 WebApp 的总体导航结构组织为 **NSU 的层次结构**。

> 教辅例题：导航语义单元是 → 答「**信息和相关的导航结构的集合**」。干扰项「一个导航页面」「一组关于导航信息的集合」「一组导航选项」都不准确。

#### 3）美学设计的参考原则（领会，6 条）

1. 适当留下**空白空间**；
2. **重视内容**；
3. 按照**从左上到右下**的顺序组织布局元素；
4. 按**导航、内容和功能**安排页面的布局；
5. **不要通过滚动条扩展空间**；
6. 设计页面布局时，要考虑**分辨率和浏览器窗口的尺寸**。

> 教辅例题：WebApp 界面设计中的美学设计**不要**关注的是 → 答「**用户界面的响应时间**」。因为 6 条原则里谈的是功能、内容、布局，没有响应时间。

#### 4）内容设计（领会 + 识记「WebApp 设计的内容」）

在 WebApp 设计中，**内容对象与传统软件中的数据对象关系更加紧密**。内容对象具有两类属性：

- 特定的**内容信息**的属性（通常在 WebApp 建模期间定义）；
- 指定为**设计成分**的实现属性。

#### 5）体系结构设计（领会，注意两个「体系结构」的区分）

体系结构设计与「已建立的 WebApp 目标、展示的内容、将要访问它的用户、已经建立的导航原则」紧密相关。设计者必须确定两样东西：

| 名称 | 关注点 | 一句话 |
| --- | --- | --- |
| **内容体系结构** | 内容对象（如网页的组成对象）的**表现**和**导航的组织方式** | 内容怎么摆、怎么串 |
| **WebApp 体系结构** | 应用以什么**组织方式**来管理用户交互、操纵内部处理任务、实现导航及展示内容 | 系统怎么运转 |

#### 6）MVC 体系结构（领会，选择题高频）

**模型-视图-控制器（MVC）体系结构是一种流行的 WebApp 体系结构模型，它将用户界面与 WebApp 的功能及信息内容分离。**

| 部件 | 职责（教材表述） |
| --- | --- |
| **模型**（模型对象） | 包括应用的**所有详细内容和处理逻辑**，还包括所有内容对象、对外部数据或信息源的访问，以及应用的特定处理功能 |
| **视图** | 包括所有**界面的特定功能**，并能够表示内容和处理逻辑，包括所有内容对象、对外部数据或信息源的访问，以及最终用户所需要的所有处理功能 |
| **控制器** | **管理对模型和视图的访问，并协调两者间的数据流**；在 WebApp 中，视图由控制器进行更新，更新数据来自基于用户输入的模型 |

> 教辅例题：下列关于 MVC 模式的叙述中，正确的是 → 答「**MVC 将应用程序划分为视图、控制器、模型三个核心部件**」。
> 干扰项 B「将系统分为界面层、业务逻辑层和数据访问层」是三层架构的说法，不是 MVC。

#### 7）构件设计（识记「WebApp 构件」+ 领会「WebApp 构件设计」）

**WebApp 构件的两层含义**：

1. 首先是**定义良好的聚合功能**，为最终用户处理内容，或提供计算及数据处理功能；
2. 其次是**内容和功能的聚合包**，提供最终用户所需的功能。

因此，WebApp 的**构件级设计通常包括内容设计元素和功能设计元素**。

> 大纲难点「基于构件的移动应用的建模」就落在这里：想清楚「一个构件既是内容包、又是功能包」，建模时就要同时建内容模型和功能模型。

#### 8）影响移动 App 质量的 6 个重要因素（领会，必背）

最终用户对于移动 App 的满意度取决于 6 个重要的质量因素：

**易用性、功能性、可靠性、时效性、可维护性及可移植性。**

此外，**安全性、可用性、可扩展性、投放市场的时间、内容的质量**作为**扩展的质量属性**，也用于评价移动应用的质量。

> 口诀：**易功可时维移**（易用性、功能性、可靠性、时效性、可维护性、可移植性）。扩展 5 项：安、可、扩、时间、内容质量。

#### 9）保证 WebApp 质量的必要步骤 / 导语（单元）元素（识记，教辅未展开）

考纲「识记」里还有两个词条：**保证 WebApp 质量的必要步骤**、**导语（单元）元素**。

- 教辅正文**没有**出现「导语（单元）元素」这个说法，也没有把「保证质量的必要步骤」单列成条目；
- 为避免误导，本讲义**不给猜测性定义**。可确定的相关内容是：WebApp 设计的内容（6 个方面）、WebApp 界面的目标（3 条）、以及第 5 节「WebApp 测试」的 10 项工作与测试策略。
- 复习时请以正文教材为准，见文末「大纲与教辅的差异」表。

### 考试这样考

- **单选题（组成部分）**：「WebApp 设计的内容不包括以下哪项」——把 6 个方面（界面、美学、内容、体系结构、导航、构件）记住就够。
- **单选题（MVC）**：见上面教辅例题，答案是「MVC 将应用程序划分为视图、控制器、模型三个核心部件」。
- **单选题（美学/NSU）**：见上面两道教辅例题。
- **简答题**：「影响移动 App 质量的 6 个重要因素是什么？」→ 易用性、功能性、可靠性、时效性、可维护性、可移植性。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 认为「MVC 的控制器负责显示内容」 | 控制器管**访问与数据流协调**；**视图**负责界面与表示 |
| 把「内容体系结构」和「WebApp 体系结构」当成一回事 | 前者管内容对象的表现与导航组织；后者管应用如何组织交互、处理、导航与展示 |
| 把 NSU 说成「一个导航页面」 | NSU 是**信息和相关导航结构的集合**，是语义单元不是页面 |
| 导航元素写成「菜单、按钮、图标、动画」 | 教材列的是**菜单、按钮、链接、操作栏** |

## 第 5 节　移动软件的测试

### 一句话定义

移动软件的测试 = **在不稳定的网络、五花八门的设备、真实的用户场景下，验证移动 App 的功能、性能、安全、体验是否达标的一整套测试活动**（包括 WebApp 测试、安全性测试、性能测试、实时测试、人工智能子系统测试、虚拟环境测试、文档测试等）。

### 用「日常生活比喻」来理解

把移动 App 测试想成**新车上市前的路试**：

- 只在实验室里跑一圈不算（→ 要**自然环境测试**，在全球各种网络环境、真实设备、真实条件下测）；
- 要拉上高原、跑烂路（→ **压力测试**：把负载加到强度极限）；
- 要模拟满载爬坡（→ **负载测试**：多种负载级别和组合下测）；
- 要试急刹、爆胎后能不能恢复（→ **恢复测试 / 警报和异常条件**）；
- 要请真实司机试驾（→ **α 测试、β 测试**）；
- 要检查说明书有没有写错（→ **文档测试**）。

### 关键概念逐个讲透

#### 1）移动软件测试的目标（识记）

移动 App 测试的总体目标是：在**真实的设备、真实的网络、真实的用户条件下**，验证 App 是否满足功能与非功能需求，并**尽早发现缺陷**。教材把目标落实为两句话：

- **在不受控制的实际测试条件下进行测试**（准则 2）；
- **测量性能只在无线通信和用户负载的实际条件下进行**（准则 7）。

#### 2）移动 App 测试应遵循的准则（领会，7 条，选择题易考「不属于」）

1. 在进行确定瓶颈的测试之前要**了解网络和设备环境**；
2. 在**不受控制的实际测试条件**下进行测试；
3. 选择适当的**自动化测试工具**；
4. 利用**加载设备平台矩阵法**确定最为关键的硬件平台测试组合；
5. **至少检查一次在所有可能的平台上的端到端功能流**；
6. 使用**实际设备**进行性能测试、图形用户界面（GUI）测试和兼容性测试；
7. **测量性能只在无线通信和用户负载的实际条件下进行**。

#### 3）移动 App 测试策略（领会，7 种）

| 策略 | 测什么 |
| --- | --- |
| ① 用户体验测试 | 用户在**开发过程早期**就参与进来，确保 App 在支持的所有设备上达到利益相关者对**易用性和可访问性**的要求 |
| ② 设备兼容性测试 | 验证 App 是否可以在**所有必需的硬件和软件组合**上正常工作 |
| ③ 性能测试 | 检查移动设备特有的**非功能性需求**（下载时间、处理器速度、存储容量、电源可用性） |
| ④ 连接性测试 | 确保 App 可以访问需要的网络或 Web 服务，并且**可以容忍网络很差或访问被中断** |
| ⑤ 安全性测试 | 确保 App 不会损害用户的**隐私或安全需求** |
| ⑥ 自然环境测试 | 在**全球各种网络环境**中，在实际的用户设备和真实的条件下进行测试 |
| ⑦ 认证测试 | 确保 App 符合**分发机构**制定的标准 |

#### 4）与用户体验相关的测试内容（识记，4 项）

**① 手势测试**
使用自动化工具测试触摸或手势界面操作是很难的：屏幕大小和分辨率以及之前的用户操作都会影响屏幕上对象的位置，使得准确的手势测试变得困难；即使进行了测试，手势也很难被准确记录下来进行重现。测试人员需要开发测试框架程序来模拟手势，问题是这样**既昂贵又费时**。
用移动 App 测试手势时要考虑**屏幕差异**，应确保手势符合为移动设备或平台设定的标准和环境。

**② 虚拟键盘输入**
激活虚拟键盘时可能会**遮挡部分显示屏**，因而应测试 App 以确保用户输入时**重要的屏幕信息不会被隐藏**。预测技术（即自动完成部分词语的输入）往往使用虚拟键盘来帮助用户加快输入。

**③ 语音输入和识别**
来自**噪声环境的干扰**会妨害各种形式语音的输入和处理；测试语音输入和识别的质量与可靠性时，应考虑**环境条件和个体语音变化**。

**④ 警报和异常条件**
当 App 在实时环境中运行时，有许多因素会影响它的行为，例如：丢失无线网络信号，传入文本消息、电话呼叫，或接收到日历警报。
**恢复测试**是一种系统测试，它**强制使软件以各种方式失效，并验证是否能正确执行恢复操作**：如果恢复由系统自动执行，则评估**重新初始化、检查点机制、数据恢复和重新启动**的正确性；如果需要人工干预，则评估**平均修复时间**是否在可接受范围内。

> 教辅例题：关于手势测试，下列叙述正确的是 → 答「**手势测试需要考虑移动设备输入屏幕的大小差异**」。
> 干扰项错在：A「对所有移动设备都必须」（无触摸屏的设备不必须）；B「自动化工具效率高」（教材说很难且昂贵费时）；D「不影响可访问性」（会影响）。

#### 5）需要对 WebApp 进行的测试（领会，10 项）

1. 对 WebApp 的**内容模型**进行评审，以发现错误；
2. 对**接口模型**进行评审，保证其适合所有的用例；
3. 评审 WebApp 的**设计模型**，发现导航错误；
4. 测试**用户界面**，发现显示和导航机制中的错误；
5. 对每个**功能构件**都要进行单元测试；
6. 对贯穿体系结构的**导航**进行测试；
7. 在各种不同的**环境配置**下实现 WebApp，并测试兼容性；
8. 进行**安全性测试**，试图攻击 WebApp 或其所处环境的弱点；
9. 进行**性能测试**；
10. 通过**可监控的终端用户群**对 WebApp 进行测试，评估他们与系统的交互结果是否有错误。

#### 6）内容测试的 3 个目标（识记）+ 内容测试方法

1. 发现基于文本的文档、图形表示和其他媒体中的**语法错误**（如拼写错误、语法错误）；
2. 发现当导航发生时所展现的任何内容对象中的**语义错误**（即信息的准确性和完备性方面的错误）；
3. 发现展示给最终用户的内容在**组织或结构方面**的错误。

**内容测试方法**（领会）：对**内容模型进行评审**（第 5 节 10 项工作的第 1 条），逐项检查语法、语义、组织结构；并与界面测试、导航测试结合进行。

#### 7）界面测试的策略与工作内容（领会）

**总体测试策略 2 条**：

1. 发现与特定的**界面机制**相关的错误（例如，未能正确执行菜单命令）；
2. 发现界面实现**导航语义方式**的错误、WebApp 的功能性错误或内容显示错误。

**必须进行的测试工作 5 项**：

1. 对**界面要素**进行测试，确保设计规则、美学和相关的可视化内容对用户有效，且没有错误；
2. 采用与**单元测试类似的方式**测试单个界面机制；
3. 对于特殊的用户类，在**用例或导航语义单元**的环境中测试每一种界面机制；
4. 对**所有界面**进行测试，发现界面的语义错误及可用性测试；
5. 在**多种环境（如浏览器）**中对界面进行测试，确保其兼容性。

#### 8）导航测试的内容（识记）+ 方法

移动应用的导航测试要测试的内容有 2 条：

1. 确保允许 WebApp 用户经由 WebApp 游历的**机制都是功能性的**；
2. 确认**每个导航语义单元都能够被合适的用户类获得**。

**导航测试的方法**（领会）：评审**设计模型**发现导航错误（10 项工作第 3 条）+ 对**贯穿体系结构的导航**进行测试（第 6 条）+ 在**用例/NSU 环境**中测试界面机制。

#### 9）安全性测试（领会）

- **目的**：安全性测试用于探查软件在安全性方面所存在的弱点（客户端环境、数据在客户端与服务器之间传输时的网络通信、服务器端环境，每个环节都可能受到攻击）。**安全性测试的任务是发现可能会被怀有恶意的人利用的弱点。**
- **解决安全性问题的 4 种技术**：**防火墙、鉴定、加密和授权**。应设计安全性测试探查每种安全性技术来发现安全漏洞。

#### 10）性能测试（领会）

- **目的（两条）**：一是了解系统如何对**负载**（用户的数量、事务的数量或总的数据量）做出反应；二是**收集度量数据用以促成设计的改善**，从而使性能得到提高。
- 性能测试的目的是**在集成系统环境中测试软件运行时的性能**；它贯穿整个测试过程的所有步骤，即使在单元测试阶段也可以评估单个模块的性能，但**直到所有系统元素都完全集成之后，才能确定系统的真正性能**。
- **影响性能的因素**：服务器端资源缺乏、不合适的网络带宽、不适当的数据库容量、操作系统不够强大、设计不良的 WebApp 功能，以及可能导致客户端和服务器性能下降的其他硬件或软件问题。

#### 11）负载测试与压力测试（识记，最爱考区分）

| 项目 | 负载测试 | 压力测试 |
| --- | --- | --- |
| 定义 | 在**多种负载级别和多种组合**下，对**真实世界的负载**进行测试 | 将负载**增加到强度极限**，以此来确定 App 环境能够处理的**容量** |
| 目的 | 确定 WebApp 和其服务器环境**如何响应不同的负载条件** | 在**极限运行条件**下力图**查找错误** |
| 附加作用 | —— | 提供一种机制，在**不损害安全性**的情况下观察 App 的运行水平是否会降低 |

#### 12）实时测试（领会）

- **必要性**：许多移动和实时应用程序具有**时间依赖性和异步性**，测试用例设计人员不仅要考虑传统的测试用例，还要考虑**事件处理（即中断处理）、数据的处理时间以及处理数据任务（进程）的并行性**。
- **方法**：许多开发商主张进行**自然环境测试**——在用户的本地环境中使用移动 App 资源的**生产发布版本**进行测试；伴随着 App 的演变，自然环境测试要**敏捷地响应变更**。

#### 13）测试人工智能子系统（领会，3 类）

| 类型 | 性质 | 要点 |
| --- | --- | --- |
| **静态测试** | 一种软件**验证**技术，关注**评审**而不是可执行的测试 | 重要的是确保**专家同意**开发人员在人工智能子系统中表示及使用信息的方式 |
| **动态测试** | 一种**确认**技术，通过测试用例来**运行源代码** | 目的是证明人工智能系统**符合专家指定的行为** |
| **基于模型的测试（MBT）** | 一种**黑盒测试**技术 | 使用**需求模型（特别是用户故事）**中的信息作为生成测试用例的基础；很多情况下使用形式化表示方法，如 **UML 状态图**作为测试用例设计的基础 |

> **基于模型的测试步骤**：注意两个关键词「需求模型/用户故事 → 生成测试用例」「UML 状态图作为设计基础」。教辅没有把步骤逐条列出（见文末差异表），答题时抓住「建模型 → 由模型生成用例 → 执行验证」的主线。

#### 14）虚拟环境测试与 α、β 测试（领会，必考对比）

虚拟环境的测试包括 3 类：**可用性测试、可访问性测试、可玩性测试**。

| 测试 | 评价什么 |
| --- | --- |
| 可用性测试 | 用户在多大程度上能够与 App 进行**有效交互**，以及 App 在多大程度上指导用户行为、提供有意义的反馈并坚持一致的交互方法 |
| 可访问性测试 | 验证**所有人**均可使用计算机系统，而不考虑任何用户的特殊需求；通常需要考虑的特殊需求是**视觉、听觉、运动和认知障碍** |
| 可玩性测试 | 确认用户/玩家进行游戏或模拟的**有趣程度**，最初被认为是电子游戏开发的一部分 |

**α 测试与 β 测试**：

| 项目 | α 测试 | β 测试 |
| --- | --- | --- |
| 地点 | **开发者的场所** | **一个或多个最终用户场所** |
| 参加者 | 有代表性的最终用户 | 最终用户 |
| 开发者是否在场 | **在场**（站在用户后面观看并记录错误和使用问题） | **通常不在场** |
| 环境 | **受控**环境 | **不为开发者控制**的「现场」环境 |
| 结果处理 | 开发者记录错误和使用问题 | 最终用户记录所有问题（现实存在的或想象的）并**定期报告**给开发者；开发者修改软件后准备发布 |

#### 15）文档测试（领会）

文档测试可分为**两个阶段**：

1. 第一阶段：**技术评审**，检查文档编辑的清晰性；
2. 第二阶段：**现场测试**，结合实际程序使用文档。

> **文档测试可使用的测试技术**：教辅未列出具体技术清单（见文末差异表）；可结合第一节的「文档属于软件的一部分」以及第 5 章确认测试中「软件配置复审」的思路理解——文档的清晰性靠**评审**，准确性靠**结合程序实际使用**来验证。

### 考试这样考

- **单选题（区分负载/压力）**：「将负载增加到强度极限以确定 App 环境能够处理的容量」属于 → 压力测试。
- **单选题（测试准则/策略）**：「下列关于移动 App 测试的叙述中，错误的是」——注意「只能在实验室受控条件下测试」「只测一台设备即可」这类选项都是错的。
- **单选题（α/β）**：「开发者不在场的测试是」→ β 测试。
- **单选题（安全性技术）**：「为移动应用安全性可采取的技术不包括」→ 防火墙、鉴定、加密、授权之外的都错（如「压缩」「负载均衡」）。
- **简答题**：
  - 「移动应用的导航测试要测试哪些内容？」→ 2 条。
  - 「为了移动应用的安全性可采取的技术有哪些？」→ 4 种。
  - 「导致移动应用性能低的原因有哪些？」→ 5 类因素。
  - 「负载测试和压力测试的任务分别是什么？」→ 见上表。
  - 「WebApp 内容测试的 3 个目标是什么？」→ 语法、语义、组织结构。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 把负载测试与压力测试搞混 | **负载测试**：多种负载级别和组合，看**响应**；**压力测试**：加到**强度极限**，找**错误**、定**容量** |
| 以为手势测试必须用自动化工具 | 教材说自动化测手势**很难、昂贵又费时**；要考虑屏幕差异 |
| 认为 α 测试是「用户自己在家测」 | α 测试在**开发者场所、受控环境**、开发者**在场**；β 测试才是用户场所、开发者不在场 |
| 「可用性测试 = 可访问性测试」 | 可用性 = 有效交互；可访问性 = **所有人**都能用（视觉、听觉、运动、认知障碍） |
| 把安全性测试的技术写成「防火墙、备份、加密、授权」 | 教材是**防火墙、鉴定、加密、授权**（没有备份） |
| 认为性能测试只能整体做完再测 | 性能测试**贯穿所有步骤**，单元测试阶段也可评估单模块性能；只是**真正性能**要等全部集成后才能确定 |
| 认为 AI 子系统的静态测试要运行程序 | 静态测试关注**评审**；**动态测试**才运行源代码 |

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 把移动应用 5 个迭代阶段写成传统的「需求—设计—编码—测试—维护」 | 背成**需求分析、设计、开发、稳定、部署**，其中「稳定」是移动开发特有的 |
| 把「3 种模型」和「3 种设计方法」混为一谈 | 模型 = 平台/表示/任务；方法 = 使用场景/观察不同应用者/低保真度纸质原型 |
| 云计算 3 层的控制程度记反 | 控制程度**由弱到强**：SaaS → PaaS → IaaS；由强到弱则倒过来 |
