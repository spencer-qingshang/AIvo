# 第 1 章 软件工程概述

## 本章要解决的问题

1. 软件究竟包含什么，为什么代码不能代表完整的软件？
2. 为什么会出现软件危机，软件工程怎样应对？
3. 软件从需求到上线、维护，要经历哪些活动？
4. 面对不同项目，怎样选择软件过程模型？
5. 敏捷开发、Scrum 和 XP 分别解决什么问题？

## 一页总览

`软件 = 程序 + 数据 + 相关文档`

`软件工程 = 从管理和技术两方面，研究如何更好地开发和维护软件`（基本思想：按工程化的原则和方法组织软件开发）

`软件过程 = 需求分析 -> 设计和实现 -> 测试 -> 演进`（考纲口径：**4 种基本活动**，第 4 种是演进，不是维护）

`软件过程模型 = 瀑布 / 原型 / 螺旋 / 统一过程`（四种模板，按需求明确度与风险选）

| 场景关键词 | 优先想到的概念 |
| --- | --- |
| 延期、超支、缺陷多、难维护 | 软件危机 |
| 需求明确、变化少、顺序推进 | 瀑布模型 |
| 用户说不清需求、先做样稿 | 原型模型 |
| 项目风险高、反复分析风险 | 螺旋模型 |
| 面向对象、迭代、增量交付 | 统一过程模型 |
| 短周期交付、持续反馈、需求可变 | 敏捷开发 |
| 修复已发现的缺陷 | 改正性维护 |
| 适应系统外部环境或政策变化 | 适应性维护 |
| 新增功能、改善体验或性能 | 完善性维护 |
| 重构、补文档以降低未来风险 | 预防性维护 |

## 1.1 软件

### 1. 定义

软件是**程序、数据及其相关文档的完整集合**。在计算机系统中，它是与硬件**相互依存**的另一部分。

三个组成部分都要能单独说清：

- **程序**：实现特定功能的**指令序列**。例如选课系统的前后端代码、安装包。
- **数据**：使程序能**正常操纵信息的数据结构**。例如学生信息、课程信息、选课记录、初始化数据。
- **相关文档**：与程序**开发、维护和使用**有关的图文材料。例如需求分析文档、设计文档、测试文档、维护记录、用户手册、API 文档。

只有代码通常不算完整的软件交付：没有数据，系统可能无法正常运行；没有文档，用户和后续维护人员很难正确使用、部署或修改系统。

> **背景补充**：「软件」一词在**广义上**指除设备、车辆、原材料之外的人的素质、技术水平、管理法规等无形因素；在**计算机专业领域**常被等同于程序；只有在**软件工程领域**才取「程序 + 数据 + 文档」这个完整定义。考试问「软件工程领域中软件的定义」，答完整集合那一条。

### 2. 软件与硬件的主要区别

| 角度 | 软件 | 硬件 |
| --- | --- | --- |
| 产生方式 | 以开发和设计为主 | 以制造和装配为主 |
| 复制成本 | 首个版本开发成本高，复制成本低 | 每增加一件产品都需要材料和制造成本 |
| 失效方式 | 不会因运行次数而物理磨损，但会因环境变化、补丁累积或设计老化而退化 | 会磨损、老化和损坏 |
| 抽象性 | 更强 | 较弱 |
| 成本控制 | 开发成本**更难**控制 | 相对容易控制 |
| 标准化程度 | 常因业务不同而高度定制 | 零件、接口通常有较高标准化程度 |
| 社会因素 | 功能常涉及机构的组织、体制及管理方式 | 牵涉较少 |

软件特点共六条，全部源于同一句话：**软件靠「设计和开发」，硬件靠「制造和装配」**。

### 3. 例子

学校选课系统：

- 程序：选课、退课、容量检查的代码。
- 数据：学生、课程、选课记录。
- 文档：管理员部署说明、学生使用说明、接口文档。

### 4. 易错点

- “安装包”主要是程序，不等于完整软件。
- “选课记录”是数据，不是文档。
- “部署说明”和“API 文档”是文档，不是程序。
- 软件的开发成本比硬件**更难**控制（常被反过来说成“容易控制”）。
- 软件不是被用坏的，是**退化**掉的。

## 1.2 软件工程

### 1. 定义

> **软件工程**是从**管理和技术两方面**研究如何更好地**开发和维护**计算机软件的一门学科。
> **基本思想**：按**工程化的原则和方法**组织软件开发。

定义里有四个要点，一个都不能丢：

- **两方面**：管理和技术——不只研究技术；
- **两个动词**：开发和**维护**——维护占软件生命周期很大比重；
- **一门学科**：它是学科，不是某个工具或流程；
- **工程化**：像造桥盖楼一样干活——先有图纸（需求、设计），再施工（编码），最后验收（测试），全程有规范、有文档、可检查。

一句话：**工程化 = 把“手艺”变成“工序”。**

### 2. 软件危机

**软件危机**指软件开发与维护中遇到的一系列严重问题。典型表现有六项：

1. 软件开发**缺乏计划性**；
2. 软件**需求不够充分**；
3. 缺乏软件开发**过程的规范**；
4. 软件开发的**成本和进度难以控制**；
5. 没有评测软件**产品质量的标准和方法**；
6. 软件**难以维护**。

> **高频陷阱**：“软件的实现缺乏好的算法”**不属于**这六项。危机的症结在管理、需求、过程、标准与维护，不在算法水平。

危机的成因：硬件进步、高级程序语言出现，应用领域迅速扩大，需要开发的软件规模与功能差异极大，而开发方式仍停留在“个人手艺”阶段——**不是技术不够先进，而是工程化程度不够**。典型现场是延期、超支、缺陷多、维护难。

### 3. 研究领域

软件工程研究这些问题：

1. 软件开发的过程应该依次包含哪些步骤；
2. 如何了解并描述用户对功能和性能等方面的需求；
3. 如何进行合理的软件设计并描述设计方案；
4. 如何实现编程，使软件质量更好、更容易维护；
5. 如何进行软件测试，保证功能正确、隐藏的错误尽可能少；
6. 如何进行软件项目管理，保证项目进展顺利。

记忆抓手：**过程 → 需求 → 设计 → 实现 → 测试 → 管理**，是一条完整的生产线。

### 4. 系统化、规范化、可度量

工程化的三个落脚点，用来判断某个做法体现了哪一点：

| 特点 | 含义 | 典型例子 |
| --- | --- | --- |
| 系统化 | 按完整过程组织工作，明确活动之间的先后和输入输出 | 先分析需求，再设计、实现、测试 |
| 规范化 | 使用统一的标准、文档和约定，减少个人随意性 | 统一代码格式、接口规范、需求模板 |
| 可度量 | 用数据判断进度、成本和质量，而不是只凭感觉 | 统计缺陷数、完成任务数、测试覆盖情况 |

### 5. 易错点

- 软件工程只研究技术 → 是**管理和技术两方面**。
- 软件工程只管开发 → 是**开发和维护**。
- 把软件危机的成因归结为“没有好算法”。
- 把“系统化、规范化、可度量”当成软件工程的定义原文——它是工程化思想的展开，定义原文是上面第 1 条。

## 1.3 软件过程

### 1. 定义

> **软件过程**：为了获得软件产品，在软件工具的支持下，由软件工程师遵循一定步骤完成的一系列软件工程活动。

通俗说：从想法到成品，一共要走哪几步、按什么顺序走、每步产出什么。

> **软件过程模型**：对软件过程的抽象描述，规定开发要经过哪些阶段、每阶段做什么、各阶段如何衔接。

**两者关系**：软件过程是实际要走的流程，过程模型是把它画成图、抽象成模板。同一件事可以套用不同模板，四种模板见 1.4。

### 2. 四种基本活动（考纲核心）

**软件过程包含 4 种基本活动**：软件需求分析、软件设计和实现、软件测试、**软件演进**。

| 活动 | 做什么 | 主要产出 |
| --- | --- | --- |
| **软件需求分析** | 对功能、行为、性能、接口等做需求调查与了解，并用规范的软件工程语言把需求描述出来 | 需求分析文档 |
| **软件设计和实现** | 设计并实现需求分析阶段定义的功能和性能要求 | 设计文档、源程序 |
| **软件测试** | 确定软件功能的正确性和性能是否符合需求分析文档描述的要求 | 测试报告 |
| **软件演进** | 因政策、规则、工作内容、运行环境、用户使用习惯变化产生新需求，持续修改完善 | 变更后的程序与文档 |

> **辨析（本知识点最大的坑）**：第 4 项是**软件演进**，不是软件维护。
> 演进是“不断根据用户需求对程序进行修改、完善的**循环往复过程**”，属于**基本活动**；维护是过程模型里的**阶段名称**（如瀑布模型的“运行与维护”阶段）。考试问第 4 种基本活动，要选**软件演进**。

### 3. 需求分析（识记：需求分析阶段的目标）

> **目标**：了解用户需求，确定用户需要软件完成什么功能，并通过需求分析文档把用户需求清晰、规范地表达出来，形成内容完整、准确、详细的软件描述文档。

它是整条生产线的**上游**：需求错了，设计和编码全跟着错，造成不断返工改代码、延期与成本上升。**上游一错，下游全废。**

**需求分析的 4 个阶段**：**可行性研究 → 分析用户需求 → 描述需求 → 需求有效性验证**。

| 阶段 | 做什么 |
| --- | --- |
| 可行性研究 | 判断项目值不值得做、技术上经济上做不做得成 |
| 分析用户需求 | 搞清用户要什么功能、有什么性能要求 |
| 描述需求 | 用规范方式把需求写清楚、写成文档 |
| 需求有效性验证 | 检查需求是否完整、正确、无矛盾，并让用户确认 |

### 4. 软件设计与实现（识记：设计目标、设计步骤、设计任务、实现任务）

> **软件设计的目标是把软件需求转化为软件表示。**

需求回答“做什么”，设计回答“怎么做”并把它表达出来，让编码的人照着实现。

**设计的步骤（从工作步骤和管理角度）= 两个阶段**：

| 阶段 | 做什么 |
| --- | --- |
| **概要设计** | 将软件需求转化为**数据结构和软件的体系结构** |
| **详细设计** | 细化体系结构，得到各组成部分的**详细数据结构和算法** |

**设计的任务（从技术内容角度）= 三类**：**数据设计**、**体系结构设计**、**实现过程设计**。

> **易混辨析**：问“设计的**步骤**”答**概要设计 + 详细设计**；问“设计的**任务**”答**数据 + 体系结构 + 实现过程**。同一知识点，两个问法，两套答案。

> **软件实现的任务**：程序员**根据软件设计文档编写程序以实现系统功能**。实现是“照图施工”，依据是设计文档，产出是源程序。

### 5. 软件测试与软件演进

**软件测试**：实现阶段生成的程序必须经过测试，以发现并纠正错误，保证功能与逻辑正确、符合需求分析文档的要求；测试需要通过几个不同阶段、采用不同策略和技术完成。

> **高频陷阱**：测试能证明程序**有错**，不能证明程序**无错**。看到“通过测试说明程序没有错误”，直接判错。

**软件演进**：因政策、规则、工作内容、运行环境、用户使用习惯等变化产生新需求，导致程序必须变更。开发者要做四件事：**了解变更需求 → 设计变更方案 → 实现程序变更 → 对变更后的程序测试**，如此循环往复。

> 软件必须持续演进，才能对抗 1.1 讲的“退化”。

### 6. 最容易混淆的边界

| 描述 | 阶段 | 原因 |
| --- | --- | --- |
| “课程容量满后不能继续选课” | 需求分析 | 这是业务规则，先决定系统要做什么 |
| “课程容量字段放在哪张表、如何加锁” | 软件设计 | 这是实现业务规则的方案 |
| “写容量检查代码” | 软件实现 | 把设计转化为程序 |
| “验证满员后确实不能选课” | 软件测试 | 检查结果是否符合需求 |
| “系统上线后新增候补排队” | 软件演进 | 因新需求改变更程序（第 6 章会细分为四类维护） |

### 7. 软件维护的四种常见类型（第 6 章展开，此处先建立印象）

| 类型 | 目的 | 例子 |
| --- | --- | --- |
| 改正性维护 | 修复已发现的缺陷 | 修复重复扣款、登录失败 |
| 适应性维护 | 适应环境、硬件、操作系统、政策或法规变化 | 因操作系统升级修改兼容性；因新政策修改税率 |
| 完善性维护 | 新增功能或改善性能、易用性 | 增加候补排队、导出 Excel |
| 预防性维护 | 降低未来出问题和维护困难的风险 | 重构复杂代码、补齐关键文档 |

### 8. 易错点

- 把 4 种基本活动记成 3 种，或把第 4 种答成“软件维护”。
- 把“软件设计”等同于写代码——写代码是**实现**。
- “设计的步骤”与“设计的任务”混答。
- 认为测试通过就等于程序没有错误。
- 认为需求分析只是走过场。

## 1.4 软件过程模型

软件过程模型规定了如何组织软件过程中的活动。没有一种模型适合所有项目，选择依据主要是需求是否明确、变化频率、风险大小、项目规模和团队特点。

### 1. 瀑布模型

**核心思路**：阶段之间**顺序推进、逐级向下**，前一阶段完成并通过评审后才进入下一阶段，每个阶段都有文档产出。

**阶段划分（识记）**：

| 序 | 阶段 | 主要任务 |
| :---: | --- | --- |
| 1 | 需求定义 | 弄清用户对软件系统的全部需求，提出系统目标和功能范围的说明，请用户审查认可，形成需求规格说明书 |
| 2 | 系统和软件设计 | 建立软件总体结构，画出由模块组成的软件体系结构图（应由需求分析文档导出）；再针对单个模块设计，确定模块内部的过程和结构 |
| 3 | 实现与单元测试 | 用选定的程序语言把模块的过程性描述转换为源程序，并对每个模块进行测试 |
| 4 | 集成与系统测试 | 把所有模块集成在一起进行全面测试，形成测试报告（含测试计划、测试用例与测试结果） |
| 5 | 运行与维护 | 向用户提交软件产品并投入运营，其间根据用户要求进行维护，填写和更改有关文档 |

> 注意第 3 与第 4 步的区别：**单元测试**测单个模块，**系统测试**把模块集成起来整体测。

**存在的问题（识记，四条）**：

1. 实际项目很少遵守它提出的顺序；
2. 客户通常难以清楚描述所有需求；
3. 客户必须很有耐心——只有项目接近尾声时才能拿到可执行的程序；
4. 在评审可运行程序之前，可能不会检测到重大错误。

- 适合：需求明确、变化少、规则稳定的项目。
- 优点：阶段清楚，文档和管理相对容易。
- 关键词：`需求明确`、`顺序推进`、`变化少`。

### 2. 原型模型

**它解决什么问题**：瀑布模型要求在对产品试用之前就完全、精确地表达需求，这非常困难、耗时长、效率低。

**基本思想（识记）**：先建立一个能够反映用户主要需要、**可运行的原型**，让用户体验未来系统的概貌，以引导用户提出更具体、确定的需求；再通过与用户沟通反复改进原型，最终实现完全符合用户需求的软件系统。

**存在的问题（识记，两条）**：

1. 相关利益者看到工作版本后，可能完全不了解原型的**体系结构（程序结构）也在演化**，导致开发者可能没考虑整体软件质量和长期可维护性；
2. 为让原型快速运行，实现中常采用**折中手段**；若不够细心，这些并不完美的选择会成为最终系统的组成部分。

- 适合：用户说不清需求，特别是界面、交互流程不明确的项目。
- 优点：尽早获得反馈，减少“做出来才发现不是用户想要的”风险。
- 关键词：`需求不清`、`先做样稿`、`用户反馈`。

### 3. 螺旋模型

**特点（识记）**：螺旋模型是一种**演进式**软件过程模型，它**结合了原型模型的迭代性质与瀑布模型的可控性和系统性特点**，具有快速开发出越来越完善版本的能力。

- 把软件开发为**一系列演进版本**：早期迭代中软件可能是理论模型或原型，后续迭代产生逐渐完整的系统版本；
- 被分割成一系列由团队定义的**框架活动**，每个框架活动代表螺旋上的一个片段；
- 从**圆心开始、顺时针**执行一圈所表示的活动；
- **每次演进都要考虑风险**，并且**每个演进过程都要标记里程碑**。

```
        第3圈 ← 里程碑
    ┌──────────────┐
    │   第2圈       │
    │  ┌────────┐  │
    │  │ 第1圈   │  │
    │  │  ┌──┐  │  │
    │  │  │● │  │  │   ● = 圆心（起点）
    │  │  └──┘  │  │   每向外一圈 = 更完整的演进版本
    │  └────────┘  │   每圈都做风险分析、都标里程碑
    └──────────────┘
      顺时针 →→→
```

- 适合：规模大、成本高、技术或业务风险高的项目。
- 优点：能较早识别并处理风险。
- 局限：管理复杂，对风险分析能力要求高，成本通常较高。
- 关键词：`风险高`、`反复风险分析`、`迭代`。

### 4. 统一过程模型

**核心思路**：尝试从传统软件过程中挖掘最好的特征，并用敏捷开发中许多最好的原则来实现——同时要“规范”和“灵活”。它也是面向对象的迭代、增量开发：系统不是一次做完，而是在多轮迭代中逐渐交付更多可用功能并完善架构。

> **极易混答的一处，务必分清**：
> - 统一过程包括的**活动**有 5 个：**策划、沟通、建模、构建、部署**；
> - 统一过程的**发展阶段**有 5 个：**起始、细化、构建、转换、生产**。
>
> 都是 5 个，但**活动**是“一类一类的工作”，**阶段**是“时间的先后段落”。

**5 个工作阶段及工作内容（识记）**：

| 阶段 | 主要工作内容 |
| --- | --- |
| **起始阶段** | 包括客户沟通和策划活动；识别基本业务需求，用用例初步描述每一类用户所需的主要特征和功能；识别资源、评估主要风险、制定初步进度计划表 |
| **细化阶段** | 包括沟通和建模活动；扩展起始阶段定义的用例，**创建体系结构基线**——包括软件的 5 种模型：用例模型、分析模型、设计模型、实现模型和部署模型；通常修订项目计划 |
| **构建阶段** | 在源代码中实现软件增量所要求的特征和功能；随着构件实现，对每一个构件设计并实施单元测试，另外实施构件组装和集成测试；用例用于导出一组验收测试 |
| **转换阶段** | 包括构建活动的后期阶段以及部署活动的第一部分；软件提交给最终用户进行 **Beta 测试**，用户反馈缺陷并提出变更；阶段结束时软件增量成为可用的发布版本 |
| **生产阶段** | 与通用过程的部署活动一致；对持续使用的软件进行监控，提供运行环境支持，提交并评估缺陷报告和变更请求 |

记忆抓手：**起始（想清楚值不值得做）→ 细化（把架构和用例做扎实）→ 构建（大规模写出来）→ 转换（交给用户试）→ 生产（长期盯着跑）**。

- 适合：面向对象的大中型项目。
- 关键词：`面向对象`、`迭代`、`增量交付`、`用例驱动`。

### 5. 四种模型对比与选型速记

| 模型 | 核心做法 | 解决的问题 | 最大毛病 | 适合 |
| --- | --- | --- | --- | --- |
| 瀑布 | 阶段顺序推进、文档驱动 | 让开发规范可控 | 需求要早期定死；客户久等；错误发现晚 | 需求明确、变化少 |
| 原型 | 先做可运行原型，反复改进 | 用户说不清需求 | 易被当成品；折中实现混入系统 | 需求不明确 |
| 螺旋 | 多轮演进，每轮做风险分析、标里程碑 | 大项目风险失控 | 过程复杂、对团队要求高 | 大型、高风险 |
| 统一过程 | 5 活动、5 阶段，用例驱动、迭代增量 | 兼顾规范与灵活 | 体系较重、落地成本高 | 中大型、面向对象 |

`需求清楚选瀑布；需求不清先原型；风险很高用螺旋；面向对象迭代用统一过程。`

## 1.5 敏捷开发

### 1. 为什么会有敏捷

在全球化、快速变化的业务环境中，软件是所有业务运行的一部分，**要把新软件迅速开发出来才能抓住新机遇**。于是快速开发与交付常成为最关键的需求——很多时候**宁愿牺牲一定的软件质量、降低某些需求，也要赢得快速交付**。

### 2. 基本思想（领会）

- **有效响应变更**，把变化当常态；
- 加强团队成员之间、技术与业务人员之间、软件工程师与经理之间的**沟通与协作**；
- 强调**可运行软件的快速交付**，不那么看重中间产品（文档）；
- **客户始终紧密参与**：提供需求、对需求排序、评估迭代；
- 以**增量方式**开发，客户指定每个增量中包含哪些需求；
- **预料变更并为之设计**。

### 3. 适用范围与代价（领会，易出简答）

| 适合 | 不适合 |
| --- | --- |
| 需求萌动、快速改变的**中小型**软件产品 | 安全性、可靠性要求**极高**的**大型**系统 |
| 团队**人数较少**、组织紧密结合 | 团队庞大、跨组织协调复杂 |

**代价**：系统维护最关键的两份文档是**需求分析文档**和**测试文档**（需求分析文档明确定义系统应该做什么，没有它很难评估变更影响）。而许多敏捷方法**非正式地、增量式地收集需求，没有建立有条理的需求分析文档**，因此**很可能使随后的系统维护变得更难、更昂贵**。

> 也就是说：敏捷是**用长期可维护性换短期交付速度**，不是“什么都好”。

### 4. Scrum 模型（管项目与团队）

**团队与产品**：Scrum 团队是**自组织的跨领域团队**，由**产品负责人**、**Scrum Master** 和**一个由 3～6 人组成的小型开发团队**构成；主要产品是**产品待定项、冲刺待定项和代码增量**；项目被分解为一系列**冲刺**，**每个冲刺为 2～4 周**。

**冲刺的定义**：Scrum 过程由**需求、分析、设计、演化和交付**等框架性活动组成；每个框架活动中，工作任务在相对较短的**时间盒**（表示为完成某些任务而分配的时间段）期限内完成，**称为一个冲刺**。冲刺数目根据产品规模与复杂度不同，冲刺中的工作由团队规定并实时修改。

**Scrum Master 的职责**：团队所有成员的**引导者**，负责组织每日 Scrum 会议、解决会议中提出的困难、指导成员互相帮助完成冲刺任务、帮助产品负责人查找管理产品待定项的技术，并确保以清晰简洁的术语说明待定项。

**四类冲刺会议**：

| 会议 | 时间安排 | 做什么 |
| --- | --- | --- |
| 冲刺规划会议 | 每个冲刺开始时 | 规划本冲刺的工作 |
| 每日 Scrum 会议 | 每个工作日开始的 **15 分钟** | 同步活动、制定未来 24 小时计划 |
| 冲刺评审会议 | 冲刺结束时（4 周冲刺通常 **4 小时**） | 演示本冲刺完成的软件增量；产品负责人决定是否接受 |
| 冲刺回顾会议 | 冲刺结束后 | 复盘本冲刺，改进下一轮 |

> **每日会议的三个关键问题（必背）**：
> 1）自上次团队例会后做了什么？ 2）遇到什么困难？ 3）下次例会前计划做些什么？

**评审会议的规则**：Scrum Master、开发团队、产品负责人和选定的利益相关者参加；主要活动是演示冲刺期间完成的软件增量——**演示可能不包含所有计划的功能**，但要演示冲刺期间已完成的功能；产品负责人**可以同意或不同意接受**该增量，不接受时相关方会反馈是否进行新一轮冲刺规划。

### 5. XP 模型（管工程实践）

XP **使用面向对象方法作为开发范型**，包括**策划、设计、编码和测试 4 个框架活动**：

| 框架活动 | 关键内容 |
| --- | --- |
| **策划** | 从需求搜集开始，**通过倾听创建一系列“故事”**，称为**用户故事**，描述待开发软件所需的输出、特征与功能 |
| **设计** | **严格遵循保持简洁（KIS）原则**，不鼓励额外的功能性设计 |
| **编码** | 在故事开发和初步设计完成后，**不要直接开始编码**，而是开发一系列单元测试，用于检验本次发布的所有故事 |
| **测试** | 为使单元测试易于执行和重复，应使用**可自动实施的框架**进行单元测试 |

XP 关键任务抓住三件事：**用户故事**、**KIS 简洁设计**、**测试先行 + 自动化单元测试框架**。

### 6. Scrum 与 XP 的分工

| 维度 | Scrum | XP |
| --- | --- | --- |
| 关注点 | **项目管理与团队协作框架** | **工程实践与技术方法** |
| 核心结构 | 角色 + 冲刺 + 四类会议 | 4 个框架活动 |
| 典型做法 | 时间盒、15 分钟站会、冲刺评审与回顾 | 用户故事、KIS、测试先行、自动化单元测试 |

两者都属于**敏捷**，不是新旧版本，也不是瀑布的变体，实际项目可以并用。

### 7. 敏捷开发的场景判断

用户想先看到“课程查询”功能，再决定选课和候补排队怎样做。团队可以先在一个冲刺中交付课程查询，再根据反馈安排下一轮工作。这体现了敏捷开发的短周期交付与持续反馈。

### 8. 易错点

- 认为敏捷适合所有项目——它只适合中小型、需求多变的项目。
- 认为敏捷“不要文档”——是**不那么看重中间产品**，代价正是不建需求文档会让维护更难更贵。
- 认为 Scrum 团队由“项目经理”领导——是产品负责人、Scrum Master 与 3～6 人开发团队，团队自组织。
- 把冲刺当成一次会议——冲刺是 2～4 周的时间盒周期。
- 把 XP 的 4 个活动答成“需求/设计/编码/测试”——是**策划/设计/编码/测试**。
