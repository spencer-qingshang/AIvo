## 第 1 节　软件

**考纲要求**：识记「软件的定义」、识记「软件的特点」。

### 1.1 软件的定义（识记）

> **定义（必背）**：软件是计算机系统中与硬件相互依存的另一部分，是**程序、数据及其相关文档的完整集合**。

这句话拆开就是三个组成要素，每一个都要能单独说清：

| 组成 | 定义 | 通俗理解 | 例子 |
| --- | --- | --- | --- |
| **程序** | 实现特定功能的**指令序列** | 让计算机一步步干活的命令清单 | 选课、退课、检查容量上限的代码 |
| **数据** | 使程序能正常操纵信息的**数据结构** | 程序干活时要读、要算、要存的东西 | 学生信息、课程信息、选课记录 |
| **文档** | 与程序开发、维护和使用有关的**图文材料** | 给人看的说明书与记录 | 需求分析文档、设计文档、测试文档、维护记录、用户手册、接口文档 |

**为什么三者绑在一起才算软件？**
只有程序、没有数据，程序跑起来没有东西可处理；只有程序和数据、没有文档，用户不知道怎么用、后来接手的人不知道怎么改。所以「只交代码」不构成一次完整的软件交付。

**辨析（选择题常设陷阱）**：

- 安装包、可执行文件 → 属于**程序**，不属于文档；
- 数据库里的选课记录 → 属于**数据**，不属于文档；
- 需求规格说明书、API 文档、部署手册 → 属于**文档**，不属于程序。

**补充一点背景（领会，帮助理解而非死记）**：「软件」这个词在**广义上**有更宽的用法——除设备、车辆、原材料之外的人的素质、技术水平、管理法规等无形的因素都可以叫「软件」。而**在计算机专业领域**，人们习惯把软件等同于程序；**在软件工程领域**，才取上面那个「程序 + 数据 + 文档」的完整定义。考试问「软件工程领域中软件的定义」，答的一定是完整集合那一条。

### 1.2 软件的特点（识记）

软件的六个特点，全部是**与硬件对比**得出的。记住这一句就抓住了纲：**软件是「设计」出来的，硬件是「制造」出来的**——后面六条都是这句话的展开。

| 序 | 特点 | 具体含义 | 一句话理解 |
| :---: | --- | --- | --- |
| 1 | **生产方式不同** | 软件以开发和设计为主，硬件以制造和装配为主 | 软件是「想」出来的，硬件是「做」出来的 |
| 2 | **「磨损」形式不同** | 硬件会物理磨损、老化、损坏；软件不会因运行次数增加而物理磨损，但会**退化** | 软件不是用坏的，是「过时」掉的 |
| 3 | **个性化细节多** | 软件的开发比硬件的生产有更多个性化细节，需要程序员定制 | 硬件零件能标准化，软件常常一项目一样 |
| 4 | **抽象性更强** | 软件比硬件具有更强的抽象性 | 硬件看得见摸得着，软件是逻辑实体 |
| 5 | **成本更难控制** | 软件的开发成本比硬件的制造成本更难控制 | 做一个和做一百个，软件成本几乎一样 |
| 6 | **牵涉社会因素** | 很多软件的功能涉及机构的组织、体制、管理方式、管理策略、管理细则 | 软件不只是技术，还改流程、改制度 |

**把第 2 条和第 5 条讲透（这两条最爱考）**：

- **关于「退化」**：一个 2019 年的手机 App，代码一个字节都没改，今天却可能又卡又闪退。原因是**运行环境变了**（系统升级）、**补丁累积了**、**当年的设计跟不上今天的需求了**。所以软件不是被用坏的，而是在环境变化中逐渐失效的。
- **关于成本**：软件**首个版本的开发成本很高，复制成本却极低**；硬件每多生产一件都要真金白银的材料费和加工费。这条推出了一个常考结论——**软件的成本比硬件更难控制**（选择题常把它反过来说成「软件成本容易控制」）。
- **顺带一条复制成本的推论**：正因为复制几乎不要钱，软件的定价与硬件完全不同，这也解释了为什么软件行业格外在意「规模」与「复用」。

**软件与硬件对比总表（建议直接背这张表）**

| 角度 | 软件 | 硬件 |
| --- | --- | --- |
| 生产方式 | 以**开发和设计**为主 | 以**制造和装配**为主 |
| 复制成本 | 首个版本贵，复制几乎不要钱 | 每多一件都要材料费、人工费 |
| 磨损方式 | 无物理磨损，会**退化** | 会磨损、老化、损坏 |
| 抽象性 | **更强** | 较弱 |
| 成本控制 | **更难**控制 | 相对容易 |
| 个性化 | 细节多，**需要程序员定制** | 零件、接口标准化程度高 |
| 社会因素 | 功能常涉及组织、体制、管理方式 | 较少 |

### 1.3 考试这样考

- **名词解释**：「软件」——按「计算机系统中与硬件相互依存的另一部分，是程序、数据及其相关文档的完整集合」答，缺一项就扣分。
- **判断题/单选题**：给四个关于软硬件比较的叙述，问哪个错误。**错误项通常是把「更难控制」说成「容易控制」**，或把软件说成会物理磨损。
- **归类题**：给出若干项目（源代码、选课记录、用户手册、安装包），问哪些属于程序/数据/文档。

### 1.4 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 软件就是程序 | 软件 = 程序 + 数据 + 文档，三者缺一不可 |
| 软件用久了会物理磨损 | 软件不物理磨损，是**退化**（环境变化、补丁累积、设计老化） |
| 软件成本比硬件容易控制 | 软件的开发成本**更难**控制 |
| 软件和硬件一样可以批量制造 | 硬件靠制造，软件靠**开发和设计** |

## 第 2 节　软件工程

**考纲要求**：识记「软件工程的定义」、识记「软件工程的研究领域」、领会「软件危机面临的问题」。

### 2.1 先看「软件危机」（领会）

> **定义（必背）**：软件危机是指在软件的开发与维护过程中所遇到的一系列严重问题。

它不是某一次事故，而是**一类反复出现、成规模出现的困境**。典型的现场是这样的：项目越做越大，进度一拖再拖，预算一加再加，交付出来的东西毛病不断，交付之后谁都不敢改——因为一改就出新的毛病。

**危机的六个表现（必背，简答与多选都从这里出）**：

| 序 | 表现 | 通俗说法 |
| :---: | --- | --- |
| 1 | 软件开发**缺乏计划性** | 干到哪算哪 |
| 2 | 软件**需求不够充分** | 没搞清用户到底要什么 |
| 3 | 缺乏软件开发**过程的规范** | 各人一套打法，没有章法 |
| 4 | 软件开发的**成本和进度难以控制** | 一再超支、一再延期 |
| 5 | 没有评测软件**产品质量的标准和方法** | 好坏没有统一尺子 |
| 6 | 软件**难以维护** | 交付即巅峰，之后动不了 |

> **辨析（高频陷阱）**：「软件的实现缺乏好的算法」**不属于**这六项。它听起来很合理，但危机的症结在**管理、需求、过程、标准、维护**，不在算法水平。看到它出现在选项里，先怀疑它是错的。

**危机为什么会发生？** 把上面六条倒推一遍就是成因：计算机硬件进步、高级程序语言出现，应用领域迅速扩大，需要开发的软件**规模大小不一、功能各异**，而人们的开发方式还停留在「个人手艺」阶段——用做小玩意儿的办法去做大系统，于是失控。危机不是技术不够先进造成的，而是**工程化程度不够**造成的。

**一个经典的例子（用来理解，不必背参数）**：某公司在为通用机开发操作系统的过程中，软件不能如期交付、投资金额不断追加、运行中不断发现新的程序缺陷，整个项目投入了几千人年、资金高达数亿美元。这个故事在教材里被反复引用，就是为了说明危机的四个典型特征：**延期、超支、缺陷多、维护难**。

### 2.2 软件工程的定义（识记）

> **定义（必背）**：软件工程是从**管理和技术两方面**研究如何更好地**开发和维护**计算机软件的一门学科。
> **基本思想（必背）**：按**工程化的原则和方法**组织软件开发。

这个定义里有四个字眼，一个都不能丢：

| 要点 | 为什么重要 |
| --- | --- |
| **两方面**：管理 + 技术 | 很多人只答「技术」，就丢了一半的分。软件工程不只研究怎么写代码，还研究怎么组织人、安排进度、控制质量 |
| **两个动词**：开发 + **维护** | 维护占了软件生命周期的很大比重，只答「开发」也是不完整的 |
| **一门学科** | 它是学科，不是某个工具或某个流程 |
| **工程化** | 这是它的灵魂，见下 |

**「工程化」到底是什么意思？**
就是承认「软件是造出来的复杂产品」，于是像造桥盖楼一样干活：

- 先有**图纸**：需求要写清楚，设计要画出来；
- 再有**施工**：按图纸编码，而不是边想边写；
- 最后有**验收**：测试通过才算交付；
- 全程有**规范、有文档、可检查、可追溯**，而不是几位程序员凭感觉闷头写。

一句话：**工程化 = 把「手艺」变成「工序」。**

### 2.3 软件工程的研究领域（识记）

大纲要求能说出它的研究领域，把它理解成「软件从想法到长期运行，一路上必须回答的问题」：

1. 软件开发的过程应该依次包含哪些步骤；
2. 如何了解并描述用户对软件功能和性能等方面的需求；
3. 如何进行合理的软件设计并描述软件设计方案；
4. 如何实现软件的编程，使软件质量更好、更容易维护；
5. 如何进行软件测试，以保证程序功能正确、隐藏的错误尽可能少；
6. 如何进行软件项目管理，以保证项目进展顺利。

**记忆抓手**：这六条正好是「**过程 → 需求 → 设计 → 实现 → 测试 → 管理**」，是一条完整的生产线。第 3 节讲的「软件过程」就是第 1 条的具体化，第 2～7 章分别展开后面几条。

### 2.4 考试这样考

- **名词解释**：「软件工程」——必须写出「管理和技术两方面」「开发和维护」两个要点。
- **简答**：软件危机的表现有哪些？（答出六条）
- **单选/多选**：从六个表现里混入「缺乏好的算法」等干扰项。
- **简答**：软件工程的基本思想是什么？（答：按工程化的原则和方法组织软件开发）

### 2.5 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 软件工程只研究技术 | 是**管理和技术两方面** |
| 软件工程只管开发 | 是**开发和维护**，维护同样重要 |
| 软件危机的原因是没有好算法 | 症结在管理、需求、过程、标准与维护 |
| 软件工程 = 写代码的规范 | 它是一门学科，覆盖从需求到维护的全过程 |

## 第 3 节　软件过程

**考纲要求**：识记「软件过程的定义」「软件过程模型的定义」「4 种基本活动」「需求分析阶段的目标」「软件设计阶段的目标」「软件设计的步骤」「软件设计的任务」「软件实现阶段的任务」。

这一节考纲给的识记项最多，是本章的**得分重心**。

### 3.1 两个定义（识记）

> **定义（必背）**：**软件过程**是为了获得软件产品，在软件工具的支持下，由软件工程师遵循一定步骤完成的一系列软件工程活动。

通俗说：**从想法到成品，一共要走哪几步、按什么顺序走、每步产出什么。**

> **定义（必背）**：**软件过程模型**是对软件过程的抽象描述，它规定了软件开发要经过哪些阶段、每个阶段做什么、各阶段如何衔接。

**两者关系（辨析点）**：软件过程是**实际要走的流程**，软件过程模型是**把这个流程画成图、抽象成模板**。同一件事可以套用不同的模板——瀑布、原型、螺旋、统一过程就是四种不同的模板，第 4 节逐个讲。

### 3.2 软件过程的 4 种基本活动（识记）

> **必背**：软件过程包含 **4 种基本活动**——软件需求分析、软件设计和实现、软件测试、**软件演进**。

| 序 | 活动 | 做什么 | 主要产出 |
| :---: | --- | --- | --- |
| 1 | **软件需求分析** | 对软件的功能、行为、性能、接口等做需求调查与了解，并用规范的软件工程语言把需求描述出来 | 需求分析文档 |
| 2 | **软件设计和实现** | 设计并实现需求分析阶段定义的功能和性能要求 | 设计文档、源程序 |
| 3 | **软件测试** | 确定软件功能的正确性和性能是否符合需求分析文档所描述的要求 | 测试报告 |
| 4 | **软件演进** | 因政策、规则、工作内容、运行环境、用户使用习惯等变化产生新需求，不断修改、完善程序 | 变更后的程序与文档 |

> **辨析（本知识点最大的坑）**：第 4 项是**软件演进**，不是软件维护。
> - **演进**是「不断根据用户需求对程序进行修改、完善的**循环往复过程**」，它是**基本活动之一**；
> - **维护**是瀑布模型等过程模型里的**阶段名称**（运行与维护阶段）。
>
> 考试问「软件过程的第 4 种基本活动是什么」，要选**软件演进**。选「软件维护」就是踩坑。

**为什么特别强调第 4 项？** 因为很多资料在讲 4 种活动时只把前 3 项写全，第 4 项一笔带过，导致考生只记住 3 种。**记住数字 4，并记住第 4 项叫演进。**

### 3.3 需求分析（识记：需求分析阶段的目标）

> **目标（必背）**：了解用户需求，确定用户需要软件完成什么功能，并通过需求分析文档把用户需求清晰、规范地表达出来，形成内容完整、准确、详细的软件描述文档。

**为什么需求分析是成败关键？** 因为它是整条生产线的**上游**。需求错了，设计和编码全跟着错，于是出现程序员最头疼的**不断返工、修改代码**，项目延期交付、成本增加。一句话：**上游一错，下游全废。**

**需求分析的 4 个阶段（必背，简答题常客）**：

| 序 | 阶段 | 做什么 |
| :---: | --- | --- |
| 1 | **可行性研究** | 先判断这个项目值不值得做、技术上和经济上做不做得成 |
| 2 | **分析用户需求** | 搞清楚用户到底要什么功能、有什么性能要求 |
| 3 | **描述需求** | 用规范的方式把需求写清楚、写成文档 |
| 4 | **需求有效性验证** | 回头检查写下的需求是否完整、正确、无矛盾，并让用户确认 |

> **口诀**：**可行 → 分析 → 描述 → 验证**。顺序不能乱，因为每一步都以上一步为输入。

### 3.4 软件设计与实现（识记：设计的目标、步骤、任务；实现的任务）

这是本次讲义重点补强的一节，考纲要求密集。

> **目标（必背）**：软件设计的**目标是把软件需求转化为软件表示**。

意思是：需求阶段回答「**做什么**」，设计阶段回答「**怎么做**」，并把这个「怎么做」用图、文档等形式表达出来，让编码的人能照着实现。

**软件设计的步骤（识记）**：从工作步骤和管理角度，软件设计分为**概要设计**和**详细设计**两个阶段。

| 阶段 | 做什么 | 回答的问题 |
| --- | --- | --- |
| **概要设计** | 将软件需求转化为**数据结构和软件的体系结构** | 系统分成哪些部分？各部分什么关系？ |
| **详细设计** | 通过对软件体系结构的细化，得到软件各组成部分的**详细数据结构和算法** | 每个部分内部具体怎么做？ |

**软件设计的任务（识记）**：从**技术内容**角度，软件设计的任务分为三类：

1. **数据设计**——把需求里的数据对象变成数据结构；
2. **体系结构设计**——定义软件的总体结构（模块及其关系）；
3. **实现过程设计**——把结构元素的过程性描述转成算法和内部数据结构。

> **辨析（易混）**：问「软件设计的**步骤**」答**概要设计 + 详细设计**（两阶段，从管理与工作步骤角度）；问「软件设计的**任务**」答**数据设计 + 体系结构设计 + 实现过程设计**（三任务，从技术内容角度）。同一个知识点，两个问法，两套答案。

> **软件实现的任务（必背）**：软件实现是**程序员根据软件设计文档编写程序以实现系统功能**的过程。

也就是说，实现阶段是「照图施工」——依据是设计文档，产出是源程序。

### 3.5 软件测试与软件演进

**软件测试**：软件实现阶段生成的程序必须经过测试，以**发现并纠正程序中的错误**，保证程序实现的功能和逻辑是正确的、符合需求分析文档要求的。测试需要通过几个不同的阶段、采用不同的策略和技术来完成。

> **辨析（选择题高频陷阱）**：测试的目的是**发现错误**，不是**证明没有错误**。
> 任何时候看到「通过测试说明程序中没有错误」这类绝对化说法，直接判错——测试能证明程序**有错**，但不能证明程序**无错**。

**软件演进**：在软件开发过程中和用户使用过程中，可能因**政策、规则、工作内容、程序运行环境、用户使用习惯**等因素对程序产生新的需求，导致程序必须变更。开发者要做四件事：**了解变更需求 → 设计变更方案 → 实现程序变更 → 对变更后的程序测试**。软件演进就是这种不断修改、完善的**循环往复**过程。

> **为什么会有演进？** 因为软件的「规格」不是一次定死的：外部规则变了、环境变了、用户习惯变了，软件就得跟着变。这正是第 1 节所说软件会「退化」的另一面——**软件必须持续演进，才能对抗退化**。

### 3.6 考试这样考

- **简答**：软件过程包含哪几种基本活动？（答 **4 种**，注意第 4 项是**软件演进**）
- **简答**：软件需求分析分为哪几个阶段？（答：可行性研究、分析用户需求、描述需求、需求有效性验证）
- **名词解释**：软件过程、软件过程模型。
- **单选**：辨析「软件设计的步骤」与「软件设计的任务」；辨析「软件演进」与「软件维护」。
- **判断**：测试的作用是否等于「证明程序无错」。

### 3.7 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 4 种基本活动记成 3 种 | 第 4 种是**软件演进** |
| 第 4 种活动是软件维护 | 是**软件演进**；维护是过程模型里的阶段名 |
| 软件设计 = 写代码 | 设计是把需求转化为软件表示（概要与详细设计），**实现**才是写代码 |
| 设计步骤与设计任务混答 | 步骤 = 概要 + 详细；任务 = 数据 + 体系结构 + 实现过程 |
| 测试通过 = 程序没错误 | 测试能证明有错，不能证明无错 |
| 需求分析是走过场 | 它是决定成败的关键上游，错了就全面返工 |

## 第 4 节　软件过程模型

**考纲要求**：领会瀑布模型、原型模型、螺旋模型、统一过程模型这四种模型的阶段划分、开发过程、存在的问题、特点与适用场合。

这一节是本章的重头戏。四种模型各回答同一个问题：**活儿该按什么节奏干？**
记的时候别死背，抓住「**它是为了解决什么问题才被提出来的**」，再记住「**它自己又留下了什么毛病**」。

### 4.1 瀑布模型

**核心特征**：把软件过程划分为若干个阶段，**阶段之间顺序推进、逐级向下**，前一个阶段完成并通过评审后才进入下一个阶段，每个阶段都有相应的文档产出。

**比喻**：瀑布的水只能往下流，流过的位置不会回头。

**阶段划分**：

| 序 | 阶段 | 主要任务 |
| :---: | --- | --- |
| 1 | **需求定义** | 弄清用户对软件系统的全部需求，提出系统目标和功能范围的说明，请用户审查认可，形成需求规格说明书 |
| 2 | **系统和软件设计** | 建立软件的总体结构，画出由模块组成的软件体系结构图（应由需求分析文档导出）；再针对单个模块进行设计，确定模块内部的过程和结构，形成模块过程性描述文档 |
| 3 | **实现与单元测试** | 用选定的程序语言把模块的过程性描述转换为源程序，并对每个模块进行测试 |
| 4 | **集成与系统测试** | 把所有模块集成在一起进行全面测试，形成测试报告（含测试计划、测试用例与测试结果） |
| 5 | **运行与维护** | 向用户提交软件产品并投入运营，其间根据用户要求进行维护，填写和更改有关文档 |

> **注意第 3 与第 4 步的区别**：**单元测试**是对单个模块测，**系统测试**是把模块集成起来整体测。二者不是一个阶段。

**瀑布模型存在的问题（必背，四条）**：

1. **实际项目很少遵守它提出的顺序**——现实中总有回头修改；
2. **客户通常难以清楚描述所有需求**——而它偏偏要求需求一开始就定死；
3. **客户必须很有耐心**——因为只有在项目接近尾声时，才能拿到可执行的程序；
4. **在评审可运行程序之前，可能不会检测到重大错误**——错误发现得晚，返工代价大。

> 第 3 条和第 4 条是一体两面：**看不到东西 → 错误发现晚 → 返工代价大**。

**适合**：需求明确、变化少、技术成熟的系统。**一句话记忆：稳，但怕变。**

### 4.2 原型模型

**它为了解决什么问题而生？** 瀑布模型的致命缺点是：在对软件产品的某个版本试用之前，就要求用户完全、精确地表达明确的需求。这件事实施起来非常困难、花费时间长、效率低。

**基本思想（必背）**：**先建立一个能够反映用户主要需要、可运行的软件原型，让用户体验未来系统的概貌，以引导用户提出更为具体、确定的需求；然后通过与用户的沟通反复改进原型，最终实现完全符合用户需求的软件系统。**

**比喻**：装修前先搭个样板间。你看了才知道「哦，原来我要的是这种」，然后才提得出具体意见。

**开发过程**：快速构建原型 → 用户试用 → 收集反馈 → 改进原型 → 反复迭代 → 形成正式系统。

**原型模型存在的问题（必背，两条）**：

1. **相关利益者看到软件的工作版本后，可能完全不了解原型的体系结构（程序结构）也在演化**——这意味着开发者可能并没有考虑整体的软件质量和长期的可维护性；
2. **为了让原型快速跑起来，开发者往往在实现过程中采用折中手段**——如果不够细心，这些并不完美的选择就会成为最终系统的组成部分。

**适合**：用户说不清需求、需求需要逐步明确的项目。**一句话记忆：治「说不清需求」，但要防止把样品当成品。**

### 4.3 螺旋模型

**核心特点（必背）**：螺旋模型是一种**演进式**软件过程模型。它**结合了原型模型的迭代性质与瀑布模型的可控性和系统性特点**，具有快速开发出越来越完善的软件版本的潜力。

**它是怎么运转的？**

- 它把软件开发为**一系列演进版本**：早期迭代中，软件可能只是一个理论模型或原型；在后续迭代中，会产生一系列逐渐完整的系统版本。
- 它被分割成**一系列由软件工程团队定义的框架活动**，每个框架活动代表螺旋上的**一个片段**。
- 随着演进开始，团队**从圆心开始、按顺时针方向**执行螺旋上一圈所表示的活动。
- **每一次演进都要考虑风险**，并且**每个演进过程都要标记里程碑**。

```
            第3圈  ← 里程碑
        ┌──────────────┐
        │   第2圈       │
        │  ┌────────┐  │
        │  │ 第1圈   │  │
        │  │  ┌──┐  │  │
        │  │  │● │  │  │     ● = 圆心（起点）
        │  │  └──┘  │  │     每向外一圈 = 一个更完整的演进版本
        │  └────────┘  │     每圈都做风险分析、每圈都标里程碑
        └──────────────┘
          顺时针 →→→
```

> **与前两种模型的区别（辨析核心）**：
> - 瀑布只有一条直线，做完不回头；
> - 原型虽然反复，但反复的目的是「弄清需求」；
> - **螺旋的反复带着明确的「风险分析」，而且一圈比一圈产出更完整的版本**。所以它同时要了瀑布的「可控」和原型的「迭代」。

**适合**：**大型、风险高**的项目。**一句话记忆：把「风险分析」写进流程，是大项目的安全绳。**

### 4.4 统一过程模型（UP）

**它是什么？** 统一过程尝试**从传统的软件过程中挖掘最好的特征和性质，并用敏捷软件开发中许多最好的原则来实现**——也就是想同时要「规范」和「灵活」。

> **这里有个极易混淆的点，务必分清**：
> - 统一过程包括的**活动**有 **5 个**：**策划、沟通、建模、构建、部署**；
> - 统一过程的**发展阶段**有 **5 个**：**起始阶段、细化阶段、构建阶段、转换阶段、生产阶段**。
>
> 都是 5 个，但**活动**是「一类一类的工作」，**阶段**是「时间的先后段落」。考纲要求掌握的是 **5 个工作阶段及每个阶段的工作内容**，而问「包括哪些软件开发活动」时答的是**策划、沟通、建模、构建、部署**。两种问法，两套答案。

**5 个工作阶段及各自的工作内容（必背）**：

| 阶段 | 主要工作内容 |
| --- | --- |
| **起始阶段** | 包括客户沟通和策划活动；识别基本的业务需求，用用例初步描述每一类用户所需的主要特征和功能；识别各种资源、评估主要风险、为软件增量制定初步的进度计划表 |
| **细化阶段** | 包括沟通和通用过程模型的建模活动；**扩展起始阶段定义的用例，创建体系结构基线**——包括软件的 5 种模型：用例模型、分析模型、设计模型、实现模型和部署模型；通常还要修订项目计划 |
| **构建阶段** | 在源代码中实现软件增量所要求的特征和功能；随着构件实现，**对每一个构件设计并实施单元测试**，另外还实施构件组装和集成测试；用例用于导出一组验收测试，以便在下一阶段开始前执行 |
| **转换阶段** | 包括构建活动的后期阶段以及部署活动的第一部分；软件提交给最终用户进行 **Beta 测试**，用户反馈缺陷、提出必要的变更；阶段结束时软件增量成为可用的发布版本 |
| **生产阶段** | 与通用过程的部署活动一致；对持续使用的软件进行监控，提供运行环境的支持，提交并评估缺陷报告和变更请求 |

**记忆抓手**：**起始（想清楚值不值得做）→ 细化（把架构和用例做扎实）→ 构建（大规模写出来）→ 转换（交给用户试）→ 生产（长期盯着跑）**。可以记成一句话：**先想明白，再打地基，然后盖楼，接着交钥匙，最后做物业。**

**适合**：中大型、面向对象的项目。**一句话记忆：阶段是 5 个，灵魂是「用例 + 体系结构 + 迭代」。**

### 4.5 四种模型一张表对比

| 模型 | 核心做法 | 解决的问题 | 最大毛病 | 适合 |
| --- | --- | --- | --- | --- |
| **瀑布** | 阶段顺序推进、文档驱动 | 让开发规范可控 | 需求要早期定死；客户久等；错误发现晚 | 需求明确、变化少、技术成熟 |
| **原型** | 先做可运行原型，反复改进 | 用户说不清需求 | 易被当成品；折中实现混入系统，可维护性差 | 需求不明确、需逐步明确 |
| **螺旋** | 多轮演进，每轮都做风险分析，每轮标里程碑 | 大项目的风险失控 | 过程复杂、对团队要求高 | 大型、风险高 |
| **统一过程** | 5 个活动、5 个阶段，用例驱动、以体系结构为中心、迭代增量 | 兼顾规范与灵活 | 体系较重、落地成本高 | 中大型、面向对象 |

> **考场选型口诀**：
> **需求清楚不许变 → 瀑布；需求说不清 → 原型；风险很高又很大 → 螺旋；面向对象、要迭代又要规范 → 统一过程。**

- **简答**：瀑布模型把软件开发分为哪几个阶段？（需求定义、系统和软件设计、实现与单元测试、集成与系统测试、运行与维护）
- **简答**：原型模型的基本思想是什么？
- **简答**：瀑布模型存在哪些问题？（四条）
- **简答**：统一过程模型包括哪些软件开发活动？（策划、沟通、建模、构建、部署）
- **简答**：统一过程模型的 5 个工作阶段是什么？各阶段做什么？
- **单选/场景题**：给出项目情境，问应该选用哪种模型。

### 4.7 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 瀑布模型阶段里「测试」是一个笼统阶段 | 分**实现与单元测试**、**集成与系统测试**两步 |
| 原型模型的毛病是「做不出原型」 | 毛病是「利益相关者不了解原型结构也在演化」+「折中实现混入系统」 |
| 螺旋模型只是「反复做」 | 关键在**每轮都有风险分析**，且**结合了原型的迭代与瀑布的可控** |
| 统一过程的「活动」与「阶段」混答 | 活动 = 策划/沟通/建模/构建/部署；阶段 = 起始/细化/构建/转换/生产 |
| 统一过程只有 4 个阶段 | **5 个**，别漏「生产阶段」 |

## 第 5 节　敏捷开发

**考纲要求**：领会「敏捷开发的基本思想、过程和工具」「Scrum 模型和 XP 模型的软件开发过程」「Scrum 模型的团队、冲刺会议」「XP 模型的关键任务」。

### 5.1 为什么会有敏捷开发？

在全球化、快速变化的业务环境中，软件是所有业务运行的一部分。**要把新的软件迅速开发出来，才能抓住新机遇、应对竞争压力。** 于是快速的开发和交付常常成为软件系统最关键的需求——很多时候，**宁愿牺牲一定的软件质量、降低某些需求，也要赢得软件的快速交付。**

**比喻**：计划赶不上变化时，与其花一年做一份完美的方案，不如两周交一版能用的东西，让变化随时进来。

### 5.2 敏捷开发的基本思想（领会）

把它的主张列清楚，选择题就从这里挑：

1. **有效响应变更**——不是抗拒变化，而是把变化当成常态；
2. **加强沟通与协作**——团队成员之间、技术与业务人员之间、软件工程师与经理之间；
3. **强调可运行软件的快速交付**，而不那么看重中间产品（文档）；
4. **客户始终紧密参与**——客户的作用是提供新系统的需求、对需求排序、评估系统的迭代；
5. **以增量方式开发**——客户指定每个增量中想要包含的需求；
6. **预料变更并为之设计**——在设计时就考虑如何适应后续变更。

**适用范围（必背）**：

| 适合 | 不适合 |
| --- | --- |
| 需求萌动、快速改变的**小型或中型**软件产品 | 安全性、可靠性要求**极高**的**大型**系统 |
| 开发团队**人员数量较少**、组织紧密结合 | 团队庞大、跨组织协调复杂的项目 |

**代价（领会，容易出简答）**：在系统维护上，最关键的文档是**系统需求分析文档**和**测试文档**——需求分析文档明确定义了系统应该做什么，没有这些信息就很难评估变更的影响。而许多敏捷方法**非正式地、增量式地收集需求，没有建立有条理的需求分析文档**。因此，**使用敏捷方法很可能使随后的系统维护变得更难、更昂贵。**

> **这段话很重要**：它说明敏捷并非「什么都好」，而是**用长期可维护性去换短期交付速度**。答简答题时把这一层说出来，答案就立体了。

### 5.3 Scrum 模型

**它管什么？** Scrum 管的是**项目怎么推进、团队怎么协作**。

**Scrum 团队与产品（必背）**：

- Scrum 团队是一个**自组织的跨领域团队**，由**产品负责人**、**Scrum Master** 和**一个由 3～6 人组成的小型开发团队**组成；
- 开发的主要产品是**产品待定项、冲刺待定项和代码增量**；
- 开发把项目分解为一系列称为**冲刺**的增量原型开发周期，**每个周期为 2～4 周**。

**关键概念：冲刺（必背）**。Scrum 过程由**需求、分析、设计、演化和交付**等框架性活动组成。每一个框架活动中，工作任务在相对较短的**时间盒**（时间盒是项目管理术语，表示为完成某些任务而分配的时间段）期限内完成，**称为一个冲刺**。每个框架活动中冲刺的数目根据产品的规模大小和复杂度而有所不同，冲刺中进行的工作适应于当前的问题，由 Scrum 团队规定并进行实时修改。

**Scrum Master 的职责**：是团队所有成员的**引导者**，负责组织每日 Scrum 会议，负责解决团队成员在会议期间提出的困难，指导团队成员在有时间时互相帮助完成冲刺任务，帮助产品负责人查找管理产品待定项的技术，并帮助确保以清晰简洁的术语说明待定项。

**冲刺会议（考纲明确要求，必背）**：

| 会议 | 时间与安排 | 做什么 |
| --- | --- | --- |
| **冲刺规划会议** | 每个冲刺开始时 | 规划本冲刺要做的工作 |
| **每日 Scrum 会议** | 每个工作日开始的 **15 分钟** | 团队成员同步活动、制定未来 24 小时计划 |
| **冲刺评审会议** | 冲刺结束时（4 周冲刺通常用 **4 小时**） | 演示本冲刺完成的软件增量；产品负责人决定是否接受 |
| **冲刺回顾会议** | 冲刺结束后 | 回顾本冲刺的经验，改进下一轮 |

> **每日会议的三个关键问题（必背，简答原题级别）**：所有团队成员都提出并回答——
> 1）**自上次团队例会后做了什么？**
> 2）**遇到什么困难？**
> 3）**下次例会前计划做些什么？**

**冲刺评审会议的参加者与规则**：Scrum Master、开发团队、产品负责人和选定的利益相关者参加。会议的主要活动是**演示冲刺期间完成的软件增量**——注意，演示**可能不包含所有计划的功能**，但要演示**冲刺期间完成的功能**。在确定是否完成时，产品负责人**可以同意或者不同意接受该增量**；如果不接受，产品负责人和利益相关者会提供是否同意进行新一轮冲刺规划的反馈。

### 5.4 XP 模型（极限编程）

**它管什么？** XP 管的是**代码怎么写好**。它**使用面向对象方法作为开发范型**，包括**策划、设计、编码和测试 4 个框架活动**。

| 框架活动 | 关键内容 |
| --- | --- |
| **策划** | 从一个需求搜集活动开始，**通过倾听来创建一系列「故事」**，称为**用户故事**，用来描述待开发软件所需的输出、特征以及功能 |
| **设计** | **严格遵循保持简洁（KIS）原则**，**不鼓励额外的功能性设计** |
| **编码** | 建议在故事开发和初步设计完成之后，团队**不要直接开始编码**，而是**开发一系列单元测试**，用于检验本次软件增量发布的所有故事 |
| **测试** | 为了使单元测试易于执行和重复，应当使用一个**可以自动实施的框架**进行单元测试 |

> **XP 的「关键任务」怎么答**：抓住三件事——**用户故事**（用故事描述需求）、**KIS 简洁设计**（不做过度的功能设计）、**测试先行 + 自动化的单元测试框架**。

### 5.5 Scrum 与 XP 的对比

| 维度 | Scrum | XP |
| --- | --- | --- |
| 关注点 | **项目管理与团队协作框架** | **工程实践与技术方法** |
| 核心结构 | 角色（产品负责人/Master/开发团队）+ 冲刺 + 四类会议 | 4 个框架活动（策划/设计/编码/测试） |
| 典型做法 | 时间盒、每日 15 分钟站会、冲刺评审与回顾 | 用户故事、KIS、测试先行、自动化单元测试 |
| 共同点 | 都属于**敏捷**，都强调快速交付、拥抱变更、客户参与 | 同左 |

> **辨析**：Scrum 不等于 XP，两者不是「新旧版本」，也不是瀑布的变体。**Scrum 是管理框架，XP 是技术实践**——一个项目完全可以两者并用。

### 5.6 考试这样考

- **简答**：在 Scrum 模型中如何定义冲刺？每日 Scrum 会议的 15 分钟内，团队成员需要回答哪三个问题？
- **简答**：请举出三个适合采用敏捷开发模型的软件项目实例。（如手机端在线购物系统、医院手机端挂号及信息查询 APP、短视频类 APP；答题时补一句适用条件——适合需求萌动、快速改变的中小型产品与人数较少、组织紧密的团队，不适合安全性可靠性要求极高的大型系统）
- **简答**：使用敏捷方法为什么可能让后期维护更难？（因为不建立有条理的需求分析文档，而需求分析文档与测试文档是维护的关键文档）
- **单选**：敏捷的适用与不适用场景；Scrum 团队的角色构成；XP 的 4 个框架活动。

### 5.7 易错点

| 易错认识 | 正确认识 |
| --- | --- |
| 敏捷适合所有项目 | 只适合**中小型、需求多变**的项目，不适合安全性可靠性要求极高的大型系统 |
| 敏捷 = 不要文档 | 是**不那么看重中间产品**；代价正是不建需求文档会使维护更难更贵 |
| Scrum 团队由「项目经理」领导 | 由**产品负责人、Scrum Master、3～6 人开发团队**组成，团队自组织 |
| 冲刺是「一次会议」 | 冲刺是**时间盒内完成工作的一段周期**（2～4 周）；会议是冲刺中的活动 |
| 每日站会要开很久 | **15 分钟**，回答三个固定问题 |
| XP 的 4 个活动是「需求/设计/编码/测试」 | 是**策划/设计/编码/测试**（策划活动产出用户故事） |

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 以为「软件 = 程序」 | 软件 = 程序 + 数据 + 文档；安装包属于程序，不属于文档 |
| 以为软件用久了会物理磨损 | 软件不物理磨损，是**退化**（环境变化、补丁累积、设计老化） |
| 以为软件成本容易控制 | 软件的开发成本**更难**控制 |
| 把「软件过程的 4 种基本活动」记成 3 种 | 第 4 种是**软件演进** |
| 把第 4 种活动答成「软件维护」 | 是**软件演进**；维护是过程模型里的阶段名 |
| 以为「测试通过 = 程序没错误」 | 测试能证明有错，不能证明无错 |
| 把「设计的步骤」和「设计的任务」混答 | 步骤 = 概要 + 详细；任务 = 数据 + 体系结构 + 实现过程 |
| 把统一过程的「活动」与「阶段」混答 | 活动 = 策划/沟通/建模/构建/部署；阶段 = 起始/细化/构建/转换/生产 |
| 以为原型模型的毛病是「做不出原型」 | 毛病是「利益相关者不了解原型结构也在演化」与「折中实现混入系统」 |
| 把 Scrum 和 XP 弄反 | Scrum 管**项目与团队**，XP 管**工程实践** |
| 以为敏捷「不要文档」 | 敏捷是**不那么看重中间产品**，代价正是不建需求文档会让维护更难更贵 |
