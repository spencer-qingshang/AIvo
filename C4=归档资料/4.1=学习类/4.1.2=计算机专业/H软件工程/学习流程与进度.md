## 第 1 章 软件工程概述

### 1.1 软件

#### 核心结论

软件是程序、数据及其相关文档的完整集合：

`软件 = 程序 + 数据 + 相关文档`

- 程序：让计算机执行的指令，例如应用的代码或安装包。
- 数据：程序处理或保存的信息，例如学生选课记录。
- 文档：供使用、部署、维护或开发参考的资料，例如系统管理员部署说明、API 文档和示例。

#### 无辅助检测

1. 学生选课记录属于数据。
2. 《系统管理员部署说明》属于文档。
3. 只有代码不等于完整的软件，因为还需要保存的数据和相关文档，例如 API 文档、示例。

结论：3 / 3 正确。

### 1.4 软件过程模型

#### 核心结论

软件过程模型是组织需求、设计、实现、测试和维护活动的方法。

- 瀑布模型：按阶段顺序推进，适用于需求明确、变化少的项目；前期需求出错时，后期修改成本高。
- 原型模型：先构建可演示的雏形并收集反馈，适用于需求或界面交互不明确的项目；不能把原型直接当作正式产品。
- 螺旋模型：每一轮都重视风险分析、开发和评估，适用于大型、复杂、风险高的项目。
- 统一过程模型：面向对象的迭代、增量开发模型，适用于大中型项目。

#### 无辅助检测

1. 需求固定、规则明确的考试报名系统：瀑布模型。
2. 涉及高额资金、技术方案不确定的大型系统：螺旋模型。
3. 用户说不清页面和操作流程：原型模型。
4. 面向对象的大型项目，逐次迭代交付功能：统一过程模型。

结论：4 / 4 正确。

### 1.5 敏捷开发

#### 核心结论

敏捷开发把工作拆分为短周期迭代，通过持续交付和反馈来适应需求变化。

- Scrum：用冲刺管理迭代和交付节奏。
  - 产品负责人：明确需求并确定优先级。
  - Scrum Master：帮助团队遵守流程、排除协作障碍。
  - 开发团队：完成冲刺中承诺的工作。
  - 每日站会：同步进度、计划和阻碍。
  - 冲刺评审会：展示本次冲刺成果并收集反馈。
  - 冲刺回顾会：复盘过程并改进下一轮工作方式。
- XP（极限编程）：强调结对编程、测试驱动开发、持续集成和重构等高质量代码实践。

#### 无辅助检测

1. 面对需求变化，应在短周期反馈后调整。
2. 确定需求优先级的角色是产品负责人。
3. 展示冲刺成果并收集反馈的会议是冲刺评审会。
4. 结对编程、测试驱动开发和持续重构属于 XP。

结论：4 / 4 正确。

### 1.2 软件工程

#### 核心结论

软件工程是用系统化、规范化、可度量的方法，开发、运行和维护软件。

- 软件危机：软件项目出现延期、超预算、缺陷多、质量差或难维护等问题。
- 系统化：按完整的软件过程开展工作，例如先分析需求，再设计、实现和测试。
- 规范化：使用共同的代码规范、文档和标准。
- 可度量：用进度、成本、缺陷数量等数据判断项目状态和质量。

#### 无辅助检测

1. 项目延期、预算超支、缺陷很多、后期难维护，属于软件危机。
2. 写需求文档体现系统化；统一代码规范体现规范化；统计缺陷数量体现可度量。

结论：通过。

### 1.3 软件过程

#### 核心结论

软件过程是把需求转化为可运行、可维护软件的一系列活动与步骤。

1. 需求分析：明确软件要解决的问题和需要具备的功能。
2. 软件设计：规划软件的结构、模块、数据和接口。
3. 软件实现：把设计转化为可运行的程序。
4. 软件测试：验证软件是否符合需求并发现缺陷。
5. 软件维护：软件上线后修复问题、适应环境或需求变化、完善功能。

#### 无辅助检测

1. “同一学生不能重复选同一门课”应在需求分析阶段首先明确。
2. 设计学生表、课程表和选课记录表属于软件设计阶段。
3. 上线后新增候补排队规则属于软件维护阶段。

结论：3 / 3 正确。
