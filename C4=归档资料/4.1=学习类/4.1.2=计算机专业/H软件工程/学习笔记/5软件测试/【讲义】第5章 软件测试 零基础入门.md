## 第 1 节　软件测试概述

### 一句话定义

**软件测试是根据软件开发各阶段的规格说明和程序的内部结构而精心设计测试用例，利用这些测试用例运行程序，以发现程序中潜在错误的过程。简而言之，软件测试就是为了发现程序中的错误而执行程序的过程。**

### 用「日常生活比喻」来理解

把软件测试想成**体检**：

- 体检的目的**不是证明你没病**，而是**尽量查出病**（→ 软件测试的目的在于发现错误，一个好的、成功的测试是能发现至今未被发现的错误）；
- 体检要**分项目、按顺序**做：先抽血（单元测试）→ 再做各科会诊（组装测试）→ 最后总检出报告（确认测试、系统测试）；
- 体检要看**的不只是器官（程序），还包括你的病历和生活习惯（需求说明、设计说明）**（→ 软件测试的对象不只是源程序）；
- 医生**不给自己和家人做手术**（→ 程序员应该避免检查自己的程序）；
- 一次体检只能覆盖一部分，**某个部位问题多，就要反复复查**（→ 注意测试中的群集现象）；
- 体检报告要**存档**，方便以后对比（→ 妥善保存测试计划、测试用例、出错统计和分析报告）。

### 关键概念逐个讲透

#### 1）软件测试的定义（识记）

拆成 3 个要素记：

| 要素 | 内容 |
| --- | --- |
| 依据 | 软件开发各阶段的**规格说明**和程序的**内部结构** |
| 手段 | **精心设计测试用例**，并用这些用例**运行程序** |
| 目的 | **发现程序中潜在的错误** |

#### 2）软件测试的步骤（识记，顺序必背）

**软件测试的基本步骤依次为：单元测试 → 组装测试 → 确认测试 → 系统测试。**

时间上的分工：

- **单元测试**可以在**编码阶段**开始，边写程序边测试；也可以在编码告一段落时由专门的软件测试人员完成；
- **组装测试、确认测试、系统测试**是在软件开发过程的**软件测试阶段**进行的。

#### 3）软件测试的目标（领会）

- 软件测试的**目的在于发现错误**；
- 一个好的、成功的测试是**能发现至今未被发现的错误**；
- 软件测试追求的目标是：**以最少的时间和人力找出软件中潜在的尽可能多的各种错误和缺陷**。

#### 4）软件测试的原则（领会，8 条，选择题高频）

1. **应当尽早且不断地进行软件测试**以减少发现和纠正错误的代价：
   ① 及时审查每个阶段的工作成果，包括各种文档；
   ② 在编码阶段及时测试各个程序模块，**写一个模块，测试一个模块**。
2. **测试用例应该包括测试输入数据和与之对应的预期输出结果**。
3. **程序员应该避免检查自己的程序**。
4. **测试用例应当包括合理的输入条件和不合理的输入条件**。
5. **充分注意测试中的群集现象**：经过测试后程序中残存的错误数量与程序中已发现的错误数量成**正比**，所以对错误较多的程序应采用不同的测试方法反复测试、纠错。
6. **严格执行测试计划、排除测试的随意性**。
7. **应对每一个测试结果做全面的检查**，以避免漏掉已经检测出的错误。
8. 软件测试的结果对于分析程序的逻辑有重要作用，**应妥善保存**测试计划、测试用例、出错统计和最终的分析报告，为软件维护提供方便。

#### 5）软件测试的对象（识记）

**软件测试的对象包括需求分析说明、概要设计和详细设计的规格说明、源程序。**

重要理解：**很多软件的错误是在需求分析和设计阶段产生的，不只是在编程阶段才会产生错误**——所以文档也要测。

> 教辅例题：下列选项中，软件测试对象一般**不包括**的是 → 答「**可执行程序**」。因为对象是需求分析说明、概要设计/详细设计规格说明、源程序，没有「可执行程序」这一项。

### 考试这样考

- **单选题**：「软件测试的目的是」→ 发现错误（不是证明程序没有错误）。
- **单选题（反向）**：「关于软件测试的原则，下列说法正确的是 / 错误的是」——教辅例题的正确选项是「**测试用例需要作为测试文档的一部分予以保留**」。
- **单选题**：「下列不属于软件测试对象的是」→ 记住 3 类对象。
- **简答题**：「软件测试的目的是什么？」→ 软件测试的目的在于发现软件中存在的错误；一个好的、成功的测试是能发现至今未被发现的错误。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「测试的目的是证明程序没有错误」 | 恰恰相反：测试是为了**发现错误**；「证明无错」只有**穷举测试**才可能做到，而它代价极高 |
| 「测试就是运行程序」 | 这只是**动态测试**；还有**静态测试**（不需要执行被测程序） |
| 「程序员最了解自己的程序，应该自己测」 | 原则明确要求：**程序员应该避免检查自己的程序** |
| 「测试用例只要给输入数据」 | 必须同时包含**输入数据和与之对应的预期输出结果** |
| 「测试用例只用合法输入」 | 应同时包括**合理与不合理的输入条件** |
| 「可执行程序是测试对象」 | 教材列的测试对象是**需求分析说明、概要设计和详细设计的规格说明、源程序** |

## 第 2 节　软件测试的方法与技术（全章重点，必会动手算）

### 一句话定义

软件测试方法**首先分为静态测试与动态测试**：静态测试不需要执行被测程序（也称代码复审，目的在于检查程序的静态结构，找出编译过程无法发现的错误）；**动态测试又称机器测试**，是指在设定的测试数据上执行被测程序的过程。常用且有效的动态测试方法是**黑盒测试与白盒测试**。结合软件测试、以发现错误原因和错误位置的技术称为**调试**。

### 用「日常生活比喻」来理解

| 方法 | 比喻 | 你要不要看内部 |
| --- | --- | --- |
| **黑盒测试**（功能测试） | 去餐厅吃饭，只看**菜单和端上来的菜**好不好吃，不进厨房 | 不管程序内部结构，只看外部功能 |
| **白盒测试** | 进厨房，看**每道工序、每个判断**有没有做对 | 了解程序内部逻辑结构，按逻辑结构设计用例 |
| **静态测试** | 不点火，只**翻菜谱和检查食材** | 不运行程序，靠评审/分析找错 |
| **边界值分析** | 试门锁，**专拧到刚好能锁上和差一点点锁不上**的刻度 | 取正好等于、刚刚大于、刚刚小于边界的值 |

### 关键概念逐个讲透

#### 1）黑盒测试原理（识记）

**黑盒测试方法是测试者把被测程序看成一个黑盒，不管程序的内部结构，仅以程序的外部功能为根据来设计测试用例。黑盒测试着重测试程序的功能是否正确，也被称为功能测试。**

**设计黑盒测试用例的 4 个步骤（教材原文，必背顺序）**：

1. **建立等价类表**；
2. 为每一个等价类规定一个**唯一的编号**；
3. 设计一个新的测试用例，使其**尽可能多地覆盖尚未被覆盖的有效等价类**。重复这一步，直到所有的有效等价类都被覆盖为止；
4. 设计一个新的测试用例，使其**覆盖一个尚未被覆盖的无效等价类**。重复这一步，直到所有的无效等价类都被覆盖为止。

> 注意第 3 步与第 4 步的差别：**有效等价类可以「一个用例盖多个」，无效等价类只能「一个用例盖一个」**——因为一个用例里只要有一个非法输入，程序多半就报错了，其余非法输入就测不到。

#### 2）等价类（识记，应用题的根）

**等价类划分的方法是把所有可能的输入数据，即程序的输入域划分成若干部分，然后从每一部分中选取少数有代表性的数据作为测试用例。**

| 术语 | 教材定义 | 通俗理解 |
| --- | --- | --- |
| **等价类** | 某个输入域的**子集**，在该子集中，各个输入数据对于**揭露程序中的错误都是等效的** | 一组「效果一样」的输入，测一个就够 |
| **有效等价类** | 对程序的需求规格说明而言是**合理的、有意义的**输入数据构成的集合，利用它可以验证程序是否实现了规格说明预先规定的功能和性能 | 合法输入 |
| **无效等价类** | 对程序的需求规格说明而言是**不合理的、无意义的**输入数据构成的集合，主要用来检查程序中的功能和性能的实现是否**不符合**规格说明的要求 | 非法输入 |

#### 3）白盒测试原理（识记）

**白盒测试是软件测试中的一种方式，它将测试重点放在程序的代码级。测试者需了解程序内部的逻辑结构，从程序的逻辑结构出发，按照一定的原则设计测试用例。通过查代码中的语句、路径、条件等，以确定代码是否满足用户需求和设计规范。**

**白盒测试的检查范围（4 条）**：

1. 对程序模块的**所有独立的执行路径**至少测试一次；
2. 对所有的**逻辑判断**，取「真」与取「假」的两种情况都至少测试一次；
3. 在**循环的边界和运行界限内**执行循环体；
4. 测试**内部数据结构**的有效性。

#### 4）逻辑覆盖的 6 种技术（识记 + 简单应用，必考）

逻辑覆盖是以程序内部的逻辑结构为基础的测试用例设计技术。**逻辑覆盖分为语句覆盖、判定覆盖、条件覆盖、判定-条件覆盖、条件组合覆盖及路径覆盖。**

| 覆盖技术 | 教材定义（背这一句） | 通俗理解 |
| --- | --- | --- |
| **语句覆盖** | 使被测程序的**每条语句都执行至少一次** | 每行代码跑到就行 |
| **判定覆盖** | 使被测程序的**每个判断的取真分支和取假分支都执行至少一次** | 每个 if 的真假都走过 |
| **条件覆盖** | 使被测程序的**每个条件都按「真」和「假」执行至少一次** | 复合判断里的每个小条件都取过真假 |
| **判定-条件覆盖** | 被测程序的**每个判断中的每个条件都按「真」「假」取值各执行至少一次，同时使每个判断都按「真」「假」取值各执行至少一次** | 判定覆盖 + 条件覆盖同时满足 |
| **条件组合覆盖** | 使**每个判断的所有可能的条件取值组合都执行至少一次** | 把小条件的真假**组合**都跑一遍 |
| **路径覆盖** | 使测试用例**覆盖程序中的所有可能路径** | 每条路径都走一遍 |

**强弱关系（按检错能力由弱到强记这条链）**：

```text
语句覆盖 → 判定覆盖 → 条件覆盖 → 判定-条件覆盖 → 条件组合覆盖 → 路径覆盖
（检错能力由弱到强）

两条必须记住的补充说明：
① 条件覆盖不一定包含判定覆盖（每个条件的真假都测到了，某个判断整体却可能只取到真），
   正因如此才引入「判定-条件覆盖」，它同时满足判定覆盖与条件覆盖；
② 路径覆盖与条件组合覆盖之间不是严格的包含关系——把 4 条路径都跑到，
   并不等于每个判断的 8 种条件组合都被触发（见下面 ⑥ 的表：4 组路径用例漏掉 ② 和 ⑥）。
```

> 补充：路径覆盖测试技术就是设计足够多的测试用例覆盖程序中所有可能的路径。在实际问题中要实现对程序的路径测试，必须使所有路径都至少执行一遍，也就是进行**路径的穷举测试**；由于路径数太多、成本极高，可以把覆盖的路径数控制在一定限度内（如**循环体内的路径只执行一次**），基于这种想法的测试称为**基本路径测试**。

#### 5）穷举测试与选择测试（识记）

| 项目 | 穷举测试 | 选择测试 |
| --- | --- | --- |
| 定义 | 让被测试的程序在**一切可能的输入情况下都执行一遍** | 选择**有代表性的测试用例**进行**有限的测试** |
| 优点 | **能证明程序无错** | 代价小、可实施 |
| 缺点 | **实现的代价高**，对规模很大的程序**无法实现** | 不能证明程序无错 |

**穷举测试的规模感（教辅原文数据，常考数值）**：对于有两个输入、一个输出的程序，若输入 x、y 为整数，则在 32 位字长的机器上，穷举测试的案例数为 2³² × 2³² = **2⁶⁴**；若测试一个案例的时间为 1 ms、每天 24 h 不停地测试，则需要 **5 亿年**才能完成这一简单的测试。对现在广泛使用的 64 位字长的机器，穷举测试的案例数会达到 **2¹²⁸** 个的规模。

#### 6）边界值分析（识记目的 + 简单应用）

**使用边界值分析方法设计测试用例，首先应确定边界情况。通常，输入等价类与输出等价类的边界就是应重点测试的边界情况。应当选取正好等于、刚刚大于或刚刚小于边界的值作为测试数据，而不是选取等价类中的典型值或任意值作为测试数据。**

**边界值分析方法选择测试用例的 7 条原则（教材原文 + 原例）**：

| 序号 | 原则 | 教材原例 |
| --- | --- | --- |
| 1 | 输入条件规定了**值的范围**：取刚达到边界的值，以及刚刚超越边界的值 | 输入范围 [-1.0, 1.0] → 取 **-1.0、1.0、-1.001、1.001** |
| 2 | 输入条件规定了**值的个数**：取最大个数、最小个数、比最大个数多 1、比最小个数少 1 | 输入文件可有 1～255 个记录 → 取 **1、255、0、256** 个记录 |
| 3 | 对**每个输出条件**用原则 1 | 折扣量最低 0 元、最高 1050 元 → 设计恰好产生 **0 元和 1050 元**的结果，还可考虑结果为**负值或大于 1050 元**的用例 |
| 4 | 对**每个输出条件**用原则 2 | 信息检索系统最多显示 4 篇摘要 → 设计显示 **1 篇、4 篇、0 篇**，并设计一个可能错误地显示 **5 篇**的用例 |
| 5 | 输入域或输出域是**有序集合**（有序表、顺序文件）：选**第一个元素和最后一个元素** | 有序表的首、末元素 |
| 6 | 程序中使用了**内部数据结构**：选该结构**边界上的值** | 数组下标下界 0、上界 99 → 选 **0 与 99** |
| 7 | 分析规格说明，**找出其他可能的边界条件** | 结合具体问题补充 |

#### 【方法 A】等价类划分法：5 步照做

```text
第 1 步  列出所有输入条件（含输出条件），逐条分析规格说明
第 2 步  为每个输入条件划分「有效等价类」和「无效等价类」，并给每个类编号
第 3 步  画等价类表（列：输入条件 / 等价类编号 / 测试数据 / 预期结果）
第 4 步  设计用例：先让一个用例尽量多覆盖「尚未覆盖的有效等价类」，重复到全覆盖
第 5 步  再为「每一个尚未覆盖的无效等价类」单独设计一个用例（一个用例只覆盖一个无效类）
```

##### 示例 1（最简版，先热身）

**题目**：某程序的功能是求整数的绝对值，输入为整数。请用等价类划分法划分等价类并给出测试用例。

**步骤**：
1. 输入条件：一个整数。
2. 按「正、零、负」三种情况划分：正数、0、负数 → 共 **3 个等价类**（都属于有效等价类）。
3. 三类中任取一个有代表性的值即可。

**答案**：

| 输入条件 | 等价类编号 | 测试数据 | 预期结果 |
| --- | --- | --- | --- |
| 输入整数 | ① 正数 | 6 | 6 |
| 输入整数 | ② 负数 | -6 | 6 |
| 输入整数 | ③ 零 | 0 | 0 |

> 教材原话：在等价类正数中任意取一个正数、在等价类负数中取一个负数，「它们对于揭露程序中的错误都是等效的」。
> 教辅例题：对求整数绝对值的函数进行黑盒测试所设计的测试用例中，应将输入数据划分为的**等价类个数为 3**。

##### 示例 2（完整版，教材例题）

**题目**：用黑盒法测试求一元二次方程 **ax² + bx + c = 0** 的功能，测试根据得到的根的值不同划分等价类，并给出测试用例。

**步骤**：
1. 输入条件是三个系数 a、b、c，判别式为 b² - 4ac，方程形态由 a 是否为 0 决定。
2. 划分有效等价类（程序应当能正常给出根）：① b²-4ac = 0 时两根相等；② b²-4ac > 0 且 b ≠ 0 时两根不等；③ b = 0 且 b²-4ac > 0 时两根大小相等符号相反；④ a = 0 且 b ≠ 0 时退化为一次方程，只有唯一实根；⑤ b²-4ac < 0 时有两个虚根。
3. 划分无效等价类（程序应报错）：系数个数不是 3 个（少于 3 个、多于 3 个）、a = 0 且 b = 0（方程无意义）。
4. 每个等价类取一组有代表性的数据，写出预期根值。

**答案（教材表格）**：

| 输入条件 | 等价类编号 | 测试数据（a, b, c） | 根的性质 | 根值 |
| --- | --- | --- | --- | --- |
| a≠0 且 b²-4ac=0 | ① | (1, 2, 1) | 两个相等的实根 | (-1, -1) |
| a≠0 且 b≠0 且 b²-4ac>0 | ② | (1, 4, 1) | 两个不相等的实根 | (-2-√3, -2+√3) |
| a≠0 且 b=0 且 b²-4ac>0 | ③ | (-1, 0, 1) | 两个大小相等符号相反的实根 | (-1, 1) |
| a=0 且 b≠0 | ④ | (0, 1, 2) | 唯一实根 | -2 |
| a≠0 且 b²-4ac<0 | ⑤ | (1, 2, 4) | 有两个虚根 | —— |
| a=0 且 b=0 | ⑥ | (0, 0, 2) | 程序报错 | —— |
| 少于 3 个系数 | ⑦ | (6, 8, -) | 程序报错 | —— |
| 多于 3 个系数 | ⑧ | (1, 2, 3, 4) | 程序报错 | —— |

**验算提示（学会自己检查答案）**：
- (1,2,1)：b²-4ac = 4-4 = 0，根 = -b/(2a) = -1，两根都是 -1 ✓
- (1,4,1)：b²-4ac = 16-4 = 12 > 0，根 = (-4±√12)/2 = -2±√3 ✓
- (-1,0,1)：b²-4ac = 0+4 = 4 > 0，b = 0，根 = ±1 ✓
- (0,1,2)：a = 0 退化为 x + 2 = 0，根 = -2 ✓
- (1,2,4)：b²-4ac = 4-16 = -12 < 0，虚根 ✓

> 备考说明：教材正文把这道例题概括为「5 个有效等价类和 1 个无效等价类」，但表中实际列出了 ①～⑧ 共 8 行（①～⑤ 为有效，⑥⑦⑧ 为三种无效情况）。**考试时按方法作答即可**（说不出具体行数不影响得分），详见文末差异表。

#### 【方法 B】边界值分析法：4 步照做

```text
第 1 步  逐条读规格说明，找出所有「有边界」的输入条件和输出条件（范围、个数、有序集合、内部数据结构）
第 2 步  确定每个条件的下边界与上边界
第 3 步  取 3 类值：正好等于边界、刚刚小于边界、刚刚大于边界
         （范围类取「边界值 + 越界值」；个数类取「最小、最大、最小-1、最大+1」）
第 4 步  对每个输出条件重复第 2、3 步，并补一个「典型中间值」作对照
```

##### 示例 3（边界值分析完整示例）

**题目**：某成绩查询程序要求用户输入考试分数 score（整数），规定 **0 ≤ score ≤ 100**；程序输出该分数对应的等级（60 分及以上为及格档，60 分以下为不及格档 F）。请用边界值分析法设计测试数据。

**步骤**：
1. 找出有边界的条件：
   - 输入条件：score 的**取值范围**是 [0, 100]；
   - 输出条件：等级是**离散的若干档**，最低档 F、最高档（满分档）。
2. 确定边界：下边界 0，上边界 100。
3. 按原则 1 取值：**-1（刚刚小于下边界）、0（正好等于下边界）、1（刚刚大于下边界）、99（刚刚小于上边界）、100（正好等于上边界）、101（刚刚大于上边界）**。
4. 按原则 3 对输出条件取边界：设计使程序输出**最低等级**和**最高等级**的用例。

**答案**：

| 编号 | 测试数据 score | 边界含义 | 预期结果 |
| --- | --- | --- | --- |
| ① | -1 | 刚刚小于下边界（无效） | 提示输入非法 |
| ② | 0 | 正好等于下边界 | 最低等级 F |
| ③ | 1 | 刚刚大于下边界 | 对应的低等级 |
| ④ | 50 | 等价类中的典型值（对照用） | 对应中间等级 |
| ⑤ | 99 | 刚刚小于上边界 | 次高等级 |
| ⑥ | 100 | 正好等于上边界 | 最高等级 |
| ⑦ | 101 | 刚刚大于上边界（无效） | 提示输入非法 |

**要点**：边界值分析**不是**在等价类里随便取典型值，而是专门盯住「正好等于、刚刚大于、刚刚小于」——这正是它和等价类划分最大的区别（例题中 ④ 只是为了对照，真正的主角是 ①②③⑤⑥⑦）。

#### 【方法 C】白盒逻辑覆盖：6 种覆盖一套打通

**统一例题（教材例题，请把这段程序抄下来）**

```c
// 被测程序（教材例题）
void P(int A, int B, int X) {
    if (A > 1 && B == 0) {      // 判断 1：条件 (A>1)、条件 (B=0)
        X = X / A;              // 语句 c
    }
    if (A == 2 || X > 1) {      // 判断 2：条件 (A=2)、条件 (X>1)
        X = X + 1;              // 语句 e
    }
}
```

**流程图与路径命名（教材图 5-2 的 a、b、c、d、e）**

```text
           a（入口）
             |
      ┌──────────────┐
      │ (A>1)∧(B=0)  │  判断 1
      └──────────────┘
    否 b │        │ 是 c
         |        X = X / A
         |        |
      ┌──────────────┐
      │ (A=2)∨(X>1)  │  判断 2
      └──────────────┘
    否 d │        │ 是 e
         |        X = X + 1
         |        |
         └── 出口 ──┘

四条可能路径：(a,c,e)、(a,b,d)、(a,b,e)、(a,c,d)
```

**解题步骤（照做）**

```text
第 1 步  画出流程图/程序图，给每条分支与每条语句起名（a、b、c、d、e）
第 2 步  数一数：有几个判断？每个判断里有几个条件？共有几条路径？
第 3 步  按题目要求的覆盖标准，列出「必须被执行到的对象」清单
         语句覆盖 → 每条语句；判定覆盖 → 每个判断的真/假；条件覆盖 → 每个条件的真/假
         判定-条件覆盖 → 上面两个都要；条件组合覆盖 → 每个判断的条件组合；路径覆盖 → 每条路径
第 4 步  为每个对象挑一组输入数据，注意 X 会在程序中变化，取值时要算一遍
第 5 步  把输入、执行过程、预期输出填成表格，逐一核对是否全部覆盖
```

##### ① 语句覆盖（使每条语句都执行至少一次）

| 输入（A, B, X） | 执行过程 | 预期结果（A, B, X） |
| --- | --- | --- |
| (2, 0, 4) | A>1 且 B=0 成立 → X = 4/2 = 2；A=2 成立 → X = 2+1 = 3 | (2, 0, 3) |

只需 **1 组**用例，就能让两条赋值语句都执行一次（教材表 5-2）。**弱点：判断中的条件取假时会怎样，完全没测到。**

##### ② 判定覆盖（每个判断的取真分支和取假分支都执行至少一次）

| 输入（A, B, X） | 判断 1 | 判断 2 | 预期结果 |
| --- | --- | --- | --- |
| (2, 0, 4) | 真（X=2） | 真（X=3） | (2, 0, 3) |
| (1, 1, 1) | 假 | 假 | (1, 1, 1) |

**最少 2 组**用例即可：判断 1 真/假各一次，判断 2 真/假各一次。
> 教辅例题：对求整数绝对值的函数进行判断覆盖测试，至少需要设计的测试用例个数为 **2**（该程序只有一个判断，真、假各一次）。

##### ③ 条件覆盖（每个条件都按「真」和「假」执行至少一次）

程序中共 4 个条件：A>1、B=0、A=2、X>1。

| 输入（A, B, X） | A>1 | B=0 | A=2 | X>1 | 预期结果 |
| --- | --- | --- | --- | --- | --- |
| (1, 0, 3) | 假 | 真 | 假 | 真（3>1） | (1, 0, 4) |
| (2, 1, 1) | 真 | 假 | 真 | 假（1>1 不成立） | (2, 1, 2) |

**2 组**用例就把 4 个条件的真假都覆盖到了（教材表 5-5）。
**注意陷阱**：条件覆盖**不一定**满足判定覆盖——本例中判断 1 恰好真、假各一次，但换一个程序就可能出现「4 个条件真假都覆盖了，某个判断却只取到真」的情况。

##### ④ 判定-条件覆盖（每个判断的每个条件取真/假各至少一次，且每个判断取真/假各至少一次）

| 输入（A, B, X） | 条件取值 | 判断取值 | 覆盖路径 | 预期结果 |
| --- | --- | --- | --- | --- |
| (2, 0, 4) | A>1 真、B=0 真、A=2 真、X>1 真 | 判断 1 真、判断 2 真 | (a, c, e) | (2, 0, 3) |
| (1, 1, 1) | A>1 假、B=0 假、A=2 假、X>1 假 | 判断 1 假、判断 2 假 | (a, b, d) | (1, 1, 1) |

**2 组**用例同时满足判定覆盖与条件覆盖（教材表 5-6）。这是考试最爱考的一张表。

##### ⑤ 条件组合覆盖（每个判断的所有可能的条件取值组合都执行至少一次）

判断 1 有 2 个条件 → 2² = 4 种组合；判断 2 有 2 个条件 → 2² = 4 种组合；**共 8 种组合**（教材把它们编号为 ①～⑧）：

| 组合 | 内容 | 组合 | 内容 |
| --- | --- | --- | --- |
| ① | A>1, B=0 | ⑤ | A=2, X>1 |
| ② | A>1, B≠0 | ⑥ | A=2, X≤1 |
| ③ | A≤1, B=0 | ⑦ | A≠2, X>1 |
| ④ | A≤1, B≠0 | ⑧ | A≠2, X≤1 |

**最少 4 组用例**即可覆盖 8 种组合（因为判断 1 的 4 种组合必须由 4 组不同数据分别触发）：

| 输入（A, B, X） | 执行过程 | 条件取值 | 覆盖组合 | 预期结果 |
| --- | --- | --- | --- | --- |
| (2, 0, 4) | X = 4/2 = 2 → X = 2+1 = 3 | A>1 真、B=0 真、A=2 真、X>1 真 | ①、⑤ | (2, 0, 3) |
| (2, 1, 1) | 判断 1 假 → 判断 2 真 → X = 1+1 = 2 | A>1 真、B=0 假、A=2 真、X>1 假 | ②、⑥ | (2, 1, 2) |
| (1, 0, 3) | 判断 1 假 → X=3>1 → X = 3+1 = 4 | A>1 假、B=0 真、A=2 假、X>1 真 | ③、⑦ | (1, 0, 4) |
| (1, 1, 1) | 判断 1 假 → 判断 2 假 | A>1 假、B=0 假、A=2 假、X>1 假 | ④、⑧ | (1, 1, 1) |

##### ⑥ 路径覆盖（覆盖程序中所有可能的路径）

本例共有 **4 条**可能路径：(a,c,e)、(a,b,d)、(a,b,e)、(a,c,d)，所以要 **4 组**用例：

| 输入（A, B, X） | 执行过程 | 覆盖路径 | 预期结果 |
| --- | --- | --- | --- |
| (2, 0, 4) | 判断 1 真（X=2）→ 判断 2 真（X=3） | (a, c, e) | (2, 0, 3) |
| (1, 0, 3) | 判断 1 假 → 判断 2 真（X=4） | (a, b, e) | (1, 0, 4) |
| (4, 0, 4) | 判断 1 真（X=4/4=1）→ 判断 2 假（1>1 不成立） | (a, c, d) | (4, 0, 1) |
| (1, 1, 1) | 判断 1 假 → 判断 2 假 | (a, b, d) | (1, 1, 1) |

> 教材还给出了**基本路径测试**的示例（另一个含循环的程序）：路径 1：1-11；路径 2：1-2-3-4-5-10-1-11；路径 3：1-2-3-6-8-9-10-1-11；路径 4：1-2-3-6-7-9-10-1-11。要点是**让循环体的路径只执行一次**，从而把路径数控制在可测的范围内。

| 覆盖技术 | 要覆盖的对象 | 本例最少用例数 |
| --- | --- | --- |
| 语句覆盖 | 每条语句 | 1 |

- **单选题（计算）**：等价类个数、最少用例数、条件组合个数、路径条数、穷举测试案例数（2⁶⁴）。
- **单选题（概念辨析）**：「黑盒测试也被称为功能测试」「白盒测试的重点在代码级」。
- **简答题**：「什么是黑盒测试？什么是白盒测试？」——按教材定义答，两句都要写全。
- **简答题**：「等价类、有效等价类、无效等价类分别是什么？」

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「语句覆盖最强，路径覆盖最弱」 | 按检错能力由弱到强是：语句 → 判定 → 条件 → 判定-条件 → 条件组合 → 路径；**路径覆盖检错能力最强** |
| 「满足条件覆盖就一定满足判定覆盖」 | 不一定！条件覆盖只管每个条件的真假，不管判断整体的真假；要同时满足得用**判定-条件覆盖** |
| 「路径覆盖一定满足条件组合覆盖」 | 不一定！把每条路径跑到，未必触发每个判断的所有条件组合（见 ⑥ 中的表，4 条路径用例漏掉了 ② 与 ⑥ 两种组合） |
| 「满足条件覆盖就一定满足判定覆盖」 | 不一定。条件覆盖只管每个条件的真假，不管判断整体的真假；要同时满足得用**判定-条件覆盖** |
| 「无效等价类也可以一个用例覆盖多个」 | 无效等价类必须**一个用例只覆盖一个**，否则其余无效输入会被掩盖 |
| 边界值只取边界上的值 | 要取**正好等于、刚刚大于、刚刚小于**三种，还要看输出条件的边界 |
| 「穷举测试最实用」 | 穷举测试**能证明程序无错**，但代价极高（2⁶⁴ 个用例要跑 5 亿年），实际用的是**选择测试** |
| 「黑盒测试不需要了解程序」 | 准确说法是：不管程序内部结构，**仅以程序的外部功能为根据**设计用例 |
| 条件组合覆盖的用例数与条件数搞混 | 判断里有 n 个条件 → 该判断有 **2ⁿ** 种组合；用例数要能让每个判断的所有组合都被触发 |

## 第 3 节　单元测试

### 一句话定义

**单元测试是对单个程序模块（如一个具有特定功能的函数）进行的测试，又称模块测试。单元测试是对软件设计的最小单位（即程序模块）进行正确性检验的测试工作。**

### 用「日常生活比喻」来理解

把整个软件想成**一辆汽车**，单元测试就是**逐个零件检验**：先单独测刹车片、再单独测发动机。

问题来了：单独测发动机时，**车上其他零件还没装或者还没测好**。怎么办？拿两个「替身」来帮忙：

- **驱动模块** = 给发动机供电、加油、按下启动键的那个人（**调用者**）；
- **桩模块** = 假装是变速箱的假零件，只要能被发动机连上就行（**被调用的下级模块的替身**）。

### 关键概念逐个讲透

#### 1）单元测试的步骤（识记）

**单元测试的一般步骤：编写辅助模块 → 设计测试用例 → 运行执行测试。**

#### 2）驱动模块与桩模块（识记，最爱考区分）

| 辅助模块 | 教材定义 | 一句话记 |
| --- | --- | --- |
| **驱动模块** | 相当于被测试模块的**调用者程序**。驱动模块接收测试数据，再把这些数据传送给被测模块，最后输出实际的测试结果 | 在上面的「老板」 |
| **桩模块** | 用于**代替被测模块所调用的模块**。桩模块仅进行少量的数据操作，不需要把被测模块所调用模块的功能都放进来 | 在下面的「临时工」 |

> 教辅例题：关于驱动模块的叙述，正确的是 → 答「**驱动模块相当于被测试模块的调用者程序**」。干扰项「用于代替被测模块的子模块」说的是**桩模块**。

#### 3）单元测试的 5 个方面内容（识记 + 领会，简答题高频）

在单元测试阶段需要分别从**模块接口、局部数据结构、路径、错误处理、边界** 5 个方面对模块进行检查：

**① 模块接口测试**（领会）

1. 检查模块输入参数与模块的形式参数的数量、类型、顺序是否匹配；
2. 检测被测模块调用子模块时，子模块接收到的输入参数与子模块的形式参数的数量、属性、顺序是否匹配；
3. 是否修改了仅作为输入的形式参数；
4. 输出给标准函数的参数的数量、类型、顺序是否正确；
5. 全局变量的定义在各模块中是否一致；
6. 是否限制了仅采用形式参数进行参数传递。

**② 局部数据结构测试**（领会）

1. 是否存在不正确或不一致的数据类型说明；
2. 是否使用了没有赋值或没有被初始化的变量；
3. 局部变量是否被设置了错误的缺省值或初始值；
4. 局部变量名的拼写是否存在错误。

**③ 路径测试**（领会）

1. 是否存在错误的计算；
2. 是否存在比较错误或控制流的错误。

**④ 错误处理测试**（领会）

1. 出错描述难以理解；
2. 出错描述不足以对错误定位，难以确定出错原因；
3. 预测的错误与实际的错误不符；
4. 对错误条件的处理不正确；
5. 在对错误进行处理之前，错误条件已经引起系统的干预。

**⑤ 边界测试**（领会）

程序很容易在一些边界值上出错，如**循环的边界值**引起的错误、**数组下标的边界值**引起的错误、**比较条件的边界值**错误等。因此需要特别注意数据流、控制流中**刚好等于、大于或小于**确定的比较值时出错的可能性，对这些地方应仔细设计或选择测试用例。

> 教辅例题：单元测试阶段进行的路径测试需要测试的内容包括 → 答「**运算的优先次序是否存在错误**」（属于「是否存在错误的计算」）。干扰项：输入参数类型是否正确 → 模块接口测试；OPEN 语句与 CLOSE 语句是否正确 → 模块接口测试；循环边界值引起的错误 → 边界测试。

### 考试这样考

- **单选题**：「驱动模块的作用是」→ 相当于被测模块的调用者程序；「桩模块的作用是」→ 代替被测模块所调用的模块。
- **单选题**：「下列属于单元测试内容的是 / 下列属于局部数据结构测试的是」。
- **简答题**：「单元测试包括哪 5 个方面的内容？」→ 模块接口、局部数据结构、路径、错误处理、边界。
- **简答题**：「单元测试的步骤是什么？」→ 编写辅助模块 → 设计测试用例 → 运行执行测试。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 把驱动模块与桩模块说反 | 驱动在上（调用者），桩在下（被调用者的替身） |
| 「桩模块要实现被调用模块的全部功能」 | 桩模块**仅进行少量的数据操作**，不需要把功能都放进来 |
| 「单元测试 = 测试一个函数，不需要额外写代码」 | 需要编写**辅助模块**（驱动模块、桩模块） |
| 「循环边界出错属于路径测试」 | 属于**边界测试**；路径测试管的是错误的计算、比较错误或控制流错误 |
| 「变量未初始化属于模块接口测试」 | 属于**局部数据结构测试** |

## 第 4 节　组装测试

### 一句话定义

**组装测试也叫作集成测试**，是把已经通过单元测试的模块按设计组装起来，检查模块之间接口与整体功能的测试。

**组装测试有一次性组装测试和增殖式组装测试两种方式；增殖式组装测试又分为自顶向下的组装测试、自底向上的组装测试及混合组装测试三种方式。合起来就是 4 种组装方式。**

### 用「日常生活比喻」来理解

把模块想成**积木**，组装测试就是「把积木搭起来看会不会倒」：

| 方式 | 比喻 | 代价 |
| --- | --- | --- |
| **一次性组装** | 把所有积木一次全倒出来，一口气搭成城堡 | 搭不起来时，**不知道是哪块积木的问题** |
| **自顶向下** | 先搭塔尖，再往下挂积木（缺的下层用纸盒代替 = **桩模块**） | 早看到整体效果，但**纸盒（桩）难做** |
| **自底向上** | 先把底层积木拼成小方块，再一层层往上垒（缺的上层用支架托着 = **驱动模块**） | **支架（驱动）好做**、可并行，但**最后才看到整体** |
| **混合组装** | 两种办法混着用 | 取长补短 |

### 关键概念逐个讲透

#### 1）一次性组装测试（识记）

把单元测试过的**所有模块组装在一起进行测试**。缺点是**查找错误位置和错误原因、纠正错误都比较困难**。

#### 2）自顶向下的组装测试（识记方式 + 领会步骤与评价）

**步骤**：

1. 把**主模块**作为所测模块的**驱动模块**，所有直属于主模块的下属模块**全部用桩模块代替**，对主模块进行测试；
2. 采用**深度优先或分层**的策略，用实际模块替代相应模块，再用模块代替这些实际模块的直接下属模块，与已测试的模块或子系统组装成新的子系统；
3. 进行**回归测试**，即重新执行以前做过的全部或部分测试，检查和排除组装过程中可能引入的新错误；
4. 判断是否所有的模块都已经组装到系统中：若还有没被组装的模块，则转第 2 步；否则终止组装测试。

**评价**：

- 优点：① 能**较早看到整个系统的效果**；② 能**较早发现主要控制中的错误**；③ **先测试输入分支**，可为以后的测试提供保证。
- 缺点：**需要编写桩模块，而编写桩模块是比较困难的**。

#### 3）自底向上的组装测试（识记方式 + 领会步骤与评价）

**步骤**：

1. 由**驱动模块控制最底层模块的并行测试**，也可以把最底层的模块组合成实现某一特定功能的**簇**，由驱动模块控制对它的测试；
2. 用**实际模块代替驱动模块**，与直属于该实际模块且已测试过的模块组装为子系统；
3. 为子系统**配备驱动模块**，进行新的测试；
4. 判断是否已经组装到主模块，是则结束测试，否则执行步骤 2。

**评价**：

- 优点：① **驱动模块比较容易编写**；② 多个模块或子系统**可并行测试**，以提高测试效率。
- 缺点：**最后才能测试主控模块，整个系统的结果最后才能看到**。

#### 4）混合组装测试（识记方式）

教材给出 3 种具体做法：

1. **演变的自顶向下的组装测试**：强化对**输入/输出模块和引入新算法模块**的测试，并**自底向上**组装成为功能完整且相对独立的子系统，然后由主模块开始**自顶向下**进行组装测试；
2. **自底向上-自顶向下的组装测试**：先对**包含读操作**的子系统采用自底向上直到根节点的组装测试，然后对**含有写操作**的子系统做自顶向下的组装测试；
3. **回归测试**：采用**自顶向下**的方式测试被修改过的模块及其子模块，然后将该部分作为子系统，再进行**自底向上**的测试，以检查该子系统与其上层模块的接口是否适配。

**关键模块的特征（常考多选/简答）**：

1. 满足某些软件需求；
2. 在程序的模块结构中处于**较高的层次**，是高层的控制模块；
3. **较复杂且易出错**；
4. 有**明确定义的性能要求**。

#### 5）组装测试计划时应考虑的问题（领会）

1. 采用**何种组装方式**进行组装测试；
2. 组装测试过程中**连接各个模块的顺序**；
3. 模块代码的编写和测试进度是否与组装测试的顺序一致；
4. 测试过程中**是否需要专门的硬件设备**。

#### 6）组装测试完成的标志（领会，3 条）

1. **成功地执行了测试计划中规定的所有组装测试**；
2. **修正了测试过程中所发现的错误**；
3. **测试结果通过了测试小组的评审**。

### 考试这样考

- **单选题**：「组装测试的方式有」→ 一次性组装 + 增殖式（自顶向下、自底向上、混合），共 4 种。
- **单选题（对比）**：「需要编写桩模块、比较困难的是」→ 自顶向下；「驱动模块容易编写、可并行测试的是」→ 自底向上。
- **简答题**：「组装测试有哪几种组装模块的方式？」→ 按上面 4 种答。
- **简答题**：「组装测试完成的标志是什么？」→ 3 条。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「自顶向下需要编写驱动模块」 | 自顶向下缺的是**下层**，用**桩模块**；自底向上缺的是**上层**，用**驱动模块** |
| 「一次性组装最容易定位错误」 | 恰恰相反，它**最难查找错误的位置和原因** |
| 「自底向上能较早看到系统整体效果」 | 那是**自顶向下**的优点；自底向上**最后才能看到**整体结果 |
| 把「回归测试」当成一种组装方式 | 回归测试是**贯穿各方式的活动**（重新执行以前做过的全部或部分测试），混合组装里也用到它 |
| 「组装测试完成的标志是没发现错误」 | 标志是：执行完计划的全部组装测试、修正了发现的错误、结果通过测试小组评审 |

## 第 5 节　确认测试

### 一句话定义

**确认测试的任务是验证软件的功能、性能及其他特性是否与用户的需求一致。**

**软件需求规格说明书中包括了对软件功能及性能的要求、全部用户可见的软件属性及有效性准则。其中，有效性准则是软件确认测试的基础。**

### 用「日常生活比喻」来理解

把软件想成**定制西装**：

- 裁剪缝制完成（单元测试、组装测试做完）后，要请**客户本人**来试穿——这才是**确认测试**（确认是否与用户需求一致）；
- 试穿要按合同上的尺寸标准来量（→ **有效性准则**是确认测试的基础）；
- 试穿时还要**清点配件**：领带、备用扣子、洗涤说明有没有齐（→ **软件配置复审**）；
- 最后客户签字收货，还要穿一整天活动活动、看看洗过之后会不会缩水（→ **验收测试、安装测试、专家鉴定**）。

### 关键概念逐个讲透

#### 1）确认测试的任务（识记）

验证软件的功能、性能及其他特性**是否与用户的需求一致**。

#### 2）有效性测试（领会）

**有效性测试通过黑盒测试技术完成**，其任务是：验证被测试的软件**是否满足需求规格说明书中定义的所有功能需求和性能要求**，同时要**保证所有文档是正确且易于使用的**。

> 注意：确认测试阶段的测试用例一般从**用户角度**设计，测试数据一般选择**应用场景中的实际数据**。

#### 3）软件配置复审（识记目的）

**软件配置复审的目的是保证软件配置的所有成分都齐全，各方面的质量都符合要求，有软件维护阶段所必需的细节，而且已经编排好分类的目录。**

#### 4）确认测试阶段需要完成的工作（领会，简答题）

**确认测试阶段需要完成的工作包括：进行有效性测试、软件配置复审、进行验收测试、安装测试以及专家鉴定。**

其中**验收测试**的特点：

- 以**用户为主**，由软件开发人员和质量保证人员参加；
- **用户参加测试用例设计**，通过软件的用户界面输入测试数据并分析测试的输出结果；
- 测试数据一般选择**应用场景中的实际数据**；
- 除了测试软件的功能及性能外，还要对软件的**可移植性、兼容性、可维护性以及错误的恢复功能**等进行确认。

**确认测试的结果有两种情况**：

1. 功能和性能与用户的要求一致，**软件可以接受**；
2. 功能和性能与用户的要求**有差距**——此时需要列出软件各项缺陷，提交**软件缺陷表或软件问题报告**，通过与用户协商解决。

**确认测试完成后应提交的文档**：**确认测试分析报告、最终的用户手册和操作手册、项目开发总结报告。**

#### 5）系统测试的任务（领会）

**系统测试是将通过确认测试的软件，作为整个基于计算机系统的一个元素，与计算机硬件、外设、支持软件、数据和人员等其他系统元素结合在一起，在实际运行环境下对计算机系统进行一系列的组装测试和确认测试。**

一句话：**确认测试看「软件符不符合需求」，系统测试看「软件装进整个真实系统后能不能干活」。**

#### 6）软件测试的种类及其适用阶段（领会）

教材列出 19 种测试：

| 序号 | 种类 | 要点 |
| --- | --- | --- |
| 1 | 设计评审 | 对软件设计方案及软件设计规格说明书进行检查和评审 |
| 2 | 代码审查 | 由评审小组通过阅读、讨论，对程序代码进行分析、检查 |
| 3 | 功能测试 | 在规定的一段时间内运行软件系统的所有功能，以检测是否有严重错误 |
| 4 | 结构测试 | 在详细了解程序模块结构的情况下进行的测试（即白盒测试） |
| 5 | 回归测试 | 检查软件经过修改后是否引入了新的错误 |
| 6 | 可靠性测试 | 需求规格说明书中有可靠性要求时进行；指标为①平均失效间隔时间 ②因故障造成的停机时间 |
| 7 | 强度测试 | 检查在系统运行环境发生不正常开始到发生故障的情况下，系统可以运行到何种程度 |
| 8 | 性能测试 | 检查系统是否满足需求规格说明书中规定的性能（实时系统、嵌入式系统尤其要满足时间性能要求） |
| 9 | 恢复测试 | 证实克服硬件故障（如掉电、硬件或网络出故障）后系统能否正常继续工作，且不对系统造成损害 |
| 10 | 启动/停止测试 | 检测在机器启动及关机阶段，软件系统正确处理的能力 |
| 11 | 配置测试 | 检查计算机系统内各个设备或各种资源之间的联结和功能分配中的错误 |
| 12 | 安全性测试 | 检验系统中已经存在的系统安全性及保密性措施是否发挥作用、有无漏洞 |
| 13 | 可使用性测试 | 从使用的合理性和方便性等角度检查软件系统，发现使用上的问题 |
| 14 | 可支持性测试 | 验证系统的支持策略对于公司与用户是否切实可行 |
| 15 | 安装测试 | 检测软件安装过程中出现的错误 |
| 16 | 互连测试 | 验证两个或多个系统之间的互连性 |
| 17 | 兼容性测试 | 验证软件产品在不同版本之间的兼容性 |
| 18 | 容量测试 | 检验系统能力最高能达到什么程度 |
| 19 | 文档测试 | 检查用户文档的清晰度和准确性 |

**与阶段的对应关系（按定义整理，教材未逐条给出，见文末差异表）**：

| 阶段 | 常见的测试种类 |
| --- | --- |
| 编码/单元测试阶段 | 代码审查、结构测试（白盒）、功能测试（单模块） |
| 组装测试阶段 | 结构测试、功能测试、回归测试、配置测试 |
| 确认测试阶段 | 功能测试、性能测试、可使用性测试、可移植性/兼容性、安装测试、文档测试 |
| 系统测试阶段 | 可靠性、强度、性能、恢复、启动/停止、配置、安全性、可使用性、可支持性、安装、互连、兼容性、容量、文档测试 |
| 维护阶段 | 回归测试（修改之后必做） |

### 考试这样考

- **单选题**：「有效性测试通过什么技术完成」→ 黑盒测试技术。
- **单选题**：「以用户为主，由软件开发人员和质量保证人员参加的测试是」→ 验收测试。
- **简答题**：「什么是系统测试？」「确认测试阶段需要完成哪些工作？」——两道教辅例题，答案见上。
- **简答题**：「软件配置复审的目的是什么？」→ 保证配置成分齐全、质量符合要求、有维护所需细节、已编排好分类目录。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「确认测试的目的是发现编码错误」 | 确认测试验证**软件与用户需求是否一致**；发现编码错误主要靠单元测试、组装测试 |
| 「有效性测试用白盒技术」 | 有效性测试**通过黑盒测试技术完成** |
| 「验收测试由开发人员主导」 | 验收测试**以用户为主**，用户还参加测试用例设计 |
| 「系统测试就是确认测试」 | 系统测试是把软件与**硬件、外设、支持软件、数据、人员**结合，在**实际运行环境**下进行的一系列组装测试和确认测试 |
| 「确认测试做完不用交文档」 | 要交：确认测试分析报告、最终的用户手册和操作手册、项目开发总结报告 |

## 第 6 节　静态测试

### 一句话定义

静态测试**不需要执行被测程序**，它通过**程序的静态分析**（生成各种引用表、静态错误分析）和**人工测试**（桌前检查、代码评审、走查）来找出编译过程无法发现的错误。

### 用「日常生活比喻」来理解

静态测试就像**老师批改作文但不动笔改写**：

- 先列一张**词汇表**，看哪些词用了、哪些词没定义就用了（→ **引用表**：标号交叉引用表、变量交叉引用表、子程序/宏/函数引用表、等价表、常量表）；
- 再挑**语法与逻辑毛病**（→ **静态错误分析**：变量类型分析、引用分析、表达式分析、接口分析）；
- 最后**开教研会一起读**（→ **人工测试**：桌前检查、代码评审、走查）。

教材给了一个很有说服力的数据：使用人工测试方法**能够有效地发现 30%～70% 的逻辑设计和编码错误**。

### 关键概念逐个讲透

#### 1）程序的静态分析之一：生成各种引用表（识记 + 领会）

按用途分 3 类：

1. **直接从表中查出说明/使用错误**：如循环层次表、变量交叉引用表、标号交叉引用表；
2. **为用户提供辅助信息**：如子程序/宏/函数引用表、等价表、常数表；
3. **用来做错误预测和程序复杂度计算**：如操作符和操作数的统计表等。

5 种常用引用表：

| 引用表 | 内容 |
| --- | --- |
| **标号交叉引用表** | 列出在各模块中出现的全部标号，顺序可按出现先后或字典顺序 |
| **变量交叉引用表** | 即变量定义与引用表；顺序可按出现先后、字典顺序，也可按变量类型排序 |
| **子程序/宏/函数引用表** | 列出各个子程序、宏和函数的属性：已定义/未定义、定义类型；输入参数与输出参数的个数、顺序、类型；已引用/未引用、引用次数等 |
| **等价表** | 列出在等价语句或等值语句中出现的全部变量和标号 |
| **常量表** | 列出全部数字常数和字符常数，并指出它们在哪些语句中首先被定义（首先出现在哪些赋值语句左侧，或出现在哪些数据语句或参数语句中） |

#### 2）程序的静态分析之二：静态错误分析（识记 4 类）

| 类型 | 教材内容 |
| --- | --- |
| **变量类型分析**（变量分析） | 为了强化对源程序中数据类型的检查，在程序设计语言中扩充一些新的数据类型 |
| **引用分析** | 静态错误分析中经常需要分析的内容就是发现**引用异常**，如变量在赋值以前被引用，或变量在赋值以后未被引用 |
| **表达式分析** | （教材只列标题，未展开；见文末差异表） |
| **接口分析** | （教材只列标题，未展开；见文末差异表） |

> 小提示：**引用分析**抓的是「赋值前被引用」「赋值后未被引用」——这正是第 8 节静态分析工具的功能之一（检查是否引用了未定义的变量、是否有已赋过值但从未使用的变量）。

#### 3）人工测试的 3 种方法（领会，最爱考区分）

| 方法 | 谁来做 | 教材要点 |
| --- | --- | --- |
| **桌前检查** | **程序员自己** | 一种传统的检查方法，由程序员检查自己编写的程序；在程序**通过编译之后**对源程序代码进行分析、检查以发现错误，并补充相关文档 |
| **代码评审** | **若干程序员和测试员组成的评审小组** | 通过**阅读、讨论**，对程序进行静态分析的过程 |
| **走查** | **走查小组** | 与代码评审**基本相同**，过程分**两步**：先把材料发给走查小组每个成员让其认真研究程序，**再开会** |

> 注意一个「反常识」的考点：测试原则里说「程序员应该避免检查自己的程序」，但**桌前检查恰恰是程序员检查自己的程序**——它是静态分析阶段的一种传统方法，两者不矛盾（桌前检查是自查代码，不是替代独立测试）。

### 考试这样考

- **单选题**：「下列属于静态测试的是」→ 桌前检查、代码评审、走查、引用表、静态错误分析（凡是不运行程序的都对）。
- **单选题（区分）**：「由评审小组通过阅读、讨论对程序进行分析、检查的过程是」→ 代码评审；「先发材料研究、再开会」→ 走查；「程序员检查自己的程序」→ 桌前检查。
- **简答题**：「程序的静态分析有哪几种方法？」→ 生成各种引用表、静态错误分析。
- **简答题**：「静态错误分析包括哪些内容？」→ 变量类型分析、引用分析、表达式分析、接口分析。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「静态测试 = 不重要的测试」 | 人工测试能有效发现 **30%～70%** 的逻辑设计和编码错误 |
| 「桌前检查是评审小组做的」 | 桌前检查是**程序员自己**做；评审小组做的是**代码评审** |
| 「走查就是开会」 | 走查分两步：**先发材料研究，再开会** |
| 「变量交叉引用表用来查语法错误」 | 引用表主要查**说明/使用错误**、提供辅助信息、做错误预测与复杂度计算 |
| 「引用分析找的是拼写错误」 | 引用分析找的是**引用异常**（赋值前被引用、赋值后未被引用） |

## 第 7 节　调试技术

### 一句话定义

**软件调试是在测试之后开始的工作。软件测试的目的是尽可能多地发现软件中的错误，调试的任务则是发现错误的原因和位置并改正程序中的错误。**

### 用「日常生活比喻」来理解

把测试与调试想成**看病**：

- **测试** = 体检，负责**发现异常指标**；
- **调试** = 医生**诊断病因并开药**（找原因、找位置、动手改）。

医生诊断有 4 种套路：

| 调试方法 | 医生版本 | 适用场景 |
| --- | --- | --- |
| **强行排错** | 把所有化验单全打出来一项项看 | 用得多但**效率低** |
| **回溯法** | 从症状出现的地方往前倒推吃了什么 | 适合**小程序** |
| **归纳法** | 收集多个病例 → 整理 → 提出假设 → 验证 | 从特殊到一般 |
| **演绎法** | 先列出所有可能病因 → 逐个排除 → 验证剩下那个 | 从一般到特殊 |

### 关键概念逐个讲透

#### 1）调试的任务与调试活动的组成（识记）

调试的任务：**发现错误的原因和位置并改正程序中的错误**。

调试活动由两部分组成：

1. **确定程序中可疑错误的确切性质和位置**；
2. **对程序（设计、编码）进行修改，排除这个错误**。

#### 2）调试的步骤（领会，5 步）

1. 从错误的**外部表现形式**入手，确定程序出错的位置；
2. 研究有关部分的程序，找出错误的**内在原因**；
3. **修改设计和代码**以排除错误；
4. **重复进行暴露了这个错误的原始测试及其他有关测试**，以确认是否排除了该错误以及是否引发了新的错误；
5. 如果所做的修正无效，则**撤销这次改动**，将程序恢复到修改之前的状态，重复上述过程，直到找到有效的解决办法为止。

#### 3）调试可采用的方法（识记 + 领会）

**① 强行排错**（使用较多、效率较低的调试方法）：

1. **通过内存全部打印来排错**：将计算机存储器和寄存器的全部内容打印出来，然后在这些大量的数据中寻找出错的位置；
2. **在程序特定部位设置打印语句**：把打印语句插入到关键变量值发生变化处、重要分支处、子程序调用处，跟踪程序执行，监视重要变量的变化；
3. **自动调试工具**：利用某些程序语言的调试功能或专门的交互式调试工具，分析程序的动态过程，而不必修改程序。

**② 回溯法排错**（适合小程序排错的一种有效方法）：
发现错误时，**先分析错误现象、确定最先发现错误表现的位置**，然后**沿程序的控制流程回溯程序代码**，直到找到错误根源或确定引发错误的程序代码的范围。

**③ 归纳法排错**（从特殊性总结出一般规律的方法，4 步）：

1. **收集有关的数据**：列出正确和存在错误的结果；
2. **组织数据**：归纳法是从特殊到一般的推断过程，因此需要组织和整理数据，以便发现规律；
3. **提出假设**：分析与错误相关的线索之间的关系，利用在线索结构中观察到的矛盾现象，设计一个或多个关于出错原因的假设；
4. **证明假设**：把假设与原始线索或数据进行比较，若它完全能解释一切与错误有关的现象，则假设得以证明。

**④ 演绎法排错**（从一般原理或前提出发，经过排除和精化的过程推导出结论）：
测试人员首先根据已有的测试用例，**设想及枚举出所有可能出错的原因作为假设**，然后再用原始测试数据或新的测试数据执行程序，**从中逐个排除不正确的假设**，最后用测试数据**验证剩余的假设**是引发错误的原因。

#### 4）调试的原则（领会，两组）

**确定错误的性质和位置的原则（4 条）**：

1. **用头脑去分析、思考与错误征兆有关的信息**；
2. **避开死胡同**；
3. **只把调试工具当作辅助手段来使用**；
4. **避免用试探法**。

**修改错误的原则（5 条）**：

1. 在出现错误的地方，**很可能还有别的错误**；
2. 修改错误的一个常见失误是**只修改了这个错误的表现，而没有修改错误的本质**；
3. **修正一个错误的同时有可能会引入新的错误**；
4. 修改错误的过程将迫使程序员**暂时回到程序设计阶段**；
5. 发现错误的原因和位置后，应**修改源代码程序，而不要改变目标代码**。

### 考试这样考

- **单选题**：「适合小程序排错的调试方法是」→ 回溯法；「使用较多、效率较低的调试方法是」→ 强行排错。
- **单选题**：「归纳法排错的第一步是」→ 收集有关的数据。
- **简答题**：「调试活动由哪两部分组成？」「调试可采用哪些方法？」「修改错误的原则有哪些？」
- **判断题式选项**：「发现错误后应修改目标代码」→ 错，应**修改源代码程序**。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「测试与调试是一回事」 | 测试**发现**错误，调试**定位原因并改正**错误；调试在测试之后开始 |
| 「调试应该优先用试探法」 | 原则明确要求**避免用试探法** |
| 「调试工具是主要手段」 | 原则要求**只把调试工具当作辅助手段** |
| 「归纳法与演绎法是一回事」 | 归纳法是**从特殊到一般**（先收集数据再提假设）；演绎法是**从一般到特殊**（先枚举假设再逐个排除） |
| 「改完一个错误就万事大吉」 | 出错的地方很可能还有别的错误，而且修正一个错误可能引入新错误，必须**重复原来的测试** |
| 「直接改目标代码更快」 | 应**修改源代码程序，而不要改变目标代码** |

## 第 8 节　软件测试工具

### 一句话定义

软件测试工具是**帮助测试人员自动完成分析、执行、度量、比对工作的程序**：静态分析工具**不执行**被测程序；动态测试工具**要执行**被测程序，按功能分为测试覆盖监视程序、断言处理程序、符号执行程序及测试结果分析程序 4 类。

### 用「日常生活比喻」来理解

把测试工具想成**体检中心的设备**：

- **静态分析工具** = 拍 X 光片、做 CT：不用你跑起来，先看结构有没有问题（扫描文档与程序正文，分析数据流和控制流，输出测试报告）；
- **测试覆盖监视程序** = 运动手环：记录你到底跑了哪些路线、跑了几次；
- **断言处理程序** = 报警器：预先设好「血压应满足的条件」，一超限就报；
- **符号执行程序** = 用公式推演代替真跑：把输入当符号推演路径；
- **测试结果分析程序** = 体检报告解读：告诉你哪项开销最大、哪段时间最长。

### 关键概念逐个讲透

#### 1）静态分析工具的组成（识记，4 部分）

**静态分析工具一般由源程序的预处理器、数据库、错误分析器和报告生成器 4 部分组成。**

工作流程（教材原文）：

```text
源程序 → 预处理器（把词法分析与语法分析结合在一起，识别各种类型的语句；
                   把源程序划分为若干程序模块单元，同时生成包含变量使用、变量类型、
                   标号与控制流等信息的许多表格）
       → 数据库（存放这些表格）
       → 错误分析器（在用户指导下利用命令语言或查询语言与系统通信以进行查错）
       → 报告生成器（生成和输出检查结果表）
```

#### 2）静态分析工具的功能（领会，6 类）

1. 检查模块中的**所有变量是否都已定义**，是否引用了未定义的变量，是否有已赋过值但从未使用的变量；
2. 检查**模块接口的一致性**：子程序调用时形式参数与实际参数的个数、类型是否一致，输入/输出参数的定义与使用是否匹配，数组参数的维数、下标变量的范围是否正确，子程序中使用的外部变量、全局变量定义是否一致等；
3. 检查在**逻辑上可能有错误的结构**以及**不可能被执行到的程序段**；
4. 建立**变量/语句交叉引用表、子程序调用顺序表、公用区/子程序交叉引用表**等，利用它们找出变量错误可能影响到哪些语句、影响到哪些其他变量等；
5. 检查被测程序**违反编程标准的错误**（模块大小、模块结构、注释的规定、某些语句形式的使用以及文档编制的规定等）；
6. 一些**静态特性的统计功能**（各种类型源语句的出现次数、标识符在每条语句中的使用情况、函数与过程引用情况、任何输入数据都执行不到的孤立代码段、未经定义或未曾使用过的变量、违背编码标准之处等）。

#### 3）动态测试工具按功能的分类（识记，4 类）

**动态测试就是通过选择适当的测试用例，实际运行所测程序，比较实际运行结果和预期结果以找出错误。动态测试工具按功能分为：测试覆盖监视程序、断言处理程序、符号执行程序及测试结果分析程序。**

**① 测试覆盖监视程序**（主要用在**结构测试**中，可以监视测试的**实际覆盖程度**）——工作过程 3 个阶段：

1. 对所测试程序做**预处理**；
2. **编译**预处理后的源程序，**运行目标程序**；
3. 一组测试后，可以根据要求输出：某语句的执行次数、某转移发生的次数、某赋值语句的数值范围、某循环控制变量的数据范围以及某子程序运行的时间、被调用次数等，从而**发现异常情况**。

**② 断言处理程序**（领会）：
「断言」是指**变量应满足的条件**。在被测试源程序中，在指定位置按一定格式用**注释语句**写出的断言叫作**断言语句**。工作过程 3 步：

1. 对源程序做**预处理**，为注释语句中的每一个断言**插入一段相应的检验程序**；
2. **运行**经过预处理的程序，验证被检查程序的**实际运行结果与断言所规定的逻辑状态是否一致**；
3. 一组测试结束后，程序输出**统计结果、现场信息**，供测试人员分析。

**③ 符号执行程序**（领会）：
符号执行法是一种介于**程序测试用例执行与程序正确性证明之间**的方法。它使用一个专用的程序对输入的源程序进行解释，在解释执行时，**所有的输入都以符号形式输入到程序中**（包括基本符号、数字及表达式等）。
**符号执行结果有两个用途**：其一是可以**检查公式的执行结果是否达到程序预期的目的**；其二是**通过程序的符号执行产生程序的路径，为进一步自动生成测试数据提供条件**。

**④ 测试结果分析程序**（领会，4 项功能）：

| 功能 | 内容 |
| --- | --- |
| **调节分析** | 确定所测程序哪部分执行次数最多、哪部分最少，甚至未执行过 |
| **成本估算** | 确定所测程序哪些部分执行开销最大 |
| **时间分析** | 报告某一程序或其部分程序的 CPU 执行时间 |
| **资源利用** | 分析与硬件和系统软件相关的资源利用情况 |

#### 4）测试数据自动生成工具的分类（识记，3 类）

1. **路径测试数据生成工具**；
2. **随机测试数据生成工具**；
3. **根据数据规格说明生成测试数据的生成工具**。

#### 5）模块测试台的功能（领会）

由于模块与其他模块之间存在调用与被调用关系，测试一个模块时需要为它编写**驱动模块和桩模块**以代替它的上下层有关模块。**模块测试台就是承担生成这类模块的工具**：它提供一种专门的**测试用例描述语言**，负责将输入数据传送给被测试模块，然后将实际输出结果与描述测试用例的语言中所表述的期望结果进行比较，以找出错误。

模块测试台还具有如下功能：

1. **语句跟踪**；
2. **动态断言**；
3. **覆盖度量**；
4. 建立**用户自定义符号的符号表**；
5. **生成内容表**；
6. **生成某种格式的输出**。

#### 6）集成测试环境（组装测试环境）的构成和作用（领会）

随着自动测试工具的发展，出现了将多种测试工具融为一体的**集成化测试系统**：它把多种不同的自动测试功能集成在一个测试系统中，**管理测试过程并提供自动化软件测试功能**；一个组装测试系统可能涵盖从**单元测试到组装测试以及基于网络的端到端测试**等各个方面，能**大大提高测试效率和质量**。

> 备考提示：教材对「集成测试环境的**构成**」只作了上述概述性说明，没有逐项列出组成部件（见文末差异表）。答题时抓住「多工具集成 + 管理测试过程 + 覆盖从单元测试到端到端测试 + 提高效率与质量」。

### 考试这样考

- **单选题**：「静态分析工具由哪几部分组成」→ 预处理器、数据库、错误分析器、报告生成器。
- **单选题**：「动态测试工具按功能分为」→ 测试覆盖监视程序、断言处理程序、符号执行程序、测试结果分析程序。
- **单选题**：「测试数据自动生成工具分为」→ 路径测试数据生成、随机测试数据生成、根据数据规格说明生成。
- **简答题**（教辅例题）：「软件的静态分析工具有哪些功能？动态测试工具有哪些功能？」
  - 静态分析工具：上述 6 类功能；
  - 动态测试工具：自动生成测试用例、自动生成驱动模块和桩模块、监视测试的实际覆盖程度、分析测试结果等。

### 易错点

| 易错说法 | 为什么错 |
| --- | --- |
| 「静态分析工具需要运行程序」 | 静态分析工具**不需要执行**所测试的程序，它扫描文档与程序正文，分析数据流和控制流 |
| 「断言是写在程序里的可执行语句」 | 断言按一定格式用**注释语句**写出，由断言处理程序在预处理时插入检验程序 |
| 「符号执行就是真的运行程序」 | 符号执行时**所有输入都以符号形式**输入，介于测试用例执行与正确性证明之间 |
| 「测试结果分析程序只做时间分析」 | 它有 4 项功能：调节分析、成本估算、时间分析、资源利用 |
| 「模块测试台只生成测试数据」 | 它生成**驱动模块和桩模块**、提供用例描述语言、比对期望结果与实际结果，还具备语句跟踪、动态断言、覆盖度量等 6 项功能 |

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 以为测试是为了「证明程序没错」 | 测试的目的是**发现错误**；只有穷举测试能证明无错，而它代价极高不现实 |
| 把条件覆盖当成「比判定覆盖强」 | 两者**互不包含**；要同时满足判定与条件，用**判定-条件覆盖** |
| 无效等价类也用一个用例盖多个 | 无效等价类必须**一个用例只覆盖一个**，否则其余非法输入测不到 |
| 边界值只在边界上取值（如只取 0 和 100） | 必须取**正好等于、刚刚大于、刚刚小于**（如 -1、0、1、99、100、101） |
| 驱动模块与桩模块分不清 | 驱动是**调用者**（在下面往上顶的测试中缺），桩是**被调用者的替身** |
| 自顶向下与自底向上记反优缺点 | 自顶向下：**桩难写**、早看整体；自底向上：**驱动好写、可并行**、最后才看到整体 |
| 测试完成后忘了保存资料 | 原则 8 条明确要求妥善保存测试计划、测试用例、出错统计和分析报告，供维护使用 |
| 调试时直接改目标代码 | 应修改**源代码程序**，不要改变目标代码 |

| 差异点 | 考纲怎么说 | 教辅怎么说 | 备考建议 |
