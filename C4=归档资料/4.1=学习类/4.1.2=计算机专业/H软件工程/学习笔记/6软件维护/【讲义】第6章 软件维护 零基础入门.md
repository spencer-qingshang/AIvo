## 开篇：这一章到底在讲什么？

前面几章讲的是「怎么把软件造出来」，这一章讲的是**软件交付之后那漫长的几十年**。

一个软件真正的成本大头不在开发，而在**交付之后的修改**——改错误、跟着环境升级、加新功能、为将来做预防。这一章要回答 4 个问题：

1. **维护是什么、为什么要维护、有几种维护？**（第 1 节）
2. **维护按什么流程做？谁审批、谁改代码、改完怎么验证、会踩什么坑？**（第 2 节）
3. **什么样的软件「好维护」？怎么给它打分？**（第 3 节）
4. **怎样在开发阶段就把「好维护」做进去？**（第 4 节）

在全书的逻辑链里，这一章是**收尾环节**：软件过程的 4 种基本活动（需求分析、设计和实现、测试、**软件演进**）中的最后一项，落到具体工作上就是「维护」。所以第 1 章讲过的「软件需要演进」，本章告诉你演进到底怎么干。

## 第 1 节　软件维护概述

### 一句话定义

**软件维护 = 软件交付使用之后，为了改正错误或满足新的需要而修改软件的过程。**

教材原话：「软件维护就是在软件已经交付使用之后，为了改正错误或满足新的需要而修改软件的过程。」

### 用「日常生活比喻」来理解

把软件想成你买的一辆车。

| 车的日常 | 软件维护 | 对应类型 |
| --- | --- | --- |
| 车开起来有异响，去 4S 店修好 | 程序跑起来报错，改掉这个 bug | **改正性维护** |
| 换了城市，得重新上牌、适配新油品 | 换了新操作系统、换了新设备，程序得改一改才能跑 | **适应性维护** |
| 想加装倒车影像、座椅加热 | 用户提出要新功能、新性能 | **完善性维护** |
| 提前做防锈处理、定期换机油，免得以后大修 | 提前把代码重构好、把文档补好，让将来好改 | **预防性维护** |

一句话区分：**改错 → 改正性；换环境 → 适应性；加功能 → 完善性；防将来 → 预防性。**

### 关键概念逐个讲透

#### 【识记】软件维护的定义

「软件维护就是在软件已经交付使用之后，为了改正错误或满足新的需要而修改软件的过程。」

两个关键词别丢：**交付使用之后**（时间范围）＋**修改软件**（不是重新开发）。

#### 【识记】引起软件维护的原因（3 条）

1. 用户在使用软件的过程中发现了**软件测试阶段没有发现的错误**。
2. 软件在使用过程中**环境发生变化**（更换新的操作系统、更新设备等）。
3. 用户在使用软件的过程中**产生了新的需求**。

> 考点提示：教材例题里，「软件投入运行的时间太长」被列为**错误**的原因——时间长短本身不引起维护，引起维护的是「发现错误」「环境变化」「新需求」这三件事。

#### 【识记】软件维护的分类（4 类，必须背全）

| 类型 | 定义（教材表述） | 典型场景 |
| --- | --- | --- |
| **改正性维护** | 识别和纠正软件错误、改正软件性能上的缺陷 | 用户报了一个 bug，开发人员定位并修复 |
| **适应性维护** | 适应外部环境（新的硬件及软件配置）发生变化 | 操作系统从 Windows 10 升到 Windows 11，程序要适配 |
| **完善性维护** | 完善用户提出的新功能与性能要求 | 用户要求「再加一个导出 Excel 的功能」 |
| **预防性维护** | 提高软件的可维护性、可靠性等 | 主动重构、补文档，为将来修改铺路 |

> 这里的「外部环境」指**硬件及软件配置**，不指业务环境；业务上的新要求属于完善性维护。

#### 【领会】影响软件维护工作量的因素（5 条）

| 因素 | 对工作量的影响 |
| --- | --- |
| 1. 软件系统的规模 | 系统越大、功能越复杂，工作量越高 |
| 2. 程序设计语言 | 使用**强功能的程序设计语言**可以控制程序规模，从而减少维护工作量；用汇编语言等低级语言写的程序难读难改，工作量变大 |
| 3. 系统年龄 | 老系统比新系统维护工作量更大 |
| 4. 数据库技术的应用 | 使用数据库可以简单有效地管理和存储数据，减少生成用户报表应用软件的维护工作量 |
| 5. 先进的软件开发技术 | 如面向对象技术、软件复用技术等，可减少大量维护工作量 |

#### 【领会】三种维护采取的不同策略

这是本节最容易混的地方，请**按「维护类型 → 策略」成对记**。

| 维护类型 | 采取的策略 |
| --- | --- |
| **改正性维护** | ① 利用应用软件包可开发出比用户自己开发的系统可靠性更高的软件；② 采用结构化技术开发的软件易于理解和测试；③ 利用防错性程序设计，把自检功能引入程序，通过非正常状态的检查，提供审查跟踪；④ 通过**周期性维护审查**，在形成维护问题前就可确定质量方面的问题 |
| **适应性维护** | ① 在**配置管理**时，把硬件、操作系统和其他相关环境因素的可能变化考虑在内；② 把与硬件、操作系统以及其他外围设备有关的程序**归到特定的程序模块中**，使因环境变化而必须修改的程序局限于某些模块；③ 使用内部程序列表、外部文件以及处理的例行程序包，为维护时修改程序提供方便 |
| **完善性维护** | 利用前两类维护中列举的方法，也可以减少这一类维护的工作量；特别是**数据库管理系统、程序生成器、应用软件包**，可减少系统或程序员的维护工作量 |

#### 【领会】维护工作量的模型

教材给出的模型是一个**指数型**公式：

```
M = p + K^(c − d)
```

| 符号 | 含义 |
| --- | --- |
| **M** | 维护中消耗的总工作量 |
| **p** | 生产性工作量（如分析和评价、设计、修改和实现） |
| **K** | 一个经验常数 |
| **c** | 因缺乏好的设计和文档而导致复杂性的度量 |
| **d** | 对软件熟悉程度的度量 |

读懂这个公式的含义：软件维护工作分成**生产性活动**（真正在改代码：分析和评价、设计、修改和实现）和**非生产性活动**（试图理解代码的功能和算法、数据结构的作用、模块间传了什么参数）。

公式说明：如果**使用了不好的软件开发方法、软件文档不齐全、程序难以理解、原来参加开发的人员或小组不能参加维护、维护人员对软件不熟悉**，那么工作量及成本将**按指数级增加**。

> 记忆抓手：`c − d` 越大（越复杂、越不熟悉），`K^(c−d)` 涨得越快，M 就爆炸。这就是「文档和人员交接比代码本身更值钱」的数学表达。

### 考试这样考

- 直接考定义原文（单选或多选的变形）。
- 给一个场景，问属于哪一类维护（**改正性 / 适应性 / 完善性 / 预防性**四选一，最容易错）。
- 「下列不属于引起软件维护的原因的是」这类反向题。
- 维护工作量模型里某个字母的含义（尤其 `c`、`d`、`p`）。
- 影响维护工作量的因素，问「会导致维护工作量和难度变大的是」。

### 易错点

- 把「用户提出新功能」当成适应性维护——**它是完善性维护**。
- 把「提高可维护性」当成改正性维护——**它是预防性维护**。
- 以为「软件运行时间长」是维护原因——**不是**。
- 以为「采用高级语言」会增加维护工作量——**恰恰相反，高级语言减少维护工作量**。

## 第 2 节　软件维护的过程

### 一句话定义

软件维护的过程 = **从「有人提出维护申请」到「改完、验证完、验收完」的一整套组织分工与操作步骤**。

### 用「日常生活比喻」来理解

把它想成**去医院看病的完整流程**：

| 医院 | 软件维护机构 | 干什么 |
| --- | --- | --- |
| 病人递挂号单 | 用户提交**维护申请报告** | 提出「哪里不舒服」 |
| 导诊台分诊 | **维护管理员** | 把申请转给对口的医生 |
| 专科医生诊断 | **系统监督员** | 是技术人员，必须熟悉产品程序的某一部分，负责评价申请 |
| 主治医生定方案 | **修改负责人** | 确定如何进行软件的修改 |
| 手术室监督 | **配置管理员** | 严格把关，控制修改的范围，对软件配置进行审计 |
| 做手术的医生 | **维护人员** | 真正动手改程序 |
| 术后复查 | 重新验证程序 | 静态确认 → 计算机确认 → 维护后验收 |

### 关键概念逐个讲透

#### 【领会】维护机构的组织及组织内的分工

教材图 6-1「软件维护工作机构的组织方案」的流程是：

```
                    ┌───────────────┐
                    │ 软件维护申请报告 │
                    └───────┬───────┘
                            ↓
   修改负责人 ←───────→ 维护管理员 ←───────→ 系统监督员
        │                   │
        ↓                   ↓
   配置管理员 ←────────→ 维护人员
```

用文字说清 5 个角色的分工：

| 角色 | 职责 |
| --- | --- |
| **维护管理员** | 接收提交上来的软件维护申请报告，把申请交给某个系统监督员去评价 |
| **系统监督员** | 技术人员，必须熟悉产品程序的某一部分；对软件维护申请做出评价 |
| **修改负责人** | 在系统监督员评价之后，确定如何进行软件的修改 |
| **配置管理员** | 在维护人员修改程序的过程中严格把关，控制修改的范围，对软件配置进行审计 |
| **维护人员** | 具体执行程序的修改 |

考过的判断题要点：确认维护要求需要**维护人员与用户反复协商**；系统监督员**也可以同时承担其他角色**的工作；应确立**正式或非正式的**维护机构（不是「必须建立正式机构」）；维护管理员**也可以参与**程序修改工作。

#### 【领会】维护申请报告的内容

维护申请报告是**由软件组织外部提交的文档**，它是**筹划维护工作的基础**。软件组织内部应形成相应的软件修改报告，报告应对以下内容进行说明：

1. 所需修改变动的**性质**。
2. 申请修改的**优先级**。
3. 为完成某个软件维护申请报告中的维护内容所需的**工作量**。
4. **预计修改后的状况**。

#### 【领会】软件维护工作的一般步骤

教材的流程图（从提交申请到软件复审）共 8 步：

```
提交维护申请 → 确认维护要求 → 判断维护类型 → 评价软件错误程度
      → 确定维护工作的优先次序 → 进行问题分析 → 修改代码、测试代码 → 软件复审
```

两个分支细节必须记：

- 第一步是先**确认维护要求**；第二步是由**维护管理员确认维护类型**。
- 对于**改正性维护申请，从评价错误的严重性开始**。
- 对于**适应性维护和完善性维护申请，需要先确定每项申请的优先次序**。

#### 【领会】维护档案记录

为了估计软件维护的有效程度，确定软件产品的质量，同时确定维护的实际开销，需要在维护的过程中做好维护档案记录。内容包括：

程序名称、源序语条数、机器代码指令条数、所用的程序设计语言、程序安装的日期、程序安装后的运行次数、与程序安装后运行次数有关的故障处理次数等。

#### 【领会】维护性能方面的度量值（维护评价，7 条）

1. 每次程序运行时的平均出错次数。
2. 花费在每类维护上的总「人时」数。
3. 每个程序、每种语言、每种维护类型的程序平均修改次数。
4. 因为维护而增加或删除每个源程序语句所花费的平均「人时」数。
5. 用于每种语言的平均「人时」数。
6. 维护申请报告的平均处理时间。
7. 各类维护申请的百分比。

#### 【识记】软件维护期间对程序进行修改的 3 个步骤

**分析理解程序 → 修改程序 → 重新验证程序。** 这三步是本节的核心骨架，下面逐个展开。

#### 【领会】分析理解程序必须完成的工作和所采取的方法

**必须完成的 5 项工作：**

1. 理解程序的**功能和目标**。
2. 掌握程序的**结构**，即从程序中细分出若干结构成分，如程序系统结构、控制结构、数据结构和输入/输出结构等。
3. 了解**数据流信息**，即所涉及的数据来自何处，在哪里被使用。
4. 了解**控制流信息**，即执行每条路径的结果。
5. 理解程序的**操作要求**。

**所采取的方法（自顶向下地理解现有源程序的程序结构和数据结构）：**

1. **分析程序结构图**：分析各个过程的接口，估计更改的复杂性。
2. **数据跟踪**：对过程内部的一些变量和控制流进行跟踪。

#### 【领会】程序修改计划的内容及程序修改的方法

**修改计划要写清 4 类内容：**

| 类别 | 具体内容 |
| --- | --- |
| 规格说明信息 | 数据修改、处理修改、作业控制语言修改、系统之间接口的修改等 |
| 维护资源 | 新程序版本、测试数据、所需的软件系统等 |
| 人员 | 程序员、用户相关人员、技术支持人员、厂家联系人、数据录入员等 |
| 需要的工作资源 | 纸、笔、计算机媒体等 |

**制定修改计划可采用自顶向下的方法，在理解程序的基础上进行以下工作：**

1. 研究程序的各个模块、模块的接口及数据库，从全局的观点提出修改计划。
2. 依次把要修改的以及受修改影响的模块和数据结构分离出来。
3. 详细分析要修改的以及受变更影响的模块和数据结构的内部细节，设计修改计划，标明新逻辑及要改动的现有逻辑。
4. 向用户提供回避措施。

#### 【领会】修改程序时应遵循的要求（6 条）

1. 正确、有效地编写修改程序。
2. 谨慎修改程序，尽量保持程序风格及格式，程序清单注明改动指令。
3. 不要删除程序语句，除非确定它是无用的。
4. **不要试图共用程序中已有的临时变量或工作区**，为了避免冲突或混淆用途，应自行设置自己的变量。
5. 插入错误检测语句。
6. 修改过程中做好修改的详细记录，消除变更中任何有害的副作用。

#### 【领会】重新验证程序的方法（3 种）

| 方法 | 做法 |
| --- | --- |
| **静态确认** | 修改软件伴随着引起新错误的危险；为了能够做出正确的判断，验证修改后的程序**至少需要两个人参加** |
| **计算机确认** | 在充分进行了静态确认的基础上，要用计算机对修改程序进行确认测试 |
| **维护后的验收** | 在交付新软件之前，维护主管部门要对相关内容进行检验 |

#### 【领会】修改程序的副作用（3 种，必须背全）

| 副作用 | 触发原因 | 后果 |
| --- | --- | --- |
| **修改代码的副作用** | 使用程序设计语言修改源代码时 | 可能引入错误 |
| **数据的副作用** | 修改数据结构时 | 可能造成软件设计与数据结构不匹配，因而导致软件出错 |
| **文档的副作用** | 对数据流、软件结构、模块逻辑或任何其他有关特性进行修改时，未对相关技术文档做相应修改 | 导致文档与程序功能不匹配、缺省条件改变、新错误信息不正确等错误，使得软件文档不能反映软件的当前状态 |

### 考试这样考

- 把「维护申请报告应该交给谁」当成角色配对题（答案是**维护管理员**）。
- 「软件维护工作基本流程的第一步是什么」（**确认维护要求**）。
- 「修改程序的副作用」给场景选类型：**文档内容与程序不一致 → 文档的副作用**。
- 「下列属于/不属于修改程序时应遵循的要求」。
- 简答题高频：软件维护的组织机构包含哪些角色、软件维护的工作步骤是什么。

### 易错点

- 把「提出申请」当成第一步——流程的真正第一步是**确认维护要求**。
- 记混「修改负责人」和「配置管理员」：**修改负责人定方案，配置管理员管范围与审计**。
- 把「重新验证程序」只记成「再测一遍」——它是**静态确认 → 计算机确认 → 维护后验收**三段。
- 三种副作用一一对应：**代码对代码、数据对数据结构、文档对技术文档**。

## 第 3 节　软件的可维护性

### 一句话定义

**软件可维护性是指纠正软件系统出现的错误和缺陷，以及为满足新的要求进行软件修改的容易程度。**

说白了：**这个软件「好不好改」。**

### 用「日常生活比喻」来理解

把软件想成一套**房子**，「可维护性」就是「这套房子好不好打理」。看房时你会关心 7 件事，正好对应 7 个指标：

| 看房时关心 | 可维护性指标 | 含义 |
| --- | --- | --- |
| 户型图、水电图齐不齐，一眼看得懂吗 | **可理解性** | 读代码和文档就能懂功能与内部结构 |
| 出故障了能不能快速查出来 | **可测试性** | 论证程序正确性的容易程度 |
| 想砸墙改格局容易吗 | **可修改性** | 程序容易修改的程度 |
| 房子结实吗，会不会老漏水 | **可靠性** | 给定时间内正确执行的概率 |
| 换城市还能住吗 / 搬家能不能带走 | **可移植性** | 转移到新的计算环境的难易程度 |
| 住着顺手吗，老人小孩会不会用错 | **可使用性** | 方便、实用及易于使用的程度 |
| 省不省水电 | **效率** | 执行预定功能而不浪费计算机资源的程度 |

### 关键概念逐个讲透

#### 【识记】衡量软件可维护性的 7 个指标

**可理解性、可测试性、可修改性、可靠性、可移植性、可使用性、效率。**

记忆口诀：**「理解 → 测试 → 修改」是核心三件套，再加「可靠、移植、使用、效率」四个外围。**

#### 【识记】7 个指标的定义与要点

| 指标 | 定义 | 补充要点 |
| --- | --- | --- |
| **可理解性** | 表明人们通过阅读源代码和相关文档，了解程序功能及其内部结构的容易程度 | 见下方「可理解的程序应具备的 4 个特性」 |
| **可靠性** | 表明一个程序按照用户的要求和设计目标，在给定的一段时间内正确执行的概率 | 度量标准主要有**平均失效间隔时间、平均修复时间和有效性**；度量方法有两大类（见下） |
| **可测试性** | 表明论证程序正确性的容易程度 | 程序越简单，证明其正确性就越容易；设计好的测试用例基于对程序的全面理解 |
| **可修改性** | 表明程序容易修改的程度 | 一个可修改的程序应当是可理解的、通用的、灵活的、简单的 |
| **可移植性** | 表明程序转移到一个新的计算环境的难易程度 | 可移植性好的程序的特点是**结构良好、灵活，不依赖于某一具体计算机硬件体系结构或操作系统** |
| **效率** | 表明一个程序能执行预定功能而又不浪费计算机系统资源的程度 | 这些资源包括**内存容量、外存容量、通道容量和执行时间** |
| **可使用性** | 指程序方便、实用及易于使用的程度 | 一个可使用性好的程序应是易于使用、允许用户出错和改变并尽可能不使用户陷入混乱状态的程序 |

#### 【领会】可理解的程序应具备的主要特性（4 条）

1. 模块结构良好，功能完整，程序和文档简明。
2. 代码风格与设计风格一致。
3. 不使用难以理解或含糊不清的代码。
4. 使用有意义的变量名、数据名和过程名。

#### 【识记】度量可靠性的方法（两大类）

| 方法 | 做法 |
| --- | --- |
| **根据程序错误统计数字进行可靠性预测** | 常用方法是利用**可靠性模型**，根据程序测试时发现并排除的错误数量，预测平均失效间隔时间 |
| **根据程序的复杂性预测软件可靠性** | 利用程序复杂性度量标准，预测哪些模块最可能发生错误、以及可能出现的错误类型 |

#### 【领会】程序修改难度的估算公式

测试可修改性的一种定量方法是**修改练习**：通过做几个简单的修改，来评价修改的难度。

```
D = A / C
```

| 符号 | 含义 |
| --- | --- |
| **C** | 程序中各个模块的平均复杂性 |
| **n** | 必须修改的模块数 |
| **A** | 要修改的模块的平均复杂性 |
| **D** | 修改的难度 |

判断规则：**对于简单的修改，若 D > 1，说明该程序修改困难。**

算例：某程序所有模块的平均复杂性 C = 10，需要修改的模块平均复杂性 A = 15，则 D = 15 / 10 = 1.5 > 1，说明这个程序修改困难。

#### 【领会】表 6-1　在各类维护中应侧重的软件可维护性指标

这是教材原表，考试可以直接照着出「哪一项是完善性维护应侧重的指标」这类题：

| 指标 | 改正性维护 | 适应性维护 | 完善性维护 |
| --- | --- | --- | --- |
| 可理解性 | √ | | |
| 可测试性 | √ | | |
| 可修改性 | √ | √ | |
| 可靠性 | √ | | |
| 可移植性 | | √ | |
| 可使用性 | | √ | √ |
| 效率 | | | √ |

记忆抓手：**改正性维护最看重「可理解、可测试、可修改、可靠」（要能看懂、能查出、能改对）；适应性维护看重「可修改、可移植、可使用」；完善性维护看重「可使用、效率」（加功能是为了更好用、更快）。**

#### 【领会】间接定量度量可维护性的方法中涉及的指标

> **重要提醒**：这一条是**大纲明确要求**的领会点，但《电子教辅（通用版）》与《精讲总结》《串讲总结》都**没有展开**。
> 可以确定的是：教材 6.3 节中，**可靠性**用「平均失效间隔时间、平均修复时间、有效性」来度量，**可修改性**用「修改练习」的 `D = A / C` 来度量，这两者是教辅中明确给出的**定量**度量方法；至于「间接定量度量方法涉及的指标」的完整清单，**本讲义不作编造**，请以教材正文为准。

### 考试这样考

- 「评价软件可维护性的指标有哪些」——简答高频，必须能一次说全 7 个。
- 「下列不属于软件可维护性指标的是」——反向题，常拿「可重用性」「可扩充性」等教材外的词当干扰项。
- 给定义选指标名：「表明论证程序正确性的容易程度」→ **可测试性**。
- 计算题：给出 C 和 A，算 D 并判断是否「修改困难」。
- 表 6-1 的配对题。

### 易错点

- **可测试性不是「测试做得多不多」**，而是「论证程序正确性容不容易」。
- **可移植性不是「代码能复制粘贴」**，而是「能不能换一套计算机环境继续跑」。
- **效率的资源清单别漏**：内存容量、外存容量、**通道容量**和执行时间。
- D = A / C，**分母是全部模块的平均复杂性，分子是要修改的模块的平均复杂性**，别写反；判据是 **D > 1 表示修改困难**（不是 D < 1）。

## 第 4 节　提高软件可维护性的方法

### 一句话定义

在软件开发的全过程中，通过**明确质量目标、使用好技术与工具、做质量保证审查、选对语言、写好文档**，把「好维护」做进软件里。

### 用「日常生活比喻」来理解

提高可维护性就像**保持身体健康**：

- 先定目标（是跑马拉松还是减脂？）→ **建立明确的软件质量目标和优先级**；
- 平时养成好习惯（规律作息、科学饮食）→ **使用提高软件质量的技术和工具**；
- 定期体检，早发现早处理 → **进行明确的质量保证审查**；
- 选对运动项目（膝盖不好就别跑越野）→ **选择易维护的程序设计语言**；
- 病历本写清楚，换医生也看得懂 → **改进程序文档**。

### 关键概念逐个讲透

#### 【领会】总纲：提高可维护性的 4 个方面

1. 建立明确的软件质量目标和优先级。
2. 使用提高软件质量的技术和工具。
3. 进行明确的质量保证审查。
4. 选择易维护的程序设计语言。

#### 【领会】建立明确的软件质量目标和优先级

尽管可维护性要求每一种质量特性都要得到满足，但它们的**相对重要性应随程序的用途及计算环境的不同有所区别**。例如：**编译程序的效率更重要**，而**管理信息系统的可使用性和可修改性更重要**。

所以，对程序的质量特征提出目标的同时**必须规定它们的优先级**，这样有助于提高软件的质量，并对软件生存期的费用产生很大的影响。

#### 【识记】模块化的优点

模块化是软件开发过程中提高软件质量、降低成本的有效方法之一，也是提高可维护性的有效技术。它的优点是：

1. 如果需要**改变某个模块的功能，只要改变这个模块**，对其他模块影响很小。
2. 如果需要**增加程序的某些功能，仅需要增加完成这些功能的新模块或模块层**。
3. 程序的测试与重复测试比较容易。
4. 程序错误易于定位和纠正。

> 补充【领会】：**结构化程序设计**不仅使得模块结构标准化，而且将模块间的相互作用也标准化了，因而把模块化又向前推进了一步；采用结构化程序设计可以获得良好的程序结构，提高现有系统的可维护性。

#### 【领会】进行明确的质量保证审查（3 种软件审查）

| 审查 | 时机 | 作用 |
| --- | --- | --- |
| **① 设置检查点进行复审** | 开发过程**每一阶段的终点**设置检查点 | 证实已开发的软件是否符合标准，是否满足规定的质量需求；不同检查点检查重点不完全相同 |
| **② 验收检查** | 软件验收时 | 保证**新**软件系统的可维护性 |
| **③ 周期性地维护审查** | 对**已有**的软件系统 | 检查点复查和验收检查用于保证新软件系统，对已有系统则应当进行周期性的维护检查 |

核心思想：**保证软件质量的最佳方法是在软件开发的最初阶段就把质量要求考虑进去。**

#### 【领会】验收检查必须遵循的最小验收标准（4 类）

| 类别 | 最小验收标准 |
| --- | --- |
| **需求和规范标准** | ① 需求应当以**可测试的术语**进行书写、排列优先次序和定义；② 区分**必需的、任选的、将来的**需求；③ 对系统运行时的计算机设备的需求，对维护、测试、操作以及维护人员的需求，对测试工具等的需求 |
| **设计标准** | ① 程序应设计成**分层的模块结构**，每个模块应完成唯一的功能，并达到**高内聚、低耦合**；② 通过一些知道预期变化的实例，说明设计的**可扩充性、可缩减性和可适应性** |
| **源代码标准** | ① 尽可能使用**最高级的**程序设计语言，且只使用语言的**标准版本**；② 所有的代码都必须具有良好的结构；③ 所有的代码都必须**文档化**，在注释中说明它的输入、输出，以及便于测试/再测试的特点与风格 |
| **文档标准** | 说明程序的输入/输出、使用的方法/算法、错误恢复方法、所有参数的范围以及缺省条件等 |

#### 【领会】选择易维护的程序设计语言

- 程序设计语言的选择对程序的可维护性**影响很大**。
- **低级语言程序（机器语言和汇编语言）难理解且难掌握，因此很难维护。**
- **高级语言程序比低级语言程序更容易理解，具有更好的可维护性。**
- 同是高级语言，可理解程度也不一样。教材举例：现在基于人工智能的应用程序，大多使用 **Python** 语言而不是 C 语言或 C++ 语言，既能提高软件开发效率，又能提高软件的可维护性。

#### 【识记】好的文档的作用及意义（3 条）

好的文档是**建立可维护性的基本条件**：

1. 有相应的好文档的程序比没有文档的程序更容易理解，因为它增加了程序的**可读性和可使用性**；但**质量低劣的文档比没有文档还要糟糕**。
2. 好的文档意味着**简洁、风格一致且易于更新**。
3. **程序应当成为其自身的文档**，如在程序中插入清晰、详细的注释可以提高程序的可理解性。

#### 【识记】3 种历史文档

在软件维护阶段，利用**历史文档**，可以大大简化维护工作：

| 历史文档 | 说明 |
| --- | --- |
| **系统开发日志** | 记录开发过程的历史 |
| **错误记载** | 记录曾经发生过的错误 |
| **系统维护日志** | 记录历次维护的情况 |

### 考试这样考

- 「提高软件可维护性的方法有哪些」——简答，按 4 个方面答。
- 「模块化的优点不包括……」——反向题。
- 「保证软件可维护性的软件审查有哪 3 种」。
- 「验收检查必须遵循的最小验收标准包括哪几类」。
- 「哪种语言更利于提高可维护性」——人工智能类应用选 **Python**。
- 「3 种历史文档是什么」——直接识记题。

### 易错点

- 以为「文档越多越好」——教材明确说**低劣文档比没有文档更糟**。
- 把「检查点复审」和「周期性维护审查」混为一谈：**前者管新软件开发过程，后者管已有系统。**
- 验收检查的 4 类标准要区分：**需求 → 设计 → 源代码 → 文档**，顺序别乱。
- 选语言题里 **Python ≠ 低级语言**，机器语言与汇编语言才是低级语言。

## 新手最容易踩的坑

| 坑 | 正确做法 |
| --- | --- |
| 把「用户提新功能」当成适应性维护 | 适应环境变化 = 适应性维护；用户提新功能 = **完善性维护** |
| 把「软件运行时间长」当成维护原因 | 维护原因只有 3 条：发现遗留错误、环境变化、产生新需求 |
| 认为文档越多越好 | 教材原话：**质量低劣的文档比没有文档还要糟糕** |
| 记混配置管理员与修改负责人 | **修改负责人定「怎么改」，配置管理员管「改的范围」并做审计** |
| 把 D = A / C 写反 | **分子 A 是要修改模块的平均复杂性，分母 C 是全部模块的平均复杂性** |
| 只背 7 个指标的名字，不会对应定义 | 用「看房子」的比喻把 7 个指标和 7 种直观感受一一挂钩 |
